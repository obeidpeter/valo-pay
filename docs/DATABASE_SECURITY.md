# Database security boundary

## Scope and rationale

Valo Pay remains an isolated **synthetic observation sandbox**, not an approved system for real lender/customer data. Its runtime security boundary is the application's scoped repository. This deliberately replaces a custom PostgreSQL role, RLS policies and a record-protection trigger that the observed managed publishing path did not reproduce faithfully. An opt-in restricted runtime adds forced row security again for a separately commissioned staging schema (see Development setup and publishing); it is off by default, and the preview database has not been commissioned with it.

By default the database connection is privileged. Explicit application checks **do not** provide the same independent barrier as a non-bypass database role with correctly configured RLS. A leaked database credential, malicious server code or an unscoped query can bypass application authorisation and immutability. Do not describe this redesign as preserving database-enforced isolation.

## Enforcement

- Identity comes from verified Clerk request context or the existing high-entropy anonymous sandbox cookie, not a caller-supplied principal/workspace identifier. An absent or malformed sandbox cookie creates a separate synthetic workspace; it never grants access to an existing workspace. New anonymous sandboxes are limited to 20 per client address per hour on top of the general request limit, and the cookie lifetime (30 days) slides with each visit. Where `VALOPAY_EXPIRED_WORKSPACE_CLEANUP=on`, as the deployment sets it (`docs/deployment.md`), an anonymous sandbox older than 30 days with no change by a person in that time becomes eligible for deletion, and it is deleted only when a new anonymous sandbox is created: that request removes up to five eligible sandboxes, oldest first (their idempotency answers, records, lenders and, by cascade, operations journal, then the workspace), so an eligible sandbox stays until enough new visitors arrive. The sweep first locks every lender of the sandbox without waiting and leaves a sandbox whose lender a scheduled close, the export worker, a test delivery or a request holds for a later sweep, so it never waits for or deadlocks with them; activity is read from the audit chain, so entries by system actors (the seed, the scheduled close) never keep a sandbox alive, and signed-in and staff workspaces are never swept. Export files in private storage are not deleted by the sweep. Without the setting (the development workspace) nothing is deleted.
- Three modules may touch the database, and `scripts/check-db-boundary.mjs` refuses a database import, a raw query or a connection setting anywhere else in the runtime source (the start-up check, `artifacts/api-server/src/lib/startup-config.ts`, may read `DATABASE_URL` only to refuse a missing or malformed value, never to connect): the scoped repository (`artifacts/api-server/src/lib/valopay-store.ts`), which owns request and scheduler SQL; the export job store (`artifacts/api-server/src/lib/export-job-store.ts`), whose worker transactions are scoped to one lender; and the runtime isolation module (`artifacts/api-server/src/lib/runtime-isolation.ts`), which verifies and binds the restricted scope. Workspace membership, selected merchant ownership and record predicates must be checked explicitly. Routes/domain code must not obtain raw clients or unrestricted query functions.
- With `VALOPAY_STAFF_ACCESS=staging`, identity is a verified Clerk session instead: every staff request loads the organisation's workspace and the caller's membership in its own transaction, holds them locked through commit, and passes them to the access and MFA check in `docs/pilot-security.md` before it reads anything else.
- The scheduled daily close is the one platform-initiated write path. It runs in the API process, on its background worker thread (`artifacts/api-server/src/background.ts`) through the same repository modules, one merchant per system transaction (`inMerchantAsSystem`), scoped to that merchant's own workspace and principal so every repository predicate still applies, with the merchant row taken `FOR UPDATE ... SKIP LOCKED` so it never queues behind a request and two processes never close the same lender at once. It writes through the same load, audit and save path as a request, under the actor `System · scheduled close`. Which merchants are due is read from the server-owned `settings.nextCloseAt` cursor. Two small service writes sit outside a merchant transaction: a lender's first `nextCloseAt`, written only where none is set, and after a failed close the `settings.closeRetry` record (the pending time, the number of failed attempts and the next attempt; never the error text, because settings are shown to the lender's users), written with the row taken `FOR UPDATE SKIP LOCKED` so a lender held by a request is left alone. The scheduler's pause of an idle sandbox's automatic close goes through the same load, audit and save path as a close. The settings endpoint strips `nextCloseAt`, `closeRetry` and `closePausedForInactivityAt` from client input. A sandbox workspace holds at most five lenders; the count runs under the exclusive workspace lock that lender creation takes, so two creations at once cannot both pass it.
- Every workspace transaction holds the workspace's advisory lock: shared for ordinary work, exclusive for persona, team, lender-access and invitation changes. PostgreSQL grants advisory locks in arrival order, so a change waits only for the work already running and is never overtaken by later requests; if that work does not finish within the request lock limit, the change answers 503 with nothing changed. The workspace row is still locked after it (`FOR SHARE`, or `FOR UPDATE` for a change), so the expiry sweep's `SKIP LOCKED` skips busy workspaces. A principal transaction lock serialises only first-visit workspace creation. A mutation takes an exclusive merchant row lock (`FOR UPDATE`) that serialises state validation, allocations, idempotency and audit sequence generation across processes, not just within one Node instance. A read takes a share lock (`FOR SHARE`), so it sees one consistent merchant state, waits for an in-flight mutation to commit, and never queues behind other reads. Lock waits are bounded: a request waits at most 5 s for a lock and is then answered 503 with nothing saved, and one lender cannot occupy more than half of a process's database connections (`artifacts/api-server/src/lib/database-limits.ts`). The lender a request names is read before the request is authorised, so the cap is counted per workspace (a staff organisation or a sandbox) and lender: a request that names another workspace's lender waits only behind its own workspace's requests. The cap limits one tenant's effect on others but does not remove it. Two lenders busy at once can fill the pool (five connections each of the default ten), and every other request then waits up to the 5 s checkout limit and may be answered 503. Because the cap is half of whatever the pool is, a larger `VALOPAY_DATABASE_POOL_SIZE` leaves room for other tenants only while each busy lender has fewer requests in flight than half the pool. Requests that name no lender are not counted against any lender. The background worker thread, which runs the scheduled closes and the export worker, has a pool of its own of three connections (one close and two export slots), so neither takes a request's connection nor waits for one; with readiness's one connection, an instance holds at most the pool size plus four (`docs/deployment.md`).
- Reads, business mutations, idempotent responses and audit appends share the authorised transaction. The repository retains its own original state for mutation validation, rather than trusting a snapshot supplied by its callers.
- The repository refuses record deletion, tenant/identity reassignment, immutable-evidence edits and changes to frozen approved/preregistered/closed versions. It validates linked records and final allocation totals before committing.
- Ordinary database foreign keys, primary/unique indexes, safe-integer money bounds and the due-item ticket floor provide additional protections. Cross-record allocation caps and evidence immutability are application rules, not triggers.
- Private exports are accessible only through authorised merchant metadata and checksum-verified downloads. The metadata is resolved inside the authorised transaction and the object is read after it ends, so no merchant lock is held for the duration of a download. Object storage is not part of the SQL transaction: an object uploaded before a later database failure can be orphaned, but must not become accessible through another tenant.
- Hash chains detect corruption relative to their stored history. They do not establish independent tamper-proof evidence against a privileged actor able to rewrite both history and hashes.

## Development setup and publishing

One opt-in database layer sits beside this boundary, and no migration of its runs during installation, build, startup or deployment. The restricted runtime is commissioned by hand with the migration owner, in a separate `valopay_runtime_staging_*` schema: `lib/db/migrations/005_runtime_isolation.sql` creates a restricted login, a non-login helper owner, scope helpers, a workspace guard and forced row security on the ten application tables, and `lib/db/migrations/006_runtime_isolation_scope.sql`, which the application requires, evaluates the same rules once per statement instead of once per row. Its isolation rehearsal (`docs/pilot-database.md`) applies both only in a disposable test schema. With `VALOPAY_RUNTIME_ISOLATION=staging` (which also needs staff access), the API refuses an elevated login and, in every transaction, compares the policies, helpers and guard with the reviewed set in `artifacts/api-server/src/lib/runtime-isolation-policy.ts`, answering 503 on any difference (`docs/pilot-operations-controls.md`). It does not authorise real data; commissioning the identity service, the restricted login and managed keys on a host, and managed-host recovery testing, remain separate work.

The Drizzle schema defines the supported tables, foreign keys, checks and unique indexes. A fresh development setup uses the normal development schema push. Do not reintroduce custom security roles, policies or triggers as an undeclared setup prerequisite. The pull-request workflow creates the schema the same way inside a PostgreSQL 16 service container that exists only for its job and holds no application secret; that is a development push against a throwaway database, not a production migration path.

The existing development database transitions only after replacement application enforcement exists. Retiring the old objects must use narrowly scoped, reviewed development changes, preserve data and ordinary constraints, and never cascade-delete unknown role dependencies.

Production remains managed by the Publish flow, and nothing applies a migration automatically: no build-hook schema push, no startup-time DDL and no deployment step that runs one. The numbered files in `lib/db/migrations` are applied by hand, by the database owner, in order, before the build that needs them is published; `docs/database-migrations.md` is the one procedure for them (which are required, superseded or optional commissioning, the commands, verification and rollback). Inspect the freshly generated development-to-production diff before concluding a publishing problem is resolved: successful compilation does not prove migration fidelity. Review unexpected drops/renames and confirm all required ordinary constraints and expression/partial indexes retain their semantics.

Removing the original role/policy dependencies addresses their specific missing-role failure mechanism. Only a subsequent user-initiated successful publish and post-publish checks establish that the complete publishing process works.

## Verification and residual requirements

- Run the database-boundary check, repository mutation/integration tests, API security regression script and existing smoke checks against the final schema **without** the legacy policies and trigger.
- Exercise foreign identities/merchant IDs, optional linked references, protected records, failed imports, transaction rollback, concurrent allocations/idempotency and audit sequencing, and authorised/unauthorised export downloads.
- Static boundary checks are a development safeguard, not a sandbox against malicious or deliberately obfuscated code.
- Real data remains blocked pending independent security assessment, production staff provisioning/MFA, documented hosting and legal prerequisites, tested recovery, and an explicitly approved production isolation design.

The reproducible checks are the ones in the README under "Checks and builds": `pnpm test` (database boundary, snapshot safeguards, repository guards, export collector and the golden suites), `pnpm run test:security-api` and `pnpm run test:smoke` against a running API, and the database-backed integration suites run with `VALOPAY_RUN_INTEGRATION=1`; the repository and scheduled-close suites (`pnpm run test:integration`) also run on every pull request against the workflow's throwaway database, while the export-stream and HTTP suites remain manual. The development transition evidence stays in the Replit workspace and is not part of this source snapshot.
