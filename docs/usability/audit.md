## Method and source guidance

[NN/G Usability 101](https://www.nngroup.com/articles/usability-101-introduction-to-usability/) supplies five separate quality components. This audit treats first use, learned performance, return after absence, error handling and experienced ease as different questions. [The heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) are diagnostic prompts for individual issues, not a weighted score. [NN/G severity guidance](https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/) supplies the 0–4 convention and frequency, impact and persistence considerations.

Severity here is expert judgement: 0 not a problem, 1 cosmetic, 2 minor, 3 major, 4 catastrophic. No live losses or observed human error rates are asserted. Conditional network/race findings are rated against their consequence and persistence, with frequency explicitly unknown. **Delivery priority is a separate Valo Pay judgement**: contain financial/privacy risks and shared defects first, then repeated work and accessibility, then secondary polish. Ordinal ratings are not multiplied into a precision score.

[NN/G usability testing](https://www.nngroup.com/articles/usability-testing-101/) informs representative tasks and participants. [NN/G questionnaire guidance](https://www.nngroup.com/articles/measuring-perceived-usability/) informs task-level SEQ and session-level SUS. Browser scripts are engineering evidence; human learnability, memorability and satisfaction remain pending. [WCAG 2.2](https://www.w3.org/TR/WCAG22/) is the accessibility target. Automated rule results, keyboard inspection and viewport emulation have narrower scope than full conformance.

Implementation references checked include [React refs](https://react.dev/reference/react/useRef), [controlled inputs](https://react.dev/reference/react-dom/components/input), [TanStack mutation behaviour](https://tanstack.com/query/latest/docs/framework/react/guides/mutations), [Radix dialogs](https://www.radix-ui.com/primitives/docs/components/dialog) and [focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html). The resulting designs and priorities are Valo Pay-specific recommendations.

Final regression and independent code review added four bounded corrections:

- **UX-R05 — malformed confirmation (errors, learnability, satisfaction; H1/H5/H9; severity 3, network frequency unknown):** a valid HTTP success with an empty or malformed body previously cleared the shared retry key. Validate existing generated response contracts before clearing it, including record/lender identity and export readiness. Seven mutation families now retain the original body/key on an incomplete receipt; null, empty and invalid JSON responses are covered. No new dependency or public response contract was introduced.
- **UX-R06 — small-screen queue filters (efficiency, satisfaction; H4/H8; WCAG 1.4.10; severity 2):** at 320 CSS pixels the collections owner select could extend beyond its clipping card once its font loaded. The first multi-browser CI run also exposed the exception-type select in mobile WebKit in both themes. Stack the collection owner and exception owner/type labels on phones and explicitly constrain native select widths. The browser assertion waits for fonts and checks main-column containment, plus card containment for the collection owner. This is an observed layout defect, not an inferred participant error; assertions were retained.
- **UX-R07 — automatic batch resilience (errors, efficiency; H1/H5/H9; severity 3, conditional on stale obligations):** a strong receipt reference could reach a stopped instalment, and narration/amount rules could choose an instalment whose balance had already reduced. Keep ineligible receipts unallocated for Finance and apply current-balance limits before automatic selection. Do not redirect a strongly linked stopped receipt to another obligation. Golden tests show later valid receipts still reconcile and repeated runs do not duplicate allocations or ageing exceptions. Manual confirmation guards remain.
- **UX-R08 — reduced-motion theme contrast (errors, satisfaction; H1/H4; WCAG 1.4.3; severity 2, transient and timing-dependent):** a later CI run passed after retry but its first mobile WebKit dark-mode Settings audit found black inherited text on dark surfaces. An isolated reproduction using the compiled stylesheet traced this to the universal `transition-duration: 0.01ms`, which activates the default `transition-property: all` on otherwise unanimated text. WebKit propagated the old inherited colour over successive frames: 8/8 theme switches and 8/8 initial stylesheet applications still had wrong descendant colour after two frames. Changing only transition duration to `0s` made all 16 correct immediately, consistent with [MDN's zero-duration definition](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transition-duration). Keep near-zero animation duration for animation-end lifecycle events; no application transition-end consumer was found. This fixes a transient rendered contrast problem rather than suppressing or delaying the axe assertion.
