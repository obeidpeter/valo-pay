# Security review

A review of the source as it stands, made after the accessibility and performance audits and in the same manner: read the surface, test what can be tested here, fix what is this repository's to fix, and write down what was found, what changed, what is accepted and what belongs to the host. It is a review of a synthetic observation sandbox, not a clearance for real lender data; the prerequisites for that are unchanged in `DATABASE_SECURITY.md` and `BUILD_STATUS.md`.

## Scope and method

The API's request surface (`artifacts/api-server/src`): how a request becomes a principal, how every read and write is scoped to a workspace and a lender, the cross-site rules, what is validated and where, the limits, the answer headers, what is logged, and how an export leaves the system. The console (`artifacts/valo-pay/src`): what it renders from data, where it navigates, what it stores in the browser. The dependencies (`pnpm audit`) and the continuous-integration workflow.

The method: every route read in full; the store's identity, transaction and lock code read; static scans for string-built SQL, HTML injection sinks, unsafe navigation, committed secrets and prototype-key handling; `pnpm audit --prod`, and `pnpm audit` over every package since the console's runtime packages are development dependencies; and the existing manual scripts noted (`pnpm run test:security-api` against a running sandbox host, which exercises tenant isolation, foreign identifiers, idempotency and allocation races end to end, and is not repeated here). New offline checks pin the changes (`artifacts/api-server/tests/api-security.test.ts`, run by `pnpm run test:pure`).

## What is sound

- **Identity.** A signed-in person is the digest of their Clerk user id, and Clerk accepts a session only from a configured origin; an anonymous visitor is the digest of a 32-byte random token held in an `HttpOnly`, `SameSite=Lax` cookie, which behind TLS is `__Host-valopay_sandbox` (`Secure`, `Path=/`, no `Domain`). The token itself is never stored or logged (the logger redacts cookies and authorisation headers, and logs only the method and the path). Malformed tokens are replaced, not honoured, and two different tokens are refused.
- **Tenancy.** Every query joins the lender on the workspace, and the workspace on the request's principal hash or, with staff access on, on the verified session's organisation, whose membership the same transaction loads and checks for fresh MFA; every workspace transaction takes the workspace's advisory lock (shared, or exclusive for a persona, team or invitation change) and a row lock on the lender, and a first visit also takes an advisory lock on the principal while its workspace is created; an export's storage location is read inside that transaction and stripped from list answers. Read-only and role rules are applied in the domain, and the API cannot reach production: the generic provider webhook address always refuses, the Paystack test ingress answers 503 until an operator configures it and checks each delivery's signature on its raw bytes before it touches a lender, and live instructions are refused.
- **Cross-site requests.** A request whose `Origin` differs from the host is refused before any route runs; a browser cannot forge the forwarded-host header a cross-site page would need, since that header forces a preflight the API does not answer; and the `SameSite=Lax` cookie is not sent on cross-site posts in any case.
- **Input.** Every body, query and path parameter goes through the shared zod contract before a route reads it; record kinds are checked against the schema's list; per-kind data schemas coerce and write back what they validated; SQL is parameterised throughout, with no string building; bodies are capped at 2 MB; idempotency keys are capped at 200 characters and digested.
- **Limits.** 300 requests a minute per principal (a signed-in person, a sandbox the process has served, otherwise the client's network: an IPv4 address or an IPv6 /64) and 1,200 per network; new sandboxes limited per network, per IPv6 /48 and per process; health checks and Paystack test deliveries limited per network, and deliveries per connection too; a sweep of expired sandboxes that is opt-in and bounded. The counts are per process (see finding 13).
- **Answers.** `Cache-Control: private, no-store`, `X-Content-Type-Options: nosniff` and `Referrer-Policy: no-referrer` on every API answer; validation failures name their fields; database safety constraints are a conflict; every answer is checked against its contract before it is sent, and one that does not match is a general 500 whose failing paths, never its values, are logged; the server's identity header is off.
- **Console.** React escapes what it renders; there is no HTML sink outside an unused chart primitive; downloads open server-issued same-origin addresses; the browser stores the theme choice (`valopay-theme`), the sandbox guide's progress per lender and the saved queue views (a name, a filter and a search, per viewer, lender and queue) in local storage, and the selected lender and the presentation checklist's progress in tab storage, never a record, a request body or a credential; the theme script in the page shell reads nothing but the theme choice.
- **Repository.** No secret is tracked and `.env` files are ignored; the workflow has read-only contents permission and does not persist the checkout credential.

## Findings, and what changed

| # | Finding | Severity | Status |
| --- | --- | --- | --- |
| 1 | A programming error (a `TypeError`, a `ReferenceError`) thrown inside a route was answered as a 400 in its own words, so a bug could describe the code to a client. | Low | **Fixed.** The error handler (`lib/error-handler.ts`) answers such errors, and anything thrown that is not an `Error`, as a 500 in general words and logs the detail. Domain rules and errors raised with a status keep their own words. |
| 2 | API answers could be framed and, where a browser applies no CORS rule, read cross-origin. | Low | **Fixed.** `X-Frame-Options: DENY` and `Cross-Origin-Resource-Policy: same-origin` on every `/api/v1` answer. |
| 3 | A record's `data` accepted any key name, so JSON could carry `__proto__`, `constructor` or `prototype` into a stored object; code that copies fields from such an object would inherit from it. The impact was confined to the sender's own workspace. | Low | **Fixed.** `validateRecord` refuses those keys before anything else looks at the data, on create, update and import. |
| 4 | Continuous integration did not audit dependencies, so a newly published advisory would go unnoticed until someone ran the audit by hand. The first fix audited production dependencies only, and the console declares its runtime packages (React, Clerk, Vite and the rest) as development dependencies, so nothing shipped to browsers, and not the Vite development server, was audited (September 2026 audit, item 23). | Low | **Fixed.** After installing, the source-checks job runs `pnpm audit --prod --audit-level=high` for the API's production packages and `pnpm audit --audit-level=high` for every package, the console's and the build tools' included. |
| 5 | `uuid` 9.0.1 (GHSA-w5hq-g745-h8pq, moderate: a missing bounds check in `v3`, `v5` and `v6` when a buffer is supplied; fixed in 11.1.1), reached only through `gaxios` 6.7.1, which `@google-cloud/storage` 8.1.0 requires directly and through `google-auth-library` 9.15.1, `gcp-metadata` 6.1.1 and `gtoken` 7.1.0. In the installed code `@google-cloud/storage` imports nothing from `uuid` (it calls Node's `crypto.randomUUID`), and `gaxios` imports only `v4`, to name a multipart boundary, so no affected function is called. | Moderate advisory, not reachable | **Accepted**, with no override: forcing `uuid` 11 beneath `gaxios` 6 would change a major version under a library that has not asked for it. Both CI audits gate at high, so they list this advisory and pass; it goes when the storage client and all three of those take a `gaxios` without `uuid` (`gaxios` 7 has none). |
| 6 | The client address for the limits comes from the forwarded-for header with one trusted proxy hop, and the origin rule compares against the forwarded host. Both are right behind the host's single proxy; exposed directly, a client could name its own address and evade the limits. | Deployment assumption | **Accepted and documented.** The API is served behind the host's proxy; this must stay true. |
| 7 | The console's HTML has no content security policy or frame-ancestors rule; those headers belong to the host that serves the built files. | Host | **Recommended to the host:** `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; font-src 'self' data:; img-src 'self' data:; connect-src 'self' <the Clerk frontend API>; frame-ancestors 'self'`, plus `Strict-Transport-Security`. Same-origin framing permits the landing page's interactive console preview; other origins remain blocked. Any HTML `X-Frame-Options` header should likewise be `SAMEORIGIN`. API answers retain `DENY`. The inline theme script is the only inline script and could be given a hash. |
| 8 | The workflow's actions were pinned to major tags, not commit hashes, and ran on the deprecated Node 20 action runtime (September 2026 audit, item 29). | Supply chain | **Fixed.** Each action is pinned to the full commit of a Node 24 release, with the version in a comment: `actions/checkout` v7.0.1, `actions/setup-node` v7.0.0, `actions/upload-artifact` v7.0.1 and `pnpm/action-setup` v6.1.0, the commits read from each repository's tags. The pnpm version comes from `packageManager` in `package.json`, so a local install and CI run the same pnpm. |
| 9 | Downloads open with `window.open(url, '_blank')` without `noopener`. The address is server-issued and same-origin, so the opened page is the console's own. | Informational | **Accepted.** `noopener` would make the "tab kept closed" detection impossible, and the target is never a third party. |
| 10 | Errors got the wrong status (September 2026 audit, item 10): malformed JSON and a NUL character answered as a general 500; the application's own 503s (export storage not configured, the key service unreachable) were flattened to the same 500, leaving the journal entry pending and the console's controls locked; a refusal without a status became 403 or 400 by matching words in its message, including words from the request; storage outages and checksum mismatches on downloads answered 400 at info level; and the body was parsed before the security headers, origin rule and request limit. | Low | **Fixed.** Body-parser errors are 400, 413 or 415 in plain words; a NUL character is refused at the edge naming the field, and PostgreSQL's character errors are 400; the application's 502, 503 and 504 keep their status and words; a refusal without a status is always a 400, and role refusals carry 403 explicitly; storage failures are 502 or 503 and an evidence checksum mismatch is a 500 that explains itself, all at error level. When the workspace transaction was rolled back before its COMMIT, a 5xx says `committed: false`, the journal entry closes and the console treats the request as finished. The headers, origin rule and request limit now run before the body is read. |
| 11 | A forged Paystack test delivery to a mapped connection locked the lender, loaded it and opened its protected payloads before the signature was checked (two key-service calls per protected import batch), told the caller whether the lender was busy or eligible, and answered 500 during a database outage (September 2026 audit, item 18). | Medium | **Fixed.** The route checks the signature on the raw bytes first, with the key read from the environment alone; only a verified event reaches the connection lookup and the lender, so a forged delivery costs one hash and gets 401 whichever connection it names. `tests/api-security.test.ts` pins it with no database, and `tests/operations-controls.integration.test.ts` shows that a forged delivery takes no database connection and gets 401, not "busy", while the lender is locked. |
| 12 | The restricted-database self-check compared only policy and helper names (September 2026 audit, item 19): a policy loosened to `USING (true)` or `WITH CHECK (true)`, widened to every role or made restrictive, a scope helper whose body was replaced and a disabled workspace guard all passed, and the readiness page reported the database as verified while the database itself no longer kept one workspace's lenders from another. The repository's own workspace and grant conditions still held, so ordinary pages did not leak; the lost layer was the defence in depth. | Medium | **Fixed.** Every isolated transaction reads the catalogue in one round trip, with `pg_catalog` first on the search path, and compares each policy's command, roles, permissive mode and expressions, each helper's owner, fixed search path, signature and body, and the guard trigger's definition and enabled state with the reviewed set in `lib/runtime-isolation-policy.ts`. Any difference is a 503 whose log names what differs; readiness reports the check this request passed, not the configuration. The guard's runtime login is written into the reviewed text before the comparison, never replaced in the live text, so a guard rewritten to compare the session with the placeholder `'{role}'`, which never fires, is refused as well. The integration suite pins the reviewed set against freshly commissioned migrations and refuses nine weakenings. |
| 13 | Anyone on IPv6 could start unlimited anonymous sandboxes (23 September 2026 audit, security item 1). The request limit (300 a minute) and the new-sandbox limit (20 an hour) counted each exact address, and a subscriber holds a whole /64, so every request could carry a fresh quota. A signed-in person shared the quota of everyone behind their office or carrier address, and past 10,000 addresses every request scanned the limiter's whole map. | Medium | **Fixed.** The limits count networks: an IPv4 address, or an IPv6 /64. A principal has its own 300 requests a minute: a signed-in person, or an anonymous sandbox the process has served, since a cookie the process has not seen is only a claim and counts as its network. A network has 1,200 a minute whoever sends them, so rotating cookies or accounts cannot escape it. New sandboxes are limited to 20 an hour per network, 60 per IPv6 /48 and 300 per process. The counts stay in each process, since a shared store would cost a database write per request, so a host running several instances multiplies them and a restart starts them afresh (the README, Operating). Every map is bounded in size and swept on a timer, never on a request. The reviewer's 30 first visits from one /64 now start 20 sandboxes, not 30. |
| 14 | The production Clerk proxy sent Clerk, with the secret key, the leftmost `X-Forwarded-For` entry, which the client writes, as the client address, and built `Clerk-Proxy-Url` from the client's `X-Forwarded-Host` and `X-Forwarded-Proto` (security item 2). Rotating the header evaded Clerk's address-based throttling and falsified the addresses Clerk records for staff sessions; the same host chose the publishable key the API derived. | Medium | **Fixed.** The proxy forwards the address the host's edge saw (`req.ip`, one trusted hop) and drops `Forwarded`, `X-Real-IP` and `CF-Connecting-IP`. `Clerk-Proxy-Url`, `X-Forwarded-Host` and `X-Forwarded-Proto` come from a configured origin (`VALOPAY_STAFF_ORIGINS` in staff mode, otherwise `VALOPAY_APP_ORIGINS`, or Replit's `REPLIT_DOMAINS`): the one the request's host names, or the first. With none configured the proxy answers 503. A production publishable key is derived only for a configured host. |
| 15 | Clerk's `authorizedParties` was set only in staff mode, so elsewhere a session minted for another origin of the same Clerk instance was accepted. Every answer, health included, also failed without `CLERK_SECRET_KEY`. | Low | **Fixed.** Wherever Clerk checks sessions it accepts them only from the configured origins. With Clerk's keys but no origin, sign-in is off and every request is an anonymous sandbox, and the start-up line `sign_in.off` says so. Without Clerk, outside staff mode, the API serves the sandbox anonymously, health and readiness included; a staff host without `CLERK_SECRET_KEY` does not start (`config.invalid`). |
| 16 | `/api/readyz` sat outside every limit, and a burst from one address queued on the check's single connection until probes timed out and answered 503 (security item 6). | Low | **Fixed.** Probes share one check while it runs, and its answer is reused for a second after it finishes, so a burst makes one database round trip; each network may make 120 health checks a minute. A burst of 1,500 probes from one address now gets 120 answers of the shared check and 1,380 refusals, and no 503. |
| 17 | `X-Request-Id` was taken from any client, so a client could reuse a reference someone had quoted to support and have its own lines found with theirs (security item 8). | Low | **Fixed.** Every request gets a fresh id, unless the deployment says its edge sets the header on every request (`VALOPAY_EDGE_REQUEST_ID=on`). |
| 18 | The sandbox cookie had no `__Host-` prefix and the first of two values under its name won, so a cookie planted for a parent domain with a longer path, from a sibling subdomain of a custom domain, could fix a visitor into a sandbox someone else can read; the legacy name was read for ever (security item 9). | Low | **Fixed.** Behind TLS the cookie is `__Host-valopay_sandbox`, which only this host can set, and it wins over a plain one beside it. Two different tokens under the name that decides are refused with a 400 that says how to recover, rather than guessed between or replaced by a fresh sandbox: the planted cookie is sent with every request and a server cannot clear a cookie set for another domain or path, so a fresh sandbox would be created, and lost, again and again, while the refusal writes nothing. An older name (`valopay_sandbox` behind TLS, or `valo_sandbox`) is read once to move a browser's sandbox, then cleared, until the end of 2026; until then a cookie planted under an old name can still fix a visitor who has no `__Host-` cookie yet. The token is not rotated. |
| 19 | One captured signed Paystack test delivery could be replayed for ever, and every replay appended an audit entry and saved the lender (security item 5); the per-address limit was evaded as in finding 13. | Low | **Fixed.** A repeat of a saved event is acknowledged without an audit entry, and its delivery count is written at most once a minute per receipt; the repeats in between are tallied by the process and added at the next write, so a tally not yet written when the process stops is lost and the count is a floor. Signed deliveries are also limited to 60 a minute per connection, whichever addresses they come from. The reviewer's 100 replays of one delivery now leave one audit entry and one receipt written once. |

## What was not reviewed

The Clerk sign-in flow itself (a hosted service, configured outside this repository); the host's TLS, proxy and static-file headers; App Storage credentials and bucket policies for exports; and the database role model, which `DATABASE_SECURITY.md` covers. Real data remains blocked pending the independent assessment and the prerequisites listed there.

## How to re-run

- `pnpm test` runs the offline security checks with everything else: error answers and their statuses, body-parser and NUL refusals, unavailable services and storage failures, prototype keys, response headers, the origin rule before the body, the body limit, the webhook ingress and the Paystack signature check before any lender work (`tests/api-security.test.ts`); the limits by principal and network, the bounded maps, health without Clerk, coalesced readiness, request ids, Clerk's accepted origins, the Clerk proxy's forwarded headers, the staff start-up check and the sandbox cookie (`tests/edge-security.test.ts`); and the Paystack delivery limit per connection and repeats without audit entries (`tests/source-ingress.test.ts`, with the database in `tests/operations-controls.integration.test.ts`).
- `pnpm audit` lists advisories for every package and `pnpm audit --prod` for the API's production packages alone; the workflow runs both and fails on high or critical ones. On 23 September 2026 each listed one advisory, finding 5, and nothing high or critical.
- `pnpm run test:security-api` against a running `*.replit.dev` sandbox host exercises tenant isolation, foreign identifiers, idempotency and allocation races end to end.
- Before a change to the request surface: read this document's table, keep every route behind the shared contract, keep every query joined on the principal, and add a check here for what the change makes possible.
