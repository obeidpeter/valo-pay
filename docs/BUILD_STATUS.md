# Valo Pay — build status

## Audit fixes, 23 September audit · September 2026

The findings of the 23 September 2026 audit are fixed and covered by tests:

- **Hosting and scheduled closes.** The deployment stays on Replit Autoscale, and the documents now say plainly what that means: the scheduled close and the export worker run inside the API process, so while the deployment has scaled to zero closes run late and exports wait, and the per-address limits count per instance. Closes run on time on a Reserved VM, or on Autoscale with `VALOPAY_CLOSE_SCHEDULER=external` and a Replit Scheduled Deployment that runs the new one-shot close pass (`artifacts/api-server/src/close-pass.ts`, built beside the server): the scheduler's own pass run once, with a ten-minute budget, ending with a `close.one_shot` line and exit status 0 (it took up every lender that was due and no close failed), 2 (a close failed and waits for its retry, or the ten-minute budget ran out with lenders still due) or 1 (it could not run or was stopped). `docs/deployment.md` sets out both ways; the choice is the owner's.
- **Review fix: closes run from a scheduled job, and a missed one still shows.** Option 2 of `docs/deployment.md`, Autoscale with a Scheduled Deployment running the one-shot close pass, set `VALOPAY_CLOSE_SCHEDULER=off` on the web instances, which means nobody runs automatic closes: the overview never raised `close_missed` or named the dates owed, every console said to run closes manually, and the monitor was told not to check, so a Scheduled Deployment that stopped, or failed at every run, went unnoticed. A third value, `external`, runs no scheduled close in the process, as `off` does, and `/api/healthz` reports the scheduler as `external`. A close the job has not run 30 minutes after its time is missed as with a running service, so `close_missed` is raised with the dates owed, and the console says "Daily closes run from a scheduled job." and, once one is missed, asks for a daily close and a check of the job. Option 2 sets it, the start-up check and the close pass accept it in any case, and `VALOPAY_MONITOR_EXPECT_SCHEDULER=external` makes the monitor check it; an expectation the monitor does not know now stops it instead of checking nothing. A host already set up with `off` should change it to `external`.
- **Review fix: a guard query to run before publishing.** The build serving now checks only tables, columns and read indexes, so its readiness cannot show a unique index or check constraint that this build requires and the database lacks, such as one an interrupted push left missing, and the new build would then fail its start-up health check. `docs/database-migrations.md` now gives the owner a read-only query, built from the catalogue readiness checks, that lists each such guard, says what to do if it lists anything, and runs it in the procedure before publishing. An offline test checks that the query lists exactly the catalogue's 24 guards, and a new database suite, `integrity-guards`, that it names what readiness names, on a pushed database and on a copy with guards dropped, rebuilt without their condition or added back without validation.
- **Review fix: the database suites run to the end in CI.** The PostgreSQL job failed on every run. The export jobs suite expected only the worker's two audit entries for a queued export, but the request's own `post.exports` entry now names the export too, so the suite stopped there and its later checks never ran; it now expects all three. The background worker suite probed `/api/healthz` every 20 ms, so a close longer than about 2.5 s met the health limit of 120 checks a minute and the probe crashed on its 429. It now probes at most every 100 ms and skips an answer other than 200, its lender has about 40,000 records instead of 20,000, so that the close, which the lender history fixes made quicker, still spans a dozen probes, and it still fails when the close runs on the main thread.
- **Review fix: the pool size is read alike at start-up.** The start-up check took up to six digits for `VALOPAY_DATABASE_POOL_SIZE` where the database module takes three, so `0010` passed the check and then ended the process with a bare stack instead of the `config.invalid` line. The check now applies the database module's own rule, at most three digits from 2 to 100, and a test loads the database module with each of 18 values to show the two agree.
- **Review fix: the isolation self-check works behind a transaction pooler.** The restricted-database check prepared its two catalogue reads as named statements, which a connection keeps between transactions. Behind a transaction-mode pooler without prepared-statement support, the next transaction can run on another server connection, where they do not exist, so every isolated request and background transaction would have failed with "prepared statement does not exist". The reads are now planned in each transaction: the check costs about 6 ms, about 2.5 ms more than before, and the integration suite runs it across three transactions that each lose the connection's prepared statements.
- **Review fix: a one-shot pass that runs out of time says so.** A one-shot close pass whose ten-minute budget ran out with lenders still due exited 0, as if every due close had run, and its `close.one_shot` line did not say lenders were left. The pass now records when its budget ended it (`budgetSpent`, on the run and on the line) and exits 2, as for a failed close, so the Scheduled Deployment's run shows as failed; the lenders it did not reach are still due for the next run. `docs/deployment.md`, `docs/observability.md` and this page say exactly what 0, 1 and 2 mean, and that the pass checks `VALOPAY_CLOSE_SCHEDULER` at start-up as the server does.
- **Deploys wait for readiness.** The deployment's start-up health check is `/api/readyz` instead of `/api/healthz`, so a build whose database lacks a table or column it needs (503) does not go live; a missing index (200, `indexes_missing`) does not hold a release back.
- **Sandbox expiry on the deployed host.** The deployment sets `VALOPAY_EXPIRED_WORKSPACE_CLEANUP=on`, and the security boundary, this status and the README now say exactly what happens: an anonymous sandbox nobody has changed for 30 days is deleted when a new sandbox is created, up to five each time and oldest first, leaving any sandbox a close, an export or a request holds for later, and leaving its export files in private storage; without the setting, as in development, nothing is deleted.
- **Start-up settings and the log during an outage.** The API and the close pass check their settings once, before anything reads them, and a bad value is one fatal `config.invalid` line naming each setting (never its value) and exit status 1, instead of a bare stack or a process that starts and fails every request. `VALOPAY_CLOSE_SCHEDULER` takes `on`, `off` or `external` in any case and refuses anything else instead of scheduling closes. The export worker logs `export.queue_error` once when its queue stops answering and `export.queue_recovered` when it answers again, looking less often meanwhile (3 s doubling to a minute), where it used to log an error every 1.5 s.
- **Clerk telemetry.** The deployment sets `CLERK_TELEMETRY_DISABLED=1`, the README and `docs/deployment.md` ask for it on every pilot host, and `docs/observability.md` now names the plain-text notice the Clerk SDK otherwise prints among the log lines.
- **Pilot administrators.** `provision-pilot` can be run again without failing on a duplicate row, and has two more modes: `--add-administrator` adds another administrator and `--renew` extends an administrator's access, active or ended, to 90 days from now; each writes a staff event, and suspended or revoked memberships are never restored this way. The console warns an administrator, above every page, when their own access or the last administrator's ends within 14 days. `docs/pilot-workflow-release.md` has the renewal routine.
- **One migrations procedure.** `docs/database-migrations.md` lists migrations 001 to 007 in order (superseded, required or optional commissioning), who applies each, the command, how to verify it and how to roll back, and how the Publish flow fits; `docs/DATABASE_SECURITY.md` now says the same. The index document's runtime-schema example uses the schema the host names, which the application accepts.
- **Integration runner.** `pnpm run test:integration` runs every suite and names the failures at the end instead of stopping at the first. The two migration rehearsals run on any loopback database whose login can create databases, naming their throwaway databases after it, and elsewhere skip, saying why (a failure under CI).
- **CI.** The four browser projects run as their own jobs with cached browsers, so the source job no longer carries the ten minutes the browser step took on the last measured run; a Node 22 job runs the typecheck and every offline suite; the whole workspace, the mockup sandbox included, is built; a weekly run repeats every check, both dependency audits included; the PostgreSQL image is pinned by digest; the recovery rehearsal runs even after a failed suite, reports a failure too, fails under CI without its opt-ins, and its missing report fails the job; the real-API browser suite honours `PLAYWRIGHT_CHROMIUM_EXECUTABLE`. The README lists the checks a branch rule should require.
- **README and local runs.** The README says what `pnpm test` and CI run; outside Replit the console's development server passes `/api` to the API process, so the two documented commands run the sandbox locally; `pnpm run check:operations` names a missing `VALOPAY_MONITOR_ORIGIN`; and the build stamp marks a checkout with uncommitted changes `-dirty`.
- **Dependencies.** Unused packages are removed (the API's `cookie-parser` and `cors`; the console's and the mockup sandbox's `@hookform/resolvers`, `framer-motion` and `date-fns` 3, which leaves one `date-fns`; the console's `react-icons`; the mockup sandbox's `tailwindcss-animate` and `zod`), `@replit/connectors-sdk` moves from the application's dependencies to the scripts package's development dependencies, `@types/node` follows the oldest supported Node (22), and the stale `stripe-replit-sync` release-age exclusion is gone. `@clerk/shared` and `google-auth-library` still come in two majors, because the latest `@clerk/themes` and `@google-cloud/storage` still require the older ones.
- **Hand-back ends the cutover contract.** After a hand-back the old contract stayed ready, so Operations could set an instalment's owner to Valo Pay again and, once the emergency stop was lifted, the engine would have planned collections. A hand-back now ends every cutover contract recorded before it: owner Valo Pay needs a new contract recorded and made ready after the last hand-back, and a contract drafted before it cannot be made ready afterwards (400). Lenders that handed back earlier are covered by the same rule without a data change.
- **Consented mandate limits.** A plain edit could raise a mandate's limit (₦50,000 to ₦10,000,000) under the same consent. The limit is part of the customer's consent: an edit that changes it is refused (400), and `mandate_reissue` takes an optional `data.amountKobo`, the limit the new consent covers, which the console's Reissue dialog asks for, starting from the current limit.
- **Retry notices follow the failure.** The engine took a pre-debit notice accepted before a failure as the notice for its retry. A notice linked to the failed attempt now counts only when the provider accepted it after that failure; otherwise the plan waits for new evidence by its deadline, or is deferred once that passes (notice_not_evidenced). The retry still waits the full notice period after acceptance.
- **Backtests of new policy versions.** Backtesting a draft returned no decisions, and an instalment pointed at it only `unapproved_policy`. A backtest now tries any version, draft or submitted, on the instalments governed by any version of its policy, as if it were approved and applied: the approval and consented-version rows are left out, nothing is recorded, and the message says when the version is not approved. The Policies page offers Test this version on every version, so a reviewer can see what a submitted version would do before approving it.
- **Each experiment group meets its own minimum.** The pass rule held the retry group to the comparison group's minimum (293 where it needs 1,172 with a 20% comparison group). The uplift report now checks each group against its own minimum, the larger of `minPerArm` and its computed one, gives them as `minimumByArm`, and the evidence view shows both.
- **Submitted policies are frozen.** An author could change a submitted policy's rules (3 attempts 48 hours apart to 4 attempts 24 hours apart) before the reviewer approved it. A submitted policy now refuses every edit (400) until a reviewer rejects it, as submitted templates already did.
- **Import corrections keep the proposer's authority.** A correction validated the amended instalment as an Admin, so Operations could lower an instalment below the lender minimum, which is refused when they edit it directly (MAN-07). The amended record is now checked with the proposer's own role, recorded on the proposal, whoever views or decides it; a proposal recorded before the role was kept is checked as a writer who is not an Admin.
- **West Africa Time boundaries.** Experiment enrolment closed at midnight UTC, an hour into the next WAT day, and the uplift report's analysis date and the daily close's name used the UTC date. All three use the WAT date now: enrolment takes a first failure up to the end of the enrolment date in WAT, the analysis date is reached at midnight WAT, and a close run at 00:30 WAT on 1 July is named for 1 July.
- **Scheduled closes check the day they close.** A 07:00 close checked the source files of the day it ran, before that day's files could arrive. A scheduled close now checks the business date it closes, the WAT day before its scheduled time (decision 1), records it as the close's `sourceBusinessDate`, and its name gives that date when it differs from the run date ("Daily close 2027-06-29 · scheduled · business date 2027-06-28").
- **One catch-up close per missed business date.** Several missed days collapsed into one late close, so the missed dates never got their own source evidence or review. The close cursor now moves one business date at a time: after an outage each missed date gets its own catch-up close, oldest first, with its own source check and Finance review, and a later date's close no longer makes an earlier date's review historical while its records are unchanged (decision 2). The scheduler runs at most one close per lender per pass, so a backlog continues on the next pass instead of running back to back, and the missed-close alert names the dates still owed. A manual close run while a scheduled close is missed takes the place of the oldest owed date unless it names another date; while the automatic close is off nothing is owed.
- **Request limits by network and principal.** The request and new-sandbox limits no longer count each exact address, which let an IPv6 client pick a fresh address in its /64 for every request: an IPv6 client is counted by its /64. A signed-in person and an anonymous sandbox the process has already served each have their own 300 requests a minute, so colleagues behind one office or carrier address no longer share one quota, and a network has 1,200 a minute whoever sends them, so rotating cookies or accounts cannot escape it. New sandboxes are limited to 20 an hour per network, 60 per IPv6 /48 and 300 per process. The counts stay in each process, and the README says what that means for a host running several instances; every limiter's map is bounded in size and swept on a timer instead of being scanned by requests.
- **Clerk proxy and accepted origins.** The production Clerk proxy tells Clerk the client address the host's edge saw, not the one the client wrote, and names its own address from a configured origin, not from the request's forwarded host; a production publishable key is derived only for a configured host. Clerk accepts sessions only from the configured origins in every mode, not only for staff: `VALOPAY_STAFF_ORIGINS` in staff mode, otherwise the new `VALOPAY_APP_ORIGINS` or, on Replit, `REPLIT_DOMAINS`. With Clerk's keys but no origin, sign-in is off and every request is an anonymous sandbox, and a warning at start-up says so.
- **Health without Clerk, and readiness bursts.** `/api/healthz` and `/api/readyz` answer before sign-in, so they work without `CLERK_SECRET_KEY`; without Clerk and outside staff mode the API serves the sandbox anonymously, which also lets it run on a local host, and a staff host without `CLERK_SECRET_KEY` does not start, with one fatal line. Readiness probes share one database check, reused for a second after it finishes, and each client network may make 120 health checks a minute, so a burst from one address no longer makes readiness answer 503.
- **Request ids.** An `X-Request-Id` sent with a request is kept only where the deployment says its edge sets the header (`VALOPAY_EDGE_REQUEST_ID=on`); otherwise every request gets a fresh id, so a client cannot reuse a reference someone else quoted.
- **Sandbox cookie.** Behind TLS the sandbox cookie is `__Host-valopay_sandbox`, which no other host can set or shadow. A request carrying two different sandbox tokens is refused with a way to recover instead of taking the first, and the older cookie names are read once to move a browser's sandbox, then cleared, and are not read after 2026.
- **Paystack replays.** A repeat of a saved Paystack test event is acknowledged without an audit entry, and its delivery count is written at most once a minute, the repeats in between tallied by the process; signed deliveries are limited to 60 a minute per connection as well as 120 per client network. One hundred replays of a captured delivery now leave one audit entry instead of 101.
- **Payments with no payer.** A payment whose evidence names no customer, such as a provider settlement line or the seeded SBX-UNIDENTIFIED-001, is applied only when Finance identifies the payer, in the same action: `manual_allocate`, or confirming the payment's proposal, records the instalment's customer on the payment with who identified it, when and why (`payerIdentification`), withdraws any proposal of it for another customer, and the audit entry adds "Payer identified as customer DEMO-C1005 for payment SBX-UNIDENTIFIED-001." to Finance's reason. Rule R1 proposes such a payment instead of applying it, so a settlement file without a customer column no longer makes every daily close, reconciliation and scheduled close fail with 409 "Allocation customer must match its parents". The console says what choosing an instalment does to the payer, offers only a known payer's instalments, marks such proposals "Payer to confirm" and announces the payer it recorded. The repository refuses an applied allocation whose payment has no payer, and any change of a recorded payer. A payment the rule ladder cannot apply is held with the reason and an unallocated_payment exception, so one record never stops a close.
- **Evidence that shares a reference.** Evidence resolves to a payment by its provider connection and reference, so the same reference through another connection is another payment. Evidence under a payment's key that names another payer, is in another currency or states another gross amount is no longer merged into that payment, which used to make every close fail with 409 "Payment due item must belong to its customer" or drop the second payer's money: it stays unresolved with a suspected_duplicate exception for Finance, and once Finance resolves that it becomes a payment of its own, held for its refund when Finance confirmed it a duplicate. A settlement line that states only its net amount still joins its payment, and the debit's gross completes it. The CSV import skips payment evidence only when the same source event, or the same evidence in every money detail, is already saved, and refuses the same event with different details, instead of skipping any row that shared a reference.
- **Rule R1's currency and connection.** Payments carry the currency and provider connection of their evidence instead of a fixed NGN and a connection check that always passed. R1 applies a match only through the lender's own connection and in naira: money in another currency is never matched or applied, by hand either (409), and a strong reference seen through another connection stays unallocated, each with an unallocated_payment exception that names the currency or connection. Connection names are compared without case.
- **Rule R4's narration references.** R4 reads instalment references on word boundaries across the whole lender and prefers the longest where references overlap, so "Loan LN0042-10 October instalment" no longer pays LN0042-1. It applies a match only when the narration names exactly one instalment, which is the payer's, open and owed the amount; a narration naming several instalments, or a reference two instalments share once case and punctuation are set aside, is never matched automatically.
- **Settlement batch credits and lines.** Every statement credit that names a batch now counts: the batch's statement total is their sum, so a second credit shows as a variance with an exception instead of replacing the first, and the same bank line delivered twice adds nothing. A settlement line for a collection another batch already counts is not counted again: it is marked with the batch that counts it and raises a settlement_variance exception that names both batches. Batches linked under the old rule are brought to the sum at the next reconciliation.
- **The rest of a partly allocated payment.** The unapplied rest of a partial or overpaid payment (`paymentAwaitsAllocation`) is now in Finance's payments queue, in SQL and in the console's read model, which shows what it has left to allocate, and in the close's opening and closing unallocated totals and their age count. The rest of a partial payment ages into an unallocated_payment exception after 24 hours; an overpayment keeps its overpayment exception.
- **Distinct payments.** Resolving a suspected duplicate as distinct_payments releases its payment at once and records Finance's decision on it (`duplicateReview`), so the next close matches it instead of holding it again or reporting it as a possible duplicate; a confirmed duplicate stays held until its refund is recorded. `artifacts/api-server/tests/payment-evidence-golden.test.ts` covers these seven findings, with a property run of random evidence, allocations, refunds, reversals, closes and resolutions that checks money is conserved and never merged into another payer's payment.
- **Every invoice month, in order.** Invoices now cover every month in order: issuing a month after the next one due is refused, naming the month to issue first, so a month can no longer be passed over and its licence lost (issuing March after January used to leave February impossible to invoice). Before the first invoice, the month due is the one the earliest signed terms took effect. A month with nothing to bill gets an explicit zero invoice, and the statement's next invoice month and the Issue invoice dialog say which month comes next.
- **Licence terms.** Any signed terms now bill the licence, not only a design partner's: the latest signed terms in effect by the end of a month bill that whole month, with no proration, so a renewal takes effect from its month instead of being ignored in favour of the first terms found. Terms belong to the lender by its id rather than by matching its name, so renaming the lender no longer stops its licence, and the Evidence page's terms dialog records the date terms take effect.
- **Reversal window from settlement.** A collection becomes billable once the provider's reversal window has passed since it settled, as the money rules document, rather than since it was collected; a payment settled before its settlement time was kept counts from when it was observed.
- **Credit Desk repayment schedule.** Explicit terms and the sample schedule fall due once a calendar month, on the assessment's day in West Africa Time or the month's last day when it is shorter, instead of every 30 days, which put two repayments in some months and doubled that month's peak. A 24-month schedule that spans 29 February still fits the two-year horizon.
- **Cash Desk tax period and overdue outflows.** The sample VAT period is the West Africa Time month, so a sample set up at 00:30 WAT on the 1st no longer lands in the month before. A forecast keeps an approved outflow past its due date as due now, with a warning, instead of dropping it; a receipt past its due date is still left out.
- **Exact money in messages.** `nairaText`, which writes money in the API's messages and invoice explanations, now splits kobo into naira and kobo with integer arithmetic, so an amount above about NGN 10 trillion no longer loses a kobo.
- **Repeats answered for their key.** A repeat of a saved request (the same Idempotency-Key, or Check original request) turned away by a busy lender, or whose stored answer the key service could not open, was answered "Nothing was saved" with `committed: false`, inviting a second submission. An answer is now decided for the key: `committed: false` only when nothing sent with the key was or can be saved (its journal entry is cancelled, or nothing was saved under the key before the request failed), and otherwise the answer names the key's journal entry (`operation` `completed`, `running` or `pending`) and says in its words that the request was saved, is still running or is not confirmed. A repeat now finds its entry without waiting for the lender, so it is answered for its key even while the lender is busy. The console keeps a key whose answer names such a state.
- **Duplicates of a running request.** A duplicate that timed out waiting for the lender cancelled the entry its original was still running, and the original was then refused and saved nothing. The attempt running a journaled request now holds its entry for its whole transaction: a duplicate sent meanwhile is answered at once with a 503, `Retry-After: 2` and `operation: "running"`, and leaves the entry alone. Only a definitive refusal, or a failure of the attempt that created the entry while no other attempt runs it, closes an entry.
- **Malformed input is a refusal, not a failure.** A path whose percent-encoding cannot be decoded, a body that cannot be decompressed, a body nested thousands of levels deep and text with an unpaired UTF-16 surrogate were 500s logged at error level (two error lines a request, which an anonymous client could repeat), and a malformed path left a journal entry pending for ever. The error handler now keeps an error's own 4xx when a library marks it safe to expose, or the router marks an undecodable path, before anything is taken for a programming error, and logs it as a refusal at info. A body nested more than 32 levels deep or holding an unpaired surrogate is refused (400, naming the field) before anything is fingerprinted, journaled or saved, and an undecodable path before the journal. A GET's or HEAD's body is ignored, and a body that is not JSON, a form's included, is refused (415). An error a dependency raises without a status, such as a missing identity-provider key, is now a 500 at error level, not a 400 at info.
- **Validation answers capped.** A validation refusal listed every problem, so a 2 MB request could get a 12 MB answer. It now names at most 20 fields, with `detailCount` saying how many problems there were, and the console says how many more it did not name.
- **Paths and keys the journal and the router agree on.** Routing was case-insensitive and ignored a trailing slash while the journal matched exact paths, so a keyed write to another spelling of a path was saved without a journal entry. The API's routes now match a path strictly and in its case, and the journal matches a path as they do. A journaled request's answer is kept under its own journal entry, and a demo role switch's under a name of its own, so a key that a demo role switch or a colleague used no longer refuses a journaled write and leaves its entry pending for ever.
- **Upstream outages are 503s.** Private storage or the identity provider out of reach was a general 500. It is now a 503 with `Retry-After`, as the contract says.
- **Console survives a failed workspace refresh.** Only a workspace that cannot be loaded at all replaces the console with the unavailable notice. A background refresh that fails (the service unreachable for a few seconds, or one 429) keeps every page, form and dialog, with its draft and any "Outcome not confirmed" retry, and a notice above the page says the workspace could not be refreshed, why, when the workspace shown was loaded and that a save whose outcome is unknown can be checked in Operations, with Try again. After a 429 or 503 with `Retry-After`, the next automatic refresh waits that long and the notice says when. Neither notice says any more that no lender data has been changed: the unavailable notice points to Operations instead.
- **Back and Forward keep a draft.** The unsaved-changes guard is installed when the app loads, before the router subscribes to the browser's location, and its listener no longer relies on capturing: in Chromium, listeners on the window run in the order they were added, so Back used to unmount the draft before the guard was asked. A browser test checks Back and Forward with a Settings draft and a case note, and the jsdom test now fails if the order is lost.
- **An edit can clear an optional field.** The record dialog sends an optional field that an edit emptied (an exception's assigned owner or severity) as `null` instead of leaving it out, and `PATCH /v1/records/{kind}/{id}` now reads `data` as a merge patch: a field sent as `null` is removed, a field left out keeps its value. Before, the API refused a `null` and the dialog, which left the emptied field out, closed as saved while the old value stayed. The contract's update description says so.
- **Pilot pages tell a failed read from a lost change.** A read on a pilot page that gets no answer says the information could not be loaded and to try again, instead of pointing to Operations for a request the person never made. A change that gets no answer points to Operations only when Operations records it; a team, access or new lender change says to refresh the page to see whether it was saved. A correction preview's own check is shown in its words again, and the invitation and identity verification pages have wording of their own.
- **Focus, headings and the presentation guide.** A button that removes itself no longer drops focus on the page body: Edit on Settings moves it to the first field, Cancel and a save back to Edit, a Pay-by-bank step taken without a review to the message that says what it did, and End presentation to the page's content. Every loading and error state has an h1: a page that shows only its waiting line gives it as the heading, and a first load that failed (the overview and the four connected pages) keeps the page's heading, and the connected module tabs, above the problem card. At phone width the presentation guide's title keeps its line and its buttons wrap under it, so the guide takes at most half of a 390 by 664 px screen instead of about 60%.
- **Console copy.** Import batch counts go through the formatters ("1 source row", "1 row to fix"), a customer batch shows no ₦0.00 source total, saved exports are listed by what they hold and a plain state ("Dispute pack · JSON", "Completed"), a recovery notice says no answer arrived rather than the browser's "Failed to fetch", and the invitation page sets its own title. The API's own "1 source rows still need correction." and the persona naming are left to a later group.
- **Revoking a staff member asks first.** As decided, Team & access now asks for confirmation before it revokes a membership: after the reason, a dialog names the person and says what revocation removes and that only a new invitation restores access; nothing is sent until Revoke access, and Keep access returns to the form. The emergency stop stays a single step after its reason.
- **A smaller entry chunk.** Clerk's React SDK left the entry chunk: its provider loads as a chunk of its own only where sign-in is available and renders beside the pages, so its arrival never remounts one, and Clerk's forms and staff controls render into the page through a slot under it; a local host without a key never fetches Clerk. The first page that writes no longer loads the whole generated contract (132 kB) to check eight answers: the console reads them with shared schemas in `lib/valopay-schema/src/receipts.ts`, which the contract generator checks field for field against the components it describes. The presenter brief moved to the Presentation page. The entry went from 537.87 kB (163.67 kB compressed) to 440.23 kB (138.33 kB), and the write receipts from 141.15 kB to 5.55 kB; `docs/design/console.md` has every figure.
- **Typefaces served with the console.** As decided, the console no longer asks Google Fonts for its typefaces: the same files (Plus Jakarta Sans and Spline Sans Mono, variable, every subset Google served) come from the registry's `@fontsource-variable` packages with their SIL Open Font Licence, declared in `src/fonts.css` with the same families, weights and `font-display: swap`, and bundled with the console. The recommended content security policy no longer needs a Google origin.
- **Repeatable schema push and readiness guards.** Every `drizzle-kit push` planned the same ten statements, so each push or publish diff dropped and rebuilt the in-flight and provider-event uniqueness guards, one statement at a time outside a transaction, and dropped and added three foreign keys; a push stopped part way left the guards missing. drizzle-kit reads every column of an index that has an expression back as an expression, so the lender column of those two indexes is now declared as one (PostgreSQL builds the same index), and the three foreign keys, whose generated names ran past PostgreSQL's 63 characters and were cut, are now named within them. A second push plans nothing, on a fresh database and on one built from the migrations, which the new `schema-push` rehearsal checks. Migration `008_export_queue_index_and_foreign_key_names.sql` renames, in place, the cut names that earlier copies of 003 and 004 left, and 003 and 004 now use the new names. `/api/readyz` also checks every unique index and check constraint the schema declares and answers 503 (`incomplete`) while one is missing, naming it in the log; `docs/database-migrations.md` says how to restore one.
- **Migration lock limits.** 003 and 004 now wait at most 5 s for a lock and run each statement for at most 60 s, as 007 does: an open write on a lender used to hold 003 back until it committed, with every later write on a lender queued behind it, and now 003 stops with nothing changed and can be run again. Both stay repeatable.
- **Export queue index.** Migration 008 also adds `valopay_records_export_queue`, a partial index of queued and running exports in the order the export worker takes them, so its look-up every few seconds reads a few index entries instead of every record (0.1 ms instead of 130 ms at 400,000 records in a local measurement); readiness reports it as `indexes_missing` until it is applied. The suggested index on `valopay_records(merchant_id, created_at, id)` for the full-state load's sort was not added: with PostgreSQL's default costs the planner keeps its sort at 25,000 and 100,000 records rather than read that index.
- **Connected Banking view.** `GET /api/v1/connected` builds its lookups once per view (consents by applicant, customers by id, reviews by assessment, the instalments an open checkout or an attempt in flight holds) instead of scanning every record for each customer and each open instalment, and lists the lender's customers once: the Credit Desk's `credit.permissions` names only the applicants holding a permission, and the Credit Desk reads the view's `customers`. The revision an action must name now covers what the workspace shows and its actions read (the lender and its settings, the customers, connected records, pay-by-bank receipts with their allocations, and the instalments it offers, a checkout names or a receipt was applied to, with their attempts) instead of hashing the whole lender with the locale collation, so a close, an audit entry or an export no longer makes a reviewed form stale; it also stops a lender with a close more than a week older than its latest from having every connected action refused with 409, because the write, which loads such closes as summaries, computed a different revision from the view. On the shared development machine the view took about 1.8 s and 11.2 s at 1,000 and 2,000 customers and now takes about 0.7 s and 1.4 s, most of it loading the lender; its answer is 169 KB and 329 KB instead of 340 KB and 672 KB, and a health check sent while the 2,000-customer view ran waited 0.3 s instead of 11 s.
- **The daily close's work.** A reconciliation pass, and the enrolment that follows every write, look records up through an index built once for the pass and extended as the pass adds records (`domain/record-index.ts`): records by id, allocations by payment, attempts, retry decisions and checkouts by instalment, exceptions by linked record, settlement batches by reference and the holiday calendar, which the policy engine's lookups share. They used to scan every record for each match confirmed and each open instalment evaluated, so a close cost the records times the items it handled. The records and answers are unchanged: the reconciliation, payment and close golden suites pass as they were, and a new golden test runs two closes over many allocations, instalments under an approved policy, duplicates, settlement lines and a reversal against the records the earlier code wrote. The domain work of a first close with 1,000 new observations took about 12.5 s at 1,000 customers and 28 s at 2,000 and now takes about 0.9 s and 1.9 s; a close of 1,000 customers with 6,000 future instalments under an approved policy took 10 s and takes 0.5 s, and enrolment after a write with 6,000 instalments Valo Pay collects took 3.5 s and takes 30 ms. Over HTTP, under the same load, those closes took about 17 s and 32 s and now take about 9 s and 7 s: most of what remains is loading the lender, the close review input digest and saving the 4,001 records the close changed.
- **Close review input digest once a read.** Pilot progress, the close reviews list and the work queue compute the close review input digest at most once each, however many closes and reviews they check, instead of once for each check (three times for pilot progress with a review awaiting Finance, and once more for each close and review in the list); nothing keeps it between reads, and the currency rules are unchanged. Pilot progress with one close and a review awaiting Finance took about 1.7 s and 3.6 s at 1,000 and 2,000 customers and now takes about 0.7 s and 1.7 s, which is the one digest; a close still computes it once.
- **A second administrator for privileged grants.** An invitation or membership change that grants Admin, Finance or Compliance reviewer (a new role, or reactivating a membership that holds one) now takes effect only when an administrator other than the one who asked approves it in Team & access; until then the invitation cannot be accepted and the membership is unchanged. The asker cannot approve, nobody approves a change to their own membership, a change can be declined or withdrawn, and the access history records the request, the approval and who gave it. One administrator can therefore no longer invite a second account they control as Finance or Compliance reviewer and satisfy the four-eyes rules for close review and import corrections alone. Taking access away still takes effect at once. A pilot with one administrator gets its second from the operator (`provision-pilot --add-administrator`), which the invitation's message, the refusal and the runbook say. New `POST /v1/team/invitations/{id}/approve`, `POST /v1/team/changes/{id}/approve` and `POST /v1/team/changes/{id}/decline`; a membership change answers `pendingChange` and a message.
- **Retention approval and minimum periods.** In a staff pilot the administrator who prepared a deletion preview can no longer approve it; a different administrator does, and either executes it. A retention policy can no longer be set below the workspace's minimum: 30 days in the sandbox (the time an inactive sandbox is kept), and in a staff pilot six years for original source files and export files, which are evidence, and a year for request payloads; a policy saved before the minimum is applied with it. The sandbox, one person playing every role, explains the approval rule without enforcing it.
- **Lifting the emergency stop needs two administrators.** Any administrator still turns the stop on at once. In a staff pilot, turning it off saves a request, and a different administrator lifts the stop with the new `approve_kill_switch_off` action; both are audited, and turning the stop on again or a hand-back settles a waiting request. The sandbox lifts it at once, since a second administrator could never exist there, and Settings says a pilot needs one.
- **Sensitive exports.** The `export_sensitive` rule is now enforced: dispute packs, the customer register and the audit trail are queued, retried and downloaded only by an Admin, Finance or Compliance reviewer, and anyone else is refused (403) in plain words; the console disables those buttons and hides the download link for other roles. Before this, Operations and Compliance reviewers could queue dispute packs and every role could download any ready export.
- **The team directory by shared lender.** Administrators still see every member; anyone else now sees only the colleagues who share one of their lenders, only those lenders, and no one's expiry but their own, where every role used to see every member's email, role, status, expiry and lender grants.
- **Fortnightly reviews and the business calendar.** A fortnightly staff review (MEA-05) is recorded in the name of the person signed in, at the service's time; a request that names another reviewer or a review date is refused, so a confirmation can no longer be fabricated with a free-text name or a chosen date. Only Admin and Operations now add or change business calendar dates; a Compliance reviewer or Finance is refused.
- **Re-wrapping payloads after a key rename.** A new operator command, `scripts/rewrap-payloads.ts`, re-seals protected payloads that still name an earlier wrapping key under the current one, a bounded batch per run, each in its original scope, and reports how many remain under each earlier key; it can be stopped and run again, and leaves a payload a request rewrote meanwhile to that request. `docs/pilot-security.md` now gives the rotation procedure: rotate by Cloud KMS key version where possible, re-wrap when the key name changes, and retire the previous key only after the re-wrap reports none left.
- **Rehearsing independent approval.** `docs/pilot-security.md` now describes a staging setup (a staging Clerk organisation with two administrators and a Finance, Compliance reviewer and Operations test identity, provisioned with `provision-pilot`) that rehearses every four-eyes flow the anonymous sandbox cannot: team approvals, close and correction approval, policy approval, retention approval, the emergency stop, sensitive exports and the directory.
- **Leaving a dispute.** An instalment put in dispute could never leave it: a reversal of the debit that paid DEMO-LOAN-1005 left it in dispute with ₦25,000 owed and no exception, a later repayment stayed unallocated, Finance's allocation was refused and resolving the customer dispute as not upheld changed nothing. Now a reversal of money that was applied (the provider's, or Finance's pay-by-bank reversal evidence) raises a customer_dispute exception for Operations naming the reversal, so someone owns the instalment. Resolving the dispute as not upheld, or Finance's new `release_dispute` action with a reason (Admin or Finance, from Collections), takes the instalment out of dispute: its status follows its balance (paid, part-paid, or scheduled or in collection), the release is recorded on the instalment (`disputeRelease`, which an edit cannot change) and in the audit entry, a waiting repayment is matched at the next reconciliation, pay-by-bank accepts the instalment again and the retry engine no longer holds it as disputed. A debit the customer disputed does not put a released instalment back in dispute (the engine records the stop decision dispute_released, since a disputed debit is never retried automatically), but a later disputed debit does. Upheld and mandate-cancelled resolutions keep the dispute until Finance releases it. A pay-by-bank refund reopens the instalment by its balance instead of putting it in dispute, and reversing a late receipt that paid nothing no longer puts its instalment in dispute.
- **Pay-by-bank outcomes that stay unknown.** A checkout whose outcome was unknown held its instalment for ever, with no exception: 19 days later the engine was still blocked and a new checkout refused. Once the outcome has been unknown for 24 hours, the daily close now raises an unknown_outcome exception owned by Finance and linked to the checkout, which names it, and the overview shows a high `pay_by_bank_outcome_unknown` alert. Finance (or an Admin) resolves it as confirmed successful, with the masked reference of the evidence that the money arrived, which records the receipt and applies it to the instalment, or as confirmed failed; either releases the instalment for a new checkout or retry. A sample outcome recorded later closes the exception. Pay-by-bank links an unknown checkout to its exception.
- **Exceptions close when their condition clears.** Exceptions stayed open after the payment they were about was settled, for example after SBX-PAY-1003's match was confirmed or SBX-UNIDENTIFIED-001 was refunded. The action or close that clears an exception's condition now closes it (status closed, resolution condition_cleared, with who, when and why on the exception and in the request's audit entry): an unallocated payment, overpayment or suspected duplicate whose payment is allocated in full, refunded or reversed; an unallocated payment on an instalment that is now paid; an unknown outcome that is now known; a customer dispute whose instalment left dispute. A closed exception is never reopened; if its condition returns, a new exception is raised. Resolutions stay durable across closes as before. `artifacts/api-server/tests/dispute-lifecycle-golden.test.ts` covers these three findings, with a property run of reversals, disputed debits, releases, resolutions, pay-by-bank outcomes, refunds and closes that checks money is conserved, every instalment in dispute and every long-unknown checkout has an owner and no settled exception stays open; `artifacts/valo-pay/tests/disputes.test.tsx` covers the console.
- **Scheduled closes and exports off the request thread.** The scheduled daily close and the export worker now run on a background worker thread of the API process (`artifacts/api-server/src/background.ts`, built as `dist/background.mjs` beside the server), so a month-end close or a large export no longer holds up every tenant's requests and the health probes: a first close of 20,000 records that stalled `/api/healthz` for 2.7 s on the event loop now runs for 3.6 s while probes answer within 16 ms. The thread has its own database pool of three connections (one close and two export slots), so an instance holds at most the request pool plus four, 14 by default; it keeps to the same repository modules and limits; its log lines carry the same events plus `thread: background` and are written by the main thread; and it posts the scheduler's state to the main thread, where `/api/healthz` and the console read it. A thread that crashes is logged (`background.crashed`) and started again after a wait that doubles from a second to a minute, while the API carries on and the console stops advertising the next automatic close until a pass succeeds; on SIGTERM the close in progress finishes and unfinished exports return to the queue before the thread ends (`background.stopped`). A close run through the API stays on the request path. Close times are not staggered, and the documents say why: on the thread a morning of 07:00 closes delays nobody else.
- **Exports held up by a busy lender.** An export could sit 'running' for five minutes with Retry unavailable after a busy moment on its lender: its progress writes skipped the locked lender and gave up after about 3 s, leaving the job under its lease. A write to a claimed export (progress, completion, hand-back) now waits for the lender, up to the worker's 1 s lock limit a try, and a progress or failure write the lender stays busy for past its retries hands the claim back, fenced by the lease, so the job is queued again at once (`export.job` `requeued`, with an `export.released` audit entry saying the lender was busy); the reviewer's 4 s hold now ends with the export ready. The worker's two slots take turns at one lender instead of one skipping the other's claim, so four queued exports of one lender finish in one look instead of two or four.
- **Export audit and queue reads.** Each export read its lender's whole audit chain under the lender lock to find its head, twice or three times per export (80 to 100 ms at 50,000 entries). The claim now finds the head among the records it loads for the export anyway, and a later write reads it from the entries since an hour before the claim, a range the lender-kind index serves (0.4 ms there); the chain stays valid. The queue look states the predicate of the partial index of unfinished exports (kind `exports`, status queued or running, ordered by created time and id), so migration 008's index serves it.
- **Audit entries name what a request changed.** A write's audit entry took its object and summary from `recordId` and `reason` in the raw request body, which most routes' schemas do not have, so any writer could record a settings change against a customer with an invented justification, a new customer against another customer's ID, or add a note to the summary through a record's own data; the chain verified, since the forged text was what it hashed. An entry's object is now the record the path names, the record an action names when it changed it or answers with it, or the record the answer names (a new record, export or batch), otherwise the lender's workspace; its summary is the reason the route's own schema parsed, otherwise "Synthetic workspace operation", and only a domain action's answer adds its note, such as the payer Finance identified. A connected action's object follows the same rule.
- **The restricted-database check covers privileges.** The isolation self-check reported the database as verified while the runtime login could `TRUNCATE` every workspace's records, held `REPLICATION` or membership of `pg_execute_server_program`, or could read a view a superuser owns over every lender's records. It now refuses those too: `REPLICATION` with the other elevated attributes, a membership of any role, any privilege on a table or column in any schema beyond the 40 that migration 005 grants, whether to the login or to PUBLIC, and any other relation or function in the runtime schema, logging what differs. The check takes about 6 ms, and the integration suite refuses eleven more weakenings.
- **A date-only deadline lasts its whole day.** An exception, activation or instalment deadline written as a day alone was read as UTC midnight by the queues, their SQL, the alerts and the overview, so an exception due today was already overdue from 01:00 WAT that day, while the console showed it as due all day. It now ends at 23:59:59.999 West Africa Time everywhere (`deadlineEnds` and `deadlinePassed` in the shared schema, and the same rule in the queues' SQL): due today until then and overdue after it, in the queues, their counts and order, the overview, the alerts, the daily close and the console's overdue labels.
- **Dates are real dates, and `updatedSince` names an instant.** A record's date was checked with `Date.parse`, which moves 30 February to 2 March and 24:00 to the next day, so both were saved. Every date a record's schema or checks read must now be a real calendar date as written (400 otherwise). A record list's `updatedSince` accepted `1`, a date alone or a time without an offset (read in the server's own zone), and answered 500 for a value `Date.parse` reads but PostgreSQL does not; it is now read by the shared instant schema, RFC 3339 with `Z` or an offset from the year 0001, and anything else is a 400 naming `updatedSince`.
- **Indexed text is bounded.** A free-form status or a reference a few kilobytes long reached a database index that cannot hold it and answered 500. A record's `status` is now at most 100 characters, its `reference` 200, its `customerId` 100 and an observation's `eventId` 200, and longer text is refused (400) naming the field, by the record routes and imports alike, before anything is saved.
- **A missing record is a 404 everywhere.** An action naming a record that does not exist, a new record naming an unknown customer or linked record, an export naming a close review that does not exist and a retention run to execute that does not exist answered 400 or 409; each is now a 404, as the record routes already were. A path parameter a route refuses is named in `details` (`id`, `kind` or `connectionId`) instead of an empty field, an id in the address over 100 characters is the same 400 on every route that takes one (a retry from Operations answered it 404 as an unknown address; it now reads its id as a cancel does), and 422, which no route answers, is no longer listed as a definitive refusal.
- **Search reads values, and a name is never empty.** A record list's search ran over the record's status and its data as JSON text, so `true`, `synthetic` or a field's name matched every record and a value holding a double quote was never found. It now reads the record's name, its reference and the text and number values in its data, each on its own, never a field's name or JSON's syntax. A record created or edited with an empty or blank name, which used to be saved under the kind's name, is refused (400).
- **Searched queues are quicker.** A searched collections queue folded the search into every count and looked up and folded the row's customer for each row, again for each count: about 330 ms for a pilot-scale lender (6,208 rows) on the shared test machine, 464 ms in `EXPLAIN ANALYZE` with five per-row subplans. The term is now matched once per row, and each customer once, in lateral columns that only a searched statement has: about 95 ms, timed alternately with the old statement on the same lender (about 60 ms in the plan), with the same totals. An unsearched queue takes the time it did, about 85 ms.
- **Payments waiting for Finance count alike.** The unallocated payments alert and the reports' `unallocatedOlderThan24Hours` counted only payments with the status unallocated, while the Finance queue, the ageing and the daily close also count the unapplied rest of a payment applied in part. Both now count with the same predicate (`paymentAwaitsAllocation`), so the alert, the reports and the close agree, and the alert says a payment applied in part is included.
- **The contract says what the service does.** The records `limit` was described as capped at 500 while 501 is refused; it now says values outside 1 to 500 are refused. The contract documents the `X-Valopay-Operation` header every journaled answer carries and the anonymous sandbox's cookie (the `sandboxCookie` security scheme, `__Host-valopay_sandbox` behind TLS), and says a Paystack signature covers a compressed body's bytes after decompression (gzip, deflate or br).
- **The allocation picker counts what it offers.** The picker dropped paid, cancelled and closed instalments from a page in the browser while its pager counted everything the server returned, so it could say "1–9 of 9 instalment choices" and offer five, or "1–1 of 1" and offer none. The record list now takes `allocatable=true` for instalments and keeps only those a manual allocation accepts: they still owe something and are not cancelled, closed or in dispute (one shared rule, `canTakeAllocation`, whose statuses the allocation itself checks). The picker asks for it, so its count is the number of choices; it says that paid, cancelled, closed and disputed instalments are not listed, and with none it says so in one plain line. `allocatable=true` with another kind is refused (400).
- **Counted text from the API, and one name per persona.** The API wrote a count with a bare number and a plural noun, so it said "1 source rows still need correction.", "Expected 1 source rows", "1 committed import batches; 1 customer records." and "up to 1 attempts". Such text now goes through the shared `counted` helper, which takes the singular for one and groups thousands ("4,440 minutes"): the source checks, the close review's differences and remaining items, the pilot journey's evidence, a retry policy's summary, its ceiling and the dispute pack's policy text, hand-back, invoices, the reports' allocation measures and the Credit Desk and Cash Desk reasons. A source file's "Declared 1 rows" check is left as it is: its words are part of a close's source evidence digest, so changing them would make existing closes with such a file read as changed. A demo persona now has one name, the actor its changes are recorded under: the case assignees and close reviewers list "Sandbox Finance", as the history does, instead of "Demo Finance".
- **Retention runs keep going.** As decided, an approved retention run no longer needs a click per source. The API removes as many of the run's sources as fit in a two-second budget per request under the lender lock (a run usually completes in one request), checking each again just before it is deleted and recording its receipt; a blocked source, or a deletion that cannot be confirmed, stops the run with its reason and the sources after it wait. The console sends the request again, each time with a new key, until the run completes or stops, shows how many sources are removed with a progress bar, and offers Stop, which ends the run after the current request; Resume approved run carries it on. The raw CSV eraser now reuses the check its request prepared, so a run no longer reads every batch again for each source it removes.
- **Import columns that go unused.** A customer file with its names in `full_name` passed the check as valid, its mapping showed Skip column, and committing it named each customer after its reference. Every import check (a preview, a saved batch's check and a commit's) now gives `warnings` when a name or reference comes from a fallback while a column is unused, naming the columns and the one that looks like the missing field; it never refuses the commit. The console suggests a field for a recognisable header (`full_name` as Name) as an unsaved change to save and check, shows the warnings above the row results, and asks for confirmation, naming the fallbacks, before it commits a batch or imports sample data whose check warns.
- **Lender history out of every load.** Every request that loaded a lender loaded its whole history: all its audit entries (51 MB of JSON at 50,000 entries) and, for a read, every close's full report, and the overview checked the whole audit chain and sorted every entry to show eight. The entries stay where they were, as records of kind `audit`, but no lender load reads them: the lender's settings keep the chain's position (`auditChain`: the head, which the next entry follows, and the last entry checked), a write checks only the entries since then before it appends, and the overview reads its eight recent entries with one bounded query and checks the chain from the last checked entry. `verify_audit` still checks the whole chain from its first entry, and the audit export, dispute packs and the Audit page show what they did before. When the stored head is further on than any entry, because an entry went missing, the next entry follows the stored head, whether a request or the export worker writes it, so the missing sequence is never issued again and the gap stays visible. Every load now has the closes older than a week as summaries, and the settings page reads only the latest close. On a 25,400-record lender on an otherwise idle host, with 50,000 audit entries, the overview takes about 0.25 s instead of 0.8 s, Work 0.2 s instead of 0.48 s and a keyed customer change 0.34 s instead of 1.05 s, with the same answers; with a year of closes, the reports answer is 1.6 MB in 0.23 s instead of 34.8 MB in 0.6 s, settings takes 6 ms instead of 150 to 190 ms, and Work, the pilot journey, gates, sources and import batches 0.17 to 0.24 s instead of 0.29 to 0.4 s. Twenty concurrent reads of those two lenders peaked at 0.6 GB of memory instead of 1.9 GB, and every one answered.
- **Repeats answered before the lender loads, and reads that never wait.** A repeat of a saved keyed request loaded the whole lender before it found its stored answer, and every read took a share lock on the lender, so it queued behind a write and failed after 5 s. A keyed request now looks for its stored answer before it loads the lender, and again once it holds its journal entry (an attempt that finished meanwhile is only visible then), so a repeat answers in about 10 ms instead of 0.2 to 0.8 s, and a month-end close's in 21 ms instead of 231 ms. A read answers from one snapshot of the database (`REPEATABLE READ`, made read only once its identity checks have passed) and takes no lender lock: it never waits for a write, and during one it shows the state from before it. The staff and row-security checks are those of before. A save writes its changed records in statements of up to 500 records instead of one statement each: a month-end close's 4,001 changed records take 0.33 s instead of 2.1 s, and the close answers in 4.3 s instead of 5.8 s. The journal step stays a transaction of its own, so that a request that fails or is refused still closes its journal entry, and a save still compares the whole lender with what it loaded, because the domain changes records in place.
- **Connection shares per tenant.** One anonymous sandbox could take every pooled connection with its own two lenders, because the cap was per lender (half the pool) and reads held their connection while they waited for a lender's lock. A tenant (a sandbox or a staff organisation) now uses at most a third of the pool for its lenders, and one of its lenders at most half of that (3 and 2 of the default 10); a request past its share waits without a connection, and reads no longer wait for a lender's lock at all. With both of a sandbox's lenders held by writes for 8 s, its ten reads answer in 20 to 60 ms instead of failing after 5 s, and another tenant's pages answer in 10 to 20 ms instead of 4.7 to 4.9 s, whether the busy sandbox sends reads or writes. A staff host that serves one organisation gives it a third of the pool, so the README now says to size the pool for that.
- **Bursts of page loads, measured again.** The reviewer's burst of 50 page loads (130 calls) across three tenants, each with one 25,400-record lender, was run again on an otherwise idle host. Before, 35 to 38 calls were turned away with 503, the slowest page took 6.0 to 7.6 s and the process peaked at 0.61 to 0.70 GB; after, 45 to 48 were turned away, the slowest page took 5.3 to 7.7 s and the process peaked at 0.57 to 0.60 GB. Each tenant now keeps to its share instead of taking the whole pool, so in a burst it turns more of its own requests away; how many calls a burst gets through is still set by the 0.2 to 0.7 s each of these views spends on the API's one thread, which this change does not reduce for a lender without a long history.
- **History lists capped, and the mandate customer picker paged.** A list without `limit` returned the whole kind: 34.8 MB for a year of closes and 37.5 MB for 50,000 audit entries. The kinds that grow with history (`audit`, `closes`, `exports`, `notifications` and `retry-decisions`) now return the newest 500 when no `limit` is given, with `nextOffset` to page on, as the contract says; every console list of them already asks for a page. Creating a mandate, the customer picker asks for one searchable page of 25 customers (about 10 KB) instead of the lender's whole book (394 KB).
- **Review fix: sign-in and the body parser only under `/api/v1`.** Any other address under `/api` went through Clerk's session check and the 2 MB body parser, with no request limit, before its 404, so forged session tokens could make the API call Clerk's Backend API without end, use up its rate limit and, once Clerk's cached keys expired, stop genuine sessions being verified. Sign-in, the principal limit, the parser and the body check now run under `/api/v1` only, and any other address under `/api` is answered 404 before any of them; the health checks, the production sign-in proxy and the Paystack test ingress keep their own handling. `CLERK_JWT_KEY`, now in the README's environment table and passed to Clerk with each request, lets the API verify sessions without calling Clerk at all.
- **Review fix: walking a body costs about what parsing it does.** The body check built a path for every value it walked, about 0.4 s of the API's only thread for a 2 MB body of a million values, within any client's limits. It now builds a path only for the value it refuses, and a body holding more than 100,000 values (every object, list, text and number counts; an import's CSV is one text) is refused with 413 before anything else reads it: the reviewer's body now costs 22 ms a request instead of 320 ms, and a keyed write can no longer keep 220 KB of unused values in the journal.
- **Review fix: the Clerk proxy keeps the sandbox cookie to itself.** The production Clerk proxy sent the visitor's sandbox cookies, this API's bearer token, to Clerk with every call. It now removes them and forwards only the other cookies, Clerk's own among them.
- **Review fix: a network's first sandbox is never refused because of others.** Fifteen addresses could use up a process's 300 new sandboxes an hour and turn every first-time visitor away for an hour. The process's limit now holds back only a network that has already started a sandbox in its hour; the limits per network and per IPv6 /48 are unchanged, and a client with many networks can start one sandbox an hour from each.
- **Review fix: the payload re-wrap reads the runtime schema, through a connection that sees every row.** The re-wrap could report none left, and that an earlier key may be retired, without having read a restricted runtime's schema: the owner's connection read `public`, and the restricted login read nothing through row security. It now refuses, before it reads a payload, a connection that row security filters or that neither owns the tables nor bypasses row security; reads the schema `VALOPAY_RUNTIME_SCHEMA` names when that is set; and names the schema it read and every other schema that holds the application's tables, saying to re-wrap those too. The key rotation procedure (`docs/pilot-security.md`) gives the runtime schema's run with the search path its migrations use.
- **Review fix: nobody declines a change to their own membership.** The person a waiting membership change was for could decline it and keep their role. The decline is now refused (403), as the approval was, and Team & access offers that person neither.

## Audit fixes, items 11 to 20 · September 2026

Items 11 to 20 of the 22 September 2026 audit are fixed and covered by tests:

- **Billing edge cases.** A correction is priced at the design-partner rate its collection was first billed under, a refund records what it returned, so refunding an overpayment's excess leaves the fee and the recovery on the money that stayed, and a direct debit that settled without its webhook is billed. Billing, audit and close months are West Africa Time months, and a month is invoiced only after it has ended.
- **Close report counts.** A close counts the matches confirmed in its period by their confirmation time, so reviewing an earlier match no longer reports it as confirmed again. Every reconciliation re-evaluates each settlement batch from its current lines and statement credit, so a provider file split across two imports reconciles, a batch that gains a line after it reconciled becomes a variance, a fee difference that a later line cancels is cleared, and a batch added by hand no longer stops the close when the provider's lines for it arrive. The record API cannot set the statement credit, lines or expected fees that reconciliation records on a batch, and a variance exception left open after its batch moves gains a dated note saying where the batch now stands.
- **Record integrity.** An instalment's status follows an amount edit (a paid instalment whose amount is raised is part-paid again, and a part-paid one reduced to what was paid is paid), and each close repairs statuses that earlier edits left behind. A policy version is numbered after the policy's whole history, one number cannot be approved twice or edited through the record API, and a retry decision is recorded again when its notice evidence or any other input changes.
- **Scheduled closes.** A scheduler pass now drains due lenders for up to 45 s in a fair order (staff and signed-in lenders first, then one lender per workspace per turn) instead of 25 a minute; a failing lender backs off from 2 to 60 minutes instead of blocking everyone else; an anonymous sandbox nobody has changed for seven days has its automatic close paused; a sandbox holds at most five lenders; and the scheduler tests are scoped to their own lenders.
- **Database limits.** Every transaction sets statement, lock and idle limits, a checkout waits at most 5 s, one lender holds at most half of the connections (counted per workspace, so another workspace cannot take a lender's share by naming it) and readiness has its own: one busy lender now turns its own requests away with a 503 and `Retry-After` instead of taking every connection and failing `/api/readyz`, though two lenders busy at once can still fill the default pool and hold up other tenants for up to 5 s. A connection the database ends fails that request instead of ending the process, and a COMMIT that never left because the idle limit had already ended the connection is answered as not saved. The collections queue reads each instalment by key even for a lender loaded since its statistics were last gathered (about 0.15 s instead of about 22 s).
- **Key service and workspace locks.** Protected source rows are opened only by a batch's detail, its commit, Sources for batches not yet committed (or committed without stored source quality), the retention screens and, for batches saved before this build (which have no check summary), the batch list, at most four at a time. Overviews, lists, scheduled closes, Paystack test receipts and unkeyed saves that touch no import batch keep working when the key service is down; the batch list then shows those older batches without their check counts. Console saves carry an idempotency key and seal their journal entries, so they still fail closed with a 503 during an outage. Team, persona and invitation changes take a queued workspace lock, so later requests wait behind them instead of holding them off, and a change that cannot start within 5 s answers 503 with nothing changed.
- **Stopped exports.** A worker stopped by the host returns its unfinished exports to the queue, fenced by its lease and with an audit entry, instead of recording them as failed, so the next worker resumes them at once; if that write cannot be made, the job keeps its lease and recovers when it expires. The documents now say that the close scheduler and the export worker run in the API process and need an always-on host: on Autoscale, closes run late and exports wait while the deployment is idle.
- **Paystack test ingress.** A delivery's signature is checked on its raw bytes before any lender is locked, loaded or decrypted, so a forged delivery costs one hash and gets 401. The address is in the contract, the documentation check follows every router `app.ts` mounts, and the README and `docs/paystack.md` say when the API reads the test key and which address to register with Paystack.
- **Isolation self-check.** The restricted-database check compares every row-security policy's roles, mode and expressions, the scope helpers' definitions and the workspace guard with the reviewed set, not just their names: a policy loosened to `USING (true)`, a replaced helper or a disabled guard now refuses staff requests, and the readiness page reports the database as verified only when the request's own check passed.
- **Console dead ends.** Reads are repeated only after a network failure or a 5xx or 408, at most twice, so a missing customer or case shows its not-found page at once instead of after about 7 s, and the case page now has one. A refusal that leaves a request's journal entry cancelled says `operation: "cancelled"`, and a cancelled entry can no longer complete, so the console releases a request it held as unconfirmed; every recovery notice, the team page's invitation revocation included, can also discard its original request after a warning, Settings' Discard draft and refresh works in that state, and a definitive refusal ends its key while a 401 or 429 keeps it. A refusal never marks a request whose key already has a receipt from before the journal. A corrected page number replaces the history entry, so Back leaves the list, and the import editor offers Load latest version after a colleague saves the batch, keeping the draft if that version cannot be loaded.

## Audit fixes · September 2026

The first ten items of the 22 September 2026 audit are fixed and covered by tests:

- **Returned money.** A reversed payment, or one refunded in full, is `returned`: its proposals are withdrawn, it cannot be allocated, and it is neither customer credit nor unallocated work. A refund of an overpayment's excess leaves the applied money on its instalment, and that money is credit Finance may allocate again if its match is later superseded.
- **Payment status follows its records.** Rejecting a stale proposal keeps money applied elsewhere; each close repairs contradictory statuses and leaves a payment it cannot apply with Finance instead of failing.
- **Reviews stick.** A match marked wrong, or a rejected proposal, is not recreated by the next close; "correct" after "incorrect" applies the same allocation again, or is refused while the money has moved on.
- **Resolutions hold.** A close-raised exception is not raised again while the condition behind it is unchanged, and an unknown outcome's resolution becomes the attempt's outcome, so the instalment no longer waits as in flight.
- **Bank-detail screen.** Record IDs and words such as "company" no longer trip the raw-identifier screen, so virtual-account links work for every customer.
- **Staff access.** Suspending or revoking a person withdraws their pending invitations, and only an invitation sent afterwards restores access.
- **Row security.** Migration `006_runtime_isolation_scope.sql` works out a person's lenders once per statement: a 13,000-record lender loads in about 80 ms instead of about 10 s under the restricted login.
- **Saves.** A save compares one JSON string per record and hashes only what changed, and writes load earlier daily closes as summaries: a keyed save on a 25,870-record lender takes about 0.4 s instead of about 1.7 s, and on a lender with a year of daily closes about 0.15 s instead of about 4.5 s.
- **Collections queue.** Each failed attempt reads its instalment by key: a page for a 6,208-instalment lender takes about 80 ms instead of about 2.8 s.
- **Error answers.** Malformed bodies, NUL characters, unavailable services and storage failures get their correct statuses, the security headers and origin rule run before the body is read, and a request whose transaction was rolled back says that nothing was saved.

Inclusive WAT date comparisons use the first and latest closes across the entire selected range, independent of the visible page. Current operational and billing measures remain unchanged. Report aggregates still read the relevant lender records, and no large-volume production capacity is claimed.

Console writes now carry stable request keys for retries after an uncertain response. Editable records and settings carry expected versions, with stale saves refused while input remains available. Modified forms ask before discarding work. Template review supports returning a submission for changes and creating a linked successor to an approved version, with supported-placeholder validation. CSV import supports file selection, column mapping, row previews and safe downloadable error reports. Exception resolution names the selected customer and amount and distinguishes recording an outcome from executing the underlying work.

Scheduler health is process-local. Heartbeat freshness uses the API host clock, while lender schedules and recorded closes use the database clock. The console distinguishes a service check from a completed lender close, refreshes the status while its page is active and leaves manual closing available. Saving a requested schedule does not start the scheduler or enable live collections.

## Closed production gates

### Pre-data

Requires NDPA registration, a signed DPA for each lender, a documented hosting/transfer basis and security foundations. The sandbox does not accept these as verified merely because an evidence reference was entered.

### Pre-live

Requires a qualified legal opinion, written aggregator agreement and partner credentials, independent penetration-test highs closed, mandatory MFA and fresh challenges, audited staff access, restore rehearsal, written runbooks, kill-switch drill and signed cohort cutover. A working development preview is not proof of any of these.

### Nine-month decisions

- **Funding:** Test 5 for both lenders, signed list-price Test 3, measured variable cost ≤₦15 and three months of lean-burn cash. All are required.
- **Recovery fee:** For each lender, at least eight percentage points of uplift and a 90% interval excluding zero on the preregistered sample. Separate from funding.
- **Portability:** Written permission from NIBSS and two aggregators. Routing at creation remains unbuilt.

## Verification boundary

Type checking, runtime API smoke checks, tenant-isolation/refusal checks and visual preview checks are development verification only. They do not replace independent security assessment, load and availability tests, real-provider recorded replay, recovery drill, legal review or lender pilot acceptance.

## Intentionally not built

Stage 2 connectors and routing, payment wallets, custody/settlement accounts, WhatsApp, NPS/RTP, open-banking feeds, recovery-fee charging, self-serve commercial onboarding, bulk exception tools, late-payment automation and elaborate analytics dashboards.

Automated browser workflows in desktop Chromium and Firefox and phone Chromium and WebKit (the projects in `artifacts/valo-pay/playwright.config.ts`) now complement jsdom checks. They run against a loopback-only synthetic HTTP API; a Chromium suite also runs against the real API and a disposable PostgreSQL database, and disposable PostgreSQL integration checks separately verify real pagination, search, sample parity, history ranges and lender isolation. External provider credentials and production gates remain outstanding.
