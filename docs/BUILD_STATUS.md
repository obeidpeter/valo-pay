# Valo Pay — build status
## Audit fixes, 23 September audit · September 2026

The findings of the 23 September 2026 audit are fixed and covered by tests:

- **Console survives a failed workspace refresh.** Only a workspace that cannot be loaded at all replaces the console with the unavailable notice. A background refresh that fails (the service unreachable for a few seconds, or one 429) keeps every page, form and dialog, with its draft and any "Outcome not confirmed" retry, and a notice above the page says the workspace could not be refreshed, why, when the workspace shown was loaded and that a save whose outcome is unknown can be checked in Operations, with Try again. After a 429 or 503 with `Retry-After`, the next automatic refresh waits that long and the notice says when. Neither notice says any more that no lender data has been changed: the unavailable notice points to Operations instead.
- **Back and Forward keep a draft.** The unsaved-changes guard is installed when the app loads, before the router subscribes to the browser's location, and its listener no longer relies on capturing: in Chromium, listeners on the window run in the order they were added, so Back used to unmount the draft before the guard was asked. A browser test checks Back and Forward with a Settings draft and a case note, and the jsdom test now fails if the order is lost.
- **An edit can clear an optional field.** The record dialog sends an optional field that an edit emptied (an exception's assigned owner or severity) as `null` instead of leaving it out, and `PATCH /v1/records/{kind}/{id}` now reads `data` as a merge patch: a field sent as `null` is removed, a field left out keeps its value. Before, the API refused a `null` and the dialog, which left the emptied field out, closed as saved while the old value stayed. The contract's update description says so.
- **Pilot pages tell a failed read from a lost change.** A read on a pilot page that gets no answer says the information could not be loaded and to try again, instead of pointing to Operations for a request the person never made. A change that gets no answer points to Operations only when Operations records it; a team, access or new lender change says to refresh the page to see whether it was saved. A correction preview's own check is shown in its words again, and the invitation and identity verification pages have wording of their own.
- **Focus, headings and the presentation guide.** A button that removes itself no longer drops focus on the page body: Edit on Settings moves it to the first field, Cancel and a save back to Edit, a Pay-by-bank step taken without a review to the message that says what it did, and End presentation to the page's content. Every loading and error state has an h1: a page that shows only its waiting line gives it as the heading, and a first load that failed (the overview and the four connected pages) keeps the page's heading, and the connected module tabs, above the problem card. At phone width the presentation guide's title keeps its line and its buttons wrap under it, so the guide takes at most half of a 390 by 664 px screen instead of about 60%.
- **Console copy.** Import batch counts go through the formatters ("1 source row", "1 row to fix"), a customer batch shows no ₦0.00 source total, saved exports are listed by what they hold and a plain state ("Dispute pack · JSON", "Completed"), a recovery notice says no answer arrived rather than the browser's "Failed to fetch", and the invitation page sets its own title. The API's own "1 source rows still need correction." and the persona naming are left to a later group.

## Audit fixes, items 21 to 31 · September 2026

- **Retention, indexes and readiness.** The retention screens check every source against the policy, the holds and the evidence read once per request, so their cost grows with the lender's records plus its sources rather than the two multiplied: with 5,010 journal entries on a 25,000-record lender the view takes about 0.5 s instead of about 4 s, and placing a hold about 0.9 s instead of about 4.5 s. An export file linked to an open case, or the reviewed-close export of an approved Finance review, is kept as evidence: it is never eligible for deletion and the view says why. A completed request's answer is stored once, as the replay copy under its key, and the journal keeps a reference to the saved record, so a daily close's 100 KB answer is no longer stored twice; removing old answers stays with the reviewed retention runs, whose markers refuse a replay, and nothing removes them by age alone. The record API lists, creates and edits exactly the kinds it did, validation refuses the new kinds as before, and a test builds a lender through every workflow and checks each of those records against its schema and statuses.
- **Contract gaps.** Every answer the API builds by hand (connected banking, operations, the pilot journey, batches, cases, progress, close reviews, corrections, sources, work, retention, team and readiness) is now checked against a shared schema in `lib/valopay-schema` before its transaction commits, so an answer that does not match is a 500 that saves nothing instead of a malformed confirmation. The contract describes those answers from the same schemas, and the console reads them with those schemas too: an incomplete answer shows as a problem, and an incomplete confirmation is held as unconfirmed. Each write now says whether it needs an Idempotency-Key (the batch, case, source profile, Paystack fixture and event replay writes no longer claim to require one, and every write the journal can recover lists the optional header); a missing `merchantId` is the same 400, naming the field, on every route, because the generated validators no longer turn it into the text "undefined"; date-times with an offset are accepted and stored as the UTC instant; every operation lists the statuses it really answers, with one error body (`error`, `requestId`, `details`, `code`, `committed`, `operation`) and `Retry-After` on 429 and 503; and the sandbox team directory answers `lenders: []`. ## Audit fixes, items 11 to 20 · September 2026

Items 11 to 20 of the 22 September 2026 audit are fixed and covered by tests:

- **Billing edge cases.** A correction is priced at the design-partner rate its collection was first billed under, a refund records what it returned, so refunding an overpayment's excess leaves the fee and the recovery on the money that stayed, and a direct debit that settled without its webhook is billed. Billing, audit and close months are West Africa Time months, and a month is invoiced only after it has ended.
- **Close report counts.** A close counts the matches confirmed in its period by their confirmation time, so reviewing an earlier match no longer reports it as confirmed again. Every reconciliation re-evaluates each settlement batch from its current lines and statement credit, so a provider file split across two imports reconciles, a batch that gains a line after it reconciled becomes a variance, a fee difference that a later line cancels is cleared, and a batch added by hand no longer stops the close when the provider's lines for it arrive. The record API cannot set the statement credit, lines or expected fees that reconciliation records on a batch, and a variance exception left open after its batch moves gains a dated note saying where the batch now stands.
- **Record integrity.** An instalment's status follows an amount edit (a paid instalment whose amount is raised is part-paid again, and a part-paid one reduced to what was paid is paid), and each close repairs statuses that earlier edits left behind. A policy version is numbered after the policy's whole history, one number cannot be approved twice or edited through the record API, and a retry decision is recorded again when its notice evidence or any other input changes.
- **Scheduled closes.** A scheduler pass now drains due lenders for up to 45 s in a fair order (staff and signed-in lenders first, then one lender per workspace per turn) instead of 25 a minute; a failing lender backs off from 2 to 60 minutes instead of blocking everyone else; an anonymous sandbox nobody has changed for seven days has its automatic close paused; a sandbox holds at most five lenders; and the scheduler tests are scoped to their own lenders.
- **Database limits.** Every transaction sets statement, lock and idle limits, a checkout waits at most 5 s, one lender holds at most half of the connections (counted per workspace, so another workspace cannot take a lender's share by naming it) and readiness has its own: one busy lender now turns its own requests away with a 503 and `Retry-After` instead of taking every connection and failing `/api/readyz`, though two lenders busy at once can still fill the default pool and hold up other tenants for up to 5 s. A connection the database ends fails that request instead of ending the process, and a COMMIT that never left because the idle limit had already ended the connection is answered as not saved. The collections queue reads each instalment by key even for a lender loaded since its statistics were last gathered (about 0.15 s instead of about 22 s).
- **Key service and workspace locks.** Protected source rows are opened only by a batch's detail, its commit, Sources for batches not yet committed (or committed without stored source quality), the retention screens and, for batches saved before this build (which have no check summary), the batch list, at most four at a time. Overviews, lists, scheduled closes, Paystack test receipts and unkeyed saves that touch no import batch keep working when the key service is down; the batch list then shows those older batches without their check counts. Console saves carry an idempotency key and seal their journal entries, so they still fail closed with a 503 during an outage. Team, persona and invitation changes take a queued workspace lock, so later requests wait behind them instead of holding them off, and a change that cannot start within 5 s answers 503 with nothing changed.
- **Stopped exports.** A worker stopped by the host returns its unfinished exports to the queue, fenced by its lease and with an audit entry, instead of recording them as failed, so the next worker resumes them at once; if that write cannot be made, the job keeps its lease and recovers when it expires. The documents now say that the close scheduler and the export worker run in the API process and need an always-on host: on Autoscale, closes run late and exports wait while the deployment is idle.
- **Paystack test ingress.** A delivery's signature is checked on its raw bytes before any lender is locked, loaded or decrypted, so a forged delivery costs one hash and gets 401. The address is in the contract, the documentation check follows every router `app.ts` mounts, and the README and `docs/paystack.md` say when the API reads the test key and which address to register with Paystack.
- **Isolation self-check.** The restricted-database check compares every row-security policy's roles, mode and expressions, the scope helpers' definitions and the workspace guard with the reviewed set, not just their names: a policy loosened to `USING (true)`, a replaced helper or a disabled guard now refuses staff requests, and the readiness page reports the database as verified only when the request's own check passed.
- **Console dead ends.** Reads are repeated only after a network failure or a 5xx or 408, at most twice, so a missing customer or case shows its not-found page at once instead of after about 7 s, and the case page now has one. A refusal that leaves a request's journal entry cancelled says `operation: "cancelled"`, and a cancelled entry can no longer complete, so the console releases a request it held as unconfirmed; every recovery notice, the team page's invitation revocation included, can also discard its original request after a warning, Settings' Discard draft and refresh works in that state, and a definitive refusal ends its key while a 401 or 429 keeps it. A refusal never marks a request whose key already has a receipt from before the journal. A corrected page number replaces the history entry, so Back leaves the list, and the import editor offers Load latest version after a colleague saves the batch, keeping the draft if that version cannot be loaded.

## Audit fixes · September 2026

The first ten items of the 22 September 2026 audit are fixed and covered by tests:

- **Returned money.** A reversed payment, or one refunded in full, is `returned`: its proposals are withdrawn, it cannot be allocated, and it is neither customer credit nor unallocated work. A refund of an overpayment's excess leaves the applied money on its instalment, and that money is credit Finance may allocate again if its match is later superseded.
- **Payment status follows its records.** Rejecting a stale proposal keeps money applied elsewhere; each close repairs contradictory statuses and leaves a payment it cannot apply with Finance instead of failing.
- **Reviews stick.** A match marked wrong, or a rejected proposal, is not recreated by the next close; "correct" after "incorrect" applies the same allocation again, or is refused while the money has moved on.
- **Resolutions hold.** A close-raised exception is not raised again while the condition behind it is unchanged, and an unknown outcome's resolution becomes the attempt's outcome, so the instalment no longer waits as in flight.
- **Bank-detail screen.** Record IDs and words such as "company" no longer trip the raw-identifier screen, so virtual-account links work for every customer.
- **Staff access.** Suspending or revoking a person withdraws their pending invitations, and only an invitation sent afterwards restores access.
- **Row security.** Migration `006_runtime_isolation_scope.sql` works out a person's lenders once per statement: a 13,000-record lender loads in about 80 ms instead of about 10 s under the restricted login.
- **Saves.** A save compares one JSON string per record and hashes only what changed, and writes load earlier daily closes as summaries: a keyed save on a 25,870-record lender takes about 0.4 s instead of about 1.7 s, and on a lender with a year of daily closes about 0.15 s instead of about 4.5 s.
- **Collections queue.** Each failed attempt reads its instalment by key: a page for a 6,208-instalment lender takes about 80 ms instead of about 2.8 s.
- **Error answers.** Malformed bodies, NUL characters, unavailable services and storage failures get their correct statuses, the security headers and origin rule run before the body is read, and a request whose transaction was rolled back says that nothing was saved.

## Delivery boundary

This is a working, persistent **synthetic observation sandbox** built towards Stage 1. It is **not** a claim that all 137 Stage 1 MUST requirements, live acceptance tests, regulatory prerequisites or nine-month pilot evidence have been completed.

The legacy core scope is retained within the later supplied Business Plan v3.0, Technical Requirements v2.0 and Roadmap v2.0 Connected Banking planning set. The original two-lender, one-aggregator core evidence gates remain separate from each expansion gate. A planning requirement is not evidence that a live capability is implemented. No funds are held.

The [22 September usability candidate](usability/README.md) adds operational review and recovery safeguards, with a traceable audit and human-validation kit. It is prepared for controlled preview and independent review; this note does not declare production acceptance.

## Closed production gates

### Pre-data

Requires NDPA registration, a signed DPA for each lender, a documented hosting/transfer basis and security foundations. The sandbox does not accept these as verified merely because an evidence reference was entered.

### Pre-live

Requires a qualified legal opinion, written aggregator agreement and partner credentials, independent penetration-test highs closed, mandatory MFA and fresh challenges, audited staff access, restore rehearsal, written runbooks, kill-switch drill and signed cohort cutover. A working development preview is not proof of any of these.

### Nine-month decisions

- **Funding:** Test 5 for both lenders, signed list-price Test 3, measured variable cost ≤₦15 and three months of lean-burn cash. All are required.
- **Recovery fee:** For each lender, at least eight percentage points of uplift and a 90% interval excluding zero on the preregistered sample. Separate from funding.
- **Portability:** Written permission from NIBSS and two aggregators. Routing at creation remains unbuilt.

## Verification boundary

Type checking, runtime API smoke checks, tenant-isolation/refusal checks and visual preview checks are development verification only. They do not replace independent security assessment, load and availability tests, real-provider recorded replay, recovery drill, legal review or lender pilot acceptance.
