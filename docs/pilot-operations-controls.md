# Pilot operations controls

This release extends the synthetic pilot across imports, source checks, personal work, independent close review, staff access and retention. It does not enable real customer data, payment instructions or production access. External commissioning requires a separate identity application, restricted database credentials, private storage and managed key access. No Paystack account or test key is available, so no external Paystack connection has been verified.

## Journey and Finance evidence

Journey steps distinguish not started, in progress, awaiting review, blocked and completed work. Completion requires saved imports, reconciled evidence, resolved cases, a current independent approval and an export tied to that approval. A customer, allocation, close or unrelated export alone does not establish completion.

New manual and scheduled closes record a fingerprint of financial inputs. The preparer names an active Finance reviewer with access to the lender, explains discrepancies and records acceptance of unresolved items. A different authenticated person must decide the review; switching demo personas cannot provide independence. Concurrent decisions and stale versions are refused. Corrections or a newer close make earlier approvals historical without changing their evidence.

Reviewed-close exports carry the immutable review ID and snapshot digest. Generation uses the saved snapshot and explanations, rather than recalculated current figures. A ready checksum must reference the current approved review before the journey marks evidence exported.

A request the service refuses outright (validation, permission, a missing record, a stale version: a 4xx the same request would receive again) closes its journal entry with the reason instead of leaving it pending. Only a request whose outcome is unknown (a lost response, a service failure, a rate limit) stays pending, and only pending entries count towards the limit of 100 per person and lender, so a run of refused submissions can never lock a person out. A closed entry's key cannot run again; a corrected submission carries a new key.

Source rows are screened for raw bank details where the batch is saved, whatever route or key delivered them; the recovery middleware's screen is a second line, not the only one.

## Sources and personal work

Source profiles reuse mappings, amount units and row identity columns. Expected delivery intervals and grace periods expose missed feeds; later uploads do not erase earlier missed intervals. Optional row and amount totals are checked before commit. Corrections retain source identities and revision history.

Each WAT business date now has an append-only declaration of expected source files and their original row and amount totals. Imports carry their business date separately from arrival time. One file cannot satisfy two business dates. An active profile counts as expected for a business date only from its first expected delivery, so a profile created for a feed that starts next week raises no issue for this week's closes. Missing declarations, missing or uncommitted files, mismatched totals, undeclared files and omitted active feeds stay visible in the close. A declaration of no files also requires independent Finance acceptance. The preparer explains every issue; the named Finance reviewer must accept each remaining source issue with a reason and supporting evidence, or return the review. Later source arrivals or declaration revisions require a new close; historical approvals retain their original evidence.

Reports can select an earlier source business date for a manual close; future dates are refused. This selects the source files to check and does not backdate the financial snapshot or its reporting interval. The close continues to record when it ran. Scheduled closes default to the WAT run date.

Committed import corrections use a separate comparison and approval workflow. Supported changes are customer display name or masked phone, and the amount or due date of an unpaid scheduled instalment with no collection or payment dependencies. The comparison lists affected records, and the closes and close reviews recorded up to the comparison time, before submission. A close recorded afterwards (the next scheduled close) carries the same uncorrected value but does not change what approval does, so it does not invalidate an open proposal; a new payment or collection against the instalment does. The named independent Finance reviewer approves or rejects the exact proposal; source batches, original row provenance, before/after snapshots and every decision remain unchanged. Changed records or dependencies make a proposal stale. Existing financial evidence must be handled through its investigation, reversal or adjustment workflow, rather than rewritten through import. Pending financial corrections prevent close approval. Switching demo personas cannot supply an independent reviewer.

Saved exports expose their processing stage, last progress and recovery status, judged by the database clock of the request that reads them. Brief lender-lock contention is retried against the existing artifact and lease, without generating another file. Lost leases cannot complete another worker's job. Persistently blocked confirmation preserves a recoverable job and the original object identity; stalled work appears in the operational alerts and the Exports page. Storage transfers and repository waits have bounded cancellation or timeout controls. These controls improve recovery but do not establish a production availability commitment.

My work lists assignments, handovers awaiting acknowledgement, due actions and close reviews. Reading a notice and accepting a handover have separate durable receipts. Acknowledgement requires the current assignee, assignment event and record version. It does not resolve the case or change financial status. Supervisors see workload and items overdue by at least 24 hours. Notices are in-app; no email service is configured.

## Paystack boundary

Fixed local scenarios cover signed synthetic payments, duplicates, changed amounts, stale mandate events and tampered signatures. They never contact Paystack. Optional test ingress at `POST /api/v1/providers/paystack/{connectionId}/events` checks each delivery's signature on its raw bytes before the lender is locked or read, and saves normalised evidence in a durable lender inbox; [the Paystack guide](paystack.md#signed-test-ingress) gives its configuration and answers. An operator-provisioned opaque connection resolves to an existing workspace and lender. Browser state, query strings and event fields cannot choose that scope. Live-mode evidence is rejected. Ingress creates no payment, allocation, debit or mandate authority; signed evidence still requires independent verification.

The existing read-only adapter supports future account/transaction verification. Configure `PAYSTACK_TEST_SECRET_KEY` through the host secret manager only after an account exists. External connectivity and Direct Debit availability require separate verification. The [Paystack webhook documentation](https://paystack.com/docs/payments/webhooks/) defines the signature and acknowledgement contract.

## Staff access and encryption

New non-administrator memberships have no lender grants. Administrators assign lenders with a reason and expected membership version. Revocation, role changes and invitation reacceptance clear old grants. Lists, direct links, recovery requests and eligible case/review assignees enforce the same scope. A revocation, role, lender-access or invitation change waits only for the requests already running in the workspace: requests that arrive meanwhile queue behind it, so steady polling cannot hold it off, and they run with the change applied. If the running requests do not finish within the request lock limit (5 s), the change answers 503, nothing changes, and it can be tried again. Under restricted database access a read queued behind a change to its own membership is refused with a 409 and the retry reads the new membership.

`lib/db/migrations/004_staff_lender_access.sql` is additive. `lib/db/migrations/005_runtime_isolation.sql` is a separate commissioning migration; it refuses public schemas and unknown pre-existing policies. `lib/db/migrations/006_runtime_isolation_scope.sql` must follow it in the same schema, with its own `valopay.runtime_migration=staging-only` opt-in: it keeps the same rules and policy names but works out the lenders a person may see once per statement instead of calling a helper for every row. With 005 alone, a 13,000-record lender took about ten seconds to load and the export claim reached its five-second timeout; with 006 the same load takes under 100 ms. The application refuses a runtime schema without 006. The runtime login can update a workspace's merchants, records, journal, memberships and invitations within its row scope, never a workspace row: its one column grant on that table exists so it can take the row locks every staff request needs, and a guard trigger refuses any change it attempts, because staff roles come from memberships. The rehearsal checks both. It installs a restricted runtime login and a distinct non-login helper owner, fixed helper search paths and forced row security across ten application tables. In every isolated transaction the application checks its database role and then compares the isolation set with the reviewed one in `artifacts/api-server/src/lib/runtime-isolation-policy.ts`: each of the 25 policies' command, roles, permissive mode and `USING` and `WITH CHECK` expressions as PostgreSQL writes them, each scope helper's owner, fixed search path, signature and body, and the workspace guard trigger's definition and enabled state. The catalogue is read with `pg_catalog` first, so an object in the runtime schema cannot stand in for a built-in. Any difference, such as a policy altered to `USING (true)`, a replaced helper or a disabled guard, refuses the request with a 503 and logs what differs, so the readiness page reports the database as verified for a request only when that request's own check passed. A migration that changes a policy, a helper or the guard updates that file in the same reviewed change. The recorded expressions are PostgreSQL 16's rendering: after a major-version upgrade, run the runtime isolation rehearsal on the new version before enabling staff access. Workers require a provisioned service member and recheck the original export requester's authority.

Managed envelope encryption protects original import CSV and validation previews, operation request/receipt bodies and idempotency responses. Each payload receives a fresh data key and authenticated lender/record/field scope. Managed KMS wraps the data key; the database stores ciphertext and key identifiers. Protected source rows are opened only by the views that show or use them: a batch's detail, its commit, Sources for batches not yet committed, and the retention screens, at most four at a time. Overviews, lists, ordinary saves, scheduled closes and Paystack test receipts never call the key service to open them, so they keep working while it is unavailable. A keyed save still seals its journal and replay records, so it fails closed (503) during an outage. The provider uses [Google Cloud KMS](https://cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys/encrypt) with Application Default Credentials. Missing or wrong keys fail closed. Team & access provides a synthetic key-access check and bounded protection of legacy payloads. Financial record fields, operational metadata and audit content are outside this added envelope layer; whole-database encryption and completed security acceptance are not claimed.

Keep old keys available during rotation and restore. Verify the new key, protect new writes, migrate historical envelopes under a reviewed procedure, and rehearse restore before retiring old key access. No raw key material is exported. Actual identity/MFA, KMS and restricted-database commissioning must be verified on the configured host; local fixtures do not establish those external facts.

## Retention and disaster recovery

Raw CSV, terminal recovery payload and export-file retention default to disabled. Financial and audit records remain retained. Policies and item holds require reasons and retain history. Preview lists up to 100 exact eligible source identities/digests and expires after 15 minutes. Approval revalidates current policy, holds and source versions. Execution handles one item per request under the lender lock, checks eligibility again and records a success, failure or blocked receipt. Resume uses the same saved manifest. Export deletion checks ownership, checksum metadata and object generation; a lost acknowledgement can recover from an already absent object.

Journal redaction retains request keys, fingerprints, actors and terminal status. Matching replay responses become expiry markers that prevent re-execution. Pending requests are never candidates. Raw-file removal preserves committed records, source identity and revision history. File expiry prevents downloading or retrying the expired export job; a new export is a separate request.

The recovery rehearsal restores all ten database tables, generated private-file bytes/metadata and reviewed key/access configuration. It verifies checksums, missing files, wrong keys, lender-bound decryption, audit chains and replay state. Timings and snapshot age are recorded, including an intentional post-snapshot lost write. These measurements do not establish a production recovery commitment. See [operational rehearsals](operational-rehearsals.md).

## Verification

`lib/api-spec/openapi.json` describes every route the API mounts, including the Paystack test ingress `app.ts` mounts outside `routes/index.ts`; `scripts/check-docs.mjs` follows every router `app.ts` mounts under `/api` and fails when one of its routes is missing from the contract, and the request and response shapes of the pilot, sources, work, retention and staff operations are translated from the shared zod definitions in `lib/valopay-schema` by the generator. `pnpm run test:operations` checks close reviews, source quality, signed ingress, work receipts, staff grants, encryption, recovery manifests and retention. PostgreSQL suites exercise persisted routes, concurrency and restricted runtime roles. Console and browser checks cover workflows, stale edits and uncertain responses. CI uses disposable synthetic data and requires no Paystack or managed key credentials.
