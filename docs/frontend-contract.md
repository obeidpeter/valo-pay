# Valo Pay console contract

The pilot operations release adds `/sources` (versioned mappings, delivery checks and Paystack fixtures), `/work` (personal assignments and supervisor workload), `/close-review` (independent Finance decisions and exact-snapshot exports), and `/lifecycle` (administrator retention policies, holds, deletion previews and receipts). `/team` also shows explicit lender grants and host commissioning status. See [pilot operations controls](pilot-operations-controls.md) for the persistence, authorisation and external-configuration boundaries.

All data is a persistent, isolated **synthetic sandbox**. No payment or SMS is actually sent. No live data upload is permitted. Use British spelling, NGN (kobo / 100) and Africa/Lagos dates. Always say “We never hold money”. Keep a visible “Sandbox · synthetic data” label and current Observation mode. No claims of compliance, live success, or gate passes from seed data.

## Workflow guidance and task queues

`/presentation` is an optional investor demonstration preparation page inside the console. It offers six talking points, a downloadable presenter brief, synthetic CSV files and self-reported preparation checks. The guide persists only in this browser session, scoped to the viewer and lender; invalid saved state is ignored. Starting, advancing, ending or clearing preparation checks never submits operational actions. Presenter notes are collapsed and explicitly labelled as visible on the shared screen. The match talking point opens the sample customer’s history (`/customers/:id`, found by the reference PRES-C001, or `/customers?q=PRES-C001` until the pack is imported), where the payment’s automatic, certain R1 match is shown with its explanation; it never appears in Matches to review. The guide renders above the page’s error boundary, so a page error keeps the toolbar and End presentation. Existing sandbox labels, permissions, source gaps and pending reviews remain visible. See [presentation preparation](investor-presentation.md).

The [evidence-led usability release](usability/README.md) keeps navigation stable while showing the actual demo role, lender operating mode and WAT separately from environment. Queue scroll offsets are held only in memory for the current lender/actor/role, with a bounded map; returning to a visited filtered route restores its position. Paging, filtering or searching on the same page changes only the query string and leaves the scroll position where it is (`lib/queue-position.ts`). This is separate from the existing saved-view preferences.

Forms distinguish a structured initial rejection from an unknown result after a lost response. Unknown writes retain the original payload and idempotency key, hold changed inputs and offer an exact retry. Later authentication/policy refusal does not turn that original outcome into a known failure, unless the refusal says `operation: "cancelled"`: the service has closed that request's journal entry, so neither the original nor any retry with its key was or can be saved, and the console releases the held request and shows the refusal. Every notice about an unconfirmed request also offers a way out after a warning that the original may have been saved: Discard original request, which points to Operations, or closing the record and review dialogs. A new submission then gets a new key. A definitive refusal (400, 403, 404, 409, 410, 413, 415, 422) ends its key, so an identical resubmission is a new request; a 401 or 429 keeps it, in forms and connected actions alike: such a refusal is not final, and any journal entry the request left stays pending until the same key is sent again. An answer that names the key's journal entry as `completed`, `running` or `pending` also keeps the key (`requestOpen` in `lib/safe-mutations.ts`): a request with it was saved, is still running or is not confirmed, so a failure is held as unconfirmed and retried with the same key, and a refusal does not end the key. Recovery state is not persisted through reload or deliberate abandonment. Check-only import failures remain editable; an import check never commits. Consequential dialogs start at their decision evidence, and correction links focus associated fields.

The console sends `proposalId` and `proposalUpdatedAt` in the existing action data for allocation confirmation/rejection. The server validates the supplied pair against the current proposed allocation before changing anything. The pair remains optional for compatibility with older API clients; adopting it as mandatory needs a separately reviewed contract change. At allocation commit, the server also checks current payment credit, current instalment balance and cancelled/closed/disputed state, and refuses an already-applied allocation. An audit correction displays its restored-balance effect and does not imply a refund.

The landing page offers a user-started preview of the actual console and a pilot enquiry email link. Loading the landing page alone still creates no workspace. Selecting Load interactive preview creates or resumes the same sample workspace used by the full console; the caption explains that its changes persist there. The preview omits the personal guide with `embedded=1`.

The console guide has five optional steps: inspect a customer, review a match, follow up an overdue exception, run daily close and export a dispute pack. Progress is stored per lender in the browser and is explicitly self-reported, not operational evidence. It can be dismissed, reopened and restarted.

Overview queues link to the relevant view: `/mandates?view=awaiting-activation`, `/reconciliation?view=review`, `/reconciliation?view=duplicates`, `/collections?view=failed` and `/exceptions?view=overdue`. URL parameters preserve task filters through navigation; exceptions also support due-today, owner and type filters. Urgent records sort first. Collection rows show amount, outstanding amount, due date, owner and next action; CSV import remains available in a secondary disclosure.

Collection next-action links identify the relevant mandate, customer event or instalment for payment review. The destination identifies and focuses that record, and Back to collections restores the view, owner filter and originating row, including its page. Collection next-action return addresses are restricted to the collections route and the same lender. Customer links can also return to Customers, Mandates, Exceptions or Reconciliation; these addresses are validated against the same internal-route and lender boundary. An unavailable record or a link belonging to another lender is explained instead of silently opening unrelated work. A deep link to a record or a section, such as Review matches on Reports (`/reconciliation#precision-audit`), focuses and scrolls to its target once, when it arrives: paging or filtering on that page afterwards changes only the query string, so the view and focus stay with the table being paged.

Customers and Audit log request one page from the API using `limit` and `offset`, with 25, 50 or 100 rows and a filtered total. Search waits for a 300 ms pause before requesting results, and lender or search changes reset the page. Exceptions, Mandates and Collections request server-filtered priority pages of 25, 50 or 100 rows. Search matches customer names and record references without case or accent sensitivity. Page, size and filters are lender-bound URL state, so browser Back and customer return links restore the queue. A page number beyond the last page is corrected in place, replacing the address instead of adding a history entry, so Back leaves the list rather than returning to the out-of-range page. Saved views store the search and filters per lender in this browser; they do not store result rows. Reconciliation requests six separate server-paged queues with complete totals and only the related records needed by each page. Each table keeps its current rows until its next page arrives, its frame is not a scroll anchor, and the pager (`components/record-pagination.tsx`) holds its own place on the screen until the page has loaded, since WebKit does not anchor the view, so the table, its pager and the pressed button stay where they are, including on a shorter last page. The allocation picker fetches a searchable page of instalments when opened; its search waits for a 300 ms pause before requesting results, and typing returns the picker to its first page by replacing the address, so Back leaves the page rather than stepping through letters. Precision review pages the seeded previous-month sample, including superseded allocations already reviewed as wrong. Reports request compact, server-filtered daily-close summaries; opening a close fetches its full evidence. Inclusive WAT date comparisons use the first and latest closes across the entire selected range, independent of the visible page. Current operational and billing measures remain unchanged. Customer timeline sections still page their rendered rows. Printing a paginated list includes only the visible page, with its range and total and an explicit notice when other pages are omitted.

Mandate confirmations show the customer, mandate reference, debit limit, current and resulting state, consequences and available recovery. Resuming a suspended mandate does not restore cancelled attempts. Cancellation cannot be undone; reissue creates a separate mandate with fresh consent evidence, leaves existing instalments linked as before and provides a link to the new record. Fresh-consent fields are not prefilled with the previous evidence. Policy and template reviews show version context, available previous values and synthetic sample messages; a missing or ambiguous predecessor is identified. Approval remains separate from sending a message or applying a new policy to existing mandates.

Money forms accept naira with at most two decimal places and submit exact integer kobo. Manual allocation previews remaining payment credit and instalment balance. Proposed-match decisions show both records and the allocation impact before submission; confirm and reject submit the payment ID required by the action contract. Reconciliation refreshes related records and dashboard reports after a change.

Evidence retains a searchable register across all gates, with owner, evidence date, status and edit controls. Reports distinguish no reviewed matches from a measured zero and identify the reporting period. A failed read is repeated automatically, at most twice, only when no answer arrived or the service failed (a 5xx or 408); a refusal such as 401, 403, 404, 409 or 429 shows at once. Query failures offer retry; actions and exports show useful success or failure feedback. Staff reviews confirm four named tasks individually. Settings label the prepared Paystack adapter as not connected: external verification and direct-debit capability confirmation remain necessary.

Customer history and the case page distinguish a confirmed 404 (Customer not found, Case not found) from a temporary loading failure; temporary failures retain a retry control. Audit verification records the lender and check time, clears its result when a new check starts or the lender changes, and discards late responses from an earlier visit. A successful check describes the entries checked at that time, not future entries or another lender's log.

### Effective daily-close status

Overview and Settings expose `closeSchedule`; Reports carries it in `operational.closeSchedule`. It combines the lender preference with actual process status: `enabled`, `automatic`, `runtimeState`, `serviceIssue`, `time`, `nextAt`, `missed`, `overdueMinutes`, `lateAfterMinutes`, `lastAt`, `lastTrigger`, `lastCheckedAt` and `lastErrorAt`, and the optional `failedAttempts`, `retryAt` and `pausedForInactivityAt`. A requested schedule is automatic only when this process is running the scheduler and has a recent successful service check. `nextAt` is null otherwise, and the legacy Overview `nextClose` is empty. `failedAttempts` counts failed automatic attempts at the pending time and `retryAt` is when the next is due, null unless automatic; `pausedForInactivityAt` says when the scheduler switched off the automatic close of a sandbox nobody changed for seven days. Answers saved by earlier builds, such as a replayed settings change, lack the three optional fields. The interface distinguishes intentionally off, paused for inactivity, unavailable, starting, failed, delayed, retrying, due and missed states and offers manual closing where appropriate. Saving the lender preference does not start the service.

The service check time is a process heartbeat, not proof that this lender's close completed. Completed-close history comes from this lender's records. Heartbeat age uses the API host clock through the internal `observedAt` value; due times and completed-close records use the database clock. A heartbeat is delayed after the greater of two minutes or three scheduler intervals. Overview, Reports and Settings refresh their queries every 60 seconds while active. A failed refresh on these pages, in the Reports close history or on a connected page keeps the figures already shown, with a small notice (`RefreshProblem` in `components/load-problem.tsx`) that they could not be refreshed, when they were last updated and Try again; the full problem card is left for a first load with nothing to show. These observations do not establish an availability guarantee or enable live operations.

## Records
API `ValopayRecord`: id, merchantId, kind, name, status, reference, amountKobo, customerId, createdAt, updatedAt, data (metadata).

Every status list, enum, failure code, exception type and resolution code below is defined once in `lib/valopay-schema` (`@workspace/valopay-schema`) and consumed by the API validator and the console. Never retype a value from this document; import it.

Kinds and data fields:
- customers: name, reference, status active; data bankName, accountMasked, phoneMasked, consentProvenance.
Every kind's data fields, including the ones the platform sets, are declared with their types in `lib/valopay-schema/src/records.ts` (`recordDataSchemas`, one schema per kind; `RecordDataOf<K>` is the inferred type). The API reads and writes record data through those types (`TypedRecord<K>` from `recordsOf`, `findRecord` and `makeRecord`), so the schema is the source and the summary below follows it.

- mandates: customerId, amountKobo=limit, reference provider ref, status per the TRD 4.2 machine (draft/submitted/pending_activation/active/suspended/expired/cancelled/failed; `mandateTransitions`); data workflow (`activationWorkflows`), frequency (`mandateFrequencies`), activationDeadline, consentEvidence, consentGaps, consentGiven, policyId, origin (created/imported/reissued), reminderCount, reissuedFrom. A PATCH may only follow the machine and never into cancelled or suspended; use the actions. The limit is part of the customer's consent (MAN-02): a PATCH that changes amountKobo is refused (400), and `mandate_reissue` with new consent evidence carries a new limit. RET-07: data.consentPolicyId, consentPolicyVersion and consentPolicySummary are pinned by the validator from data.policyId when the mandate is created (and by mandate_reissue, which accepts an optional data.policyId of an approved version of the same policy); they are server-owned, a direct policyId change is refused, and policyVersionHistory records each move made by apply_policy_version.
- due-items: customerId, reference, amountKobo, status scheduled/in_collection/partially_paid/paid/unpaid_final/in_dispute/cancelled/closed (derived; never set by PATCH: an edit rebuilds outstandingKobo from the confirmed allocations and the status follows it, so an instalment with nothing outstanding is paid and its unsent attempts are cancelled, one with part outstanding is partially_paid, and one with its full balance keeps scheduled or in_collection; in_dispute, cancelled and closed are kept, and unpaid_final is kept while money is owed. Each reconciliation re-derives any status that contradicts the stored balance and reports the count as `dueStatusesRepaired`); data dueDate, mandateId, owner (`executionOwners`; the TRD spelling `valo` is accepted and stored as `valopay`), outstandingKobo, overrideReason (needed between ₦5,000 and the merchant minimum from settings), amendedAt (set when amount or dueDate change), experimentId/experimentArm/firstFailureAt (immutable once assigned).
- attempts: customerId, amountKobo, status scheduled/sent/succeeded/failed/unknown/cancelled/reversed; data dueItemId, number (across every source), source=external, failureCode (normalised to the TRD 4.4 catalogue `failureCodes`; unmapped codes become UNKNOWN with rawFailureCode kept), occurredAt, providerReference (the debit reference the ladder's R1 matches on), noticeId.
- observations: customerId, reference canonical provider reference, amountKobo, status resolved/unresolved; data source (`observationSources`), dueItemId (a strong link the ladder treats as R1 when the amount matches), narration, paymentId, resolutionKey, batchReference, feeKobo, grossAmountKobo, occurredAt, reversed, provider=Sandbox Rail, providerConnection (the connection the evidence came through; provider when absent, and the lender's provider when neither is given), currency (NGN when absent). Reconciliation records countedInBatchId on a settlement line whose collection another batch already counts, and duplicateStatementCredit on a statement credit that repeats one already counted (see settlement-batches).
- payments: customerId, reference, amountKobo; status unallocated/proposed/allocated/partial/overpaid/possible_duplicate/returned; data channel, observedAt, and the four independent dimensions collectionStatus (received/succeeded/failed/unknown), settlementStatus (unsettled/settled/variance), reversalStatus (none/reversed), refundStatus (none/requested/refunded); dueItemId, allocatedKobo, explanation, rejectedDueItemIds (instalments Finance said the payment does not belong to; automatic matching never pairs them again), currency and providerConnection (the evidence's, see Payment evidence and the matching ladder under Mutations), payerIdentification {customerId, identifiedBy, identifiedAt, reason, dueItemId, allocationId} (Finance identified the payer of evidence that named none, see `manual_allocate`), duplicateReview {exceptionId, resolutionCode, reviewedBy, reviewedAt} (a suspected duplicate Finance resolved as distinct_payments; it is never held again for the same reason), evidenceConflict {paymentId, exceptionId, resolutionCode} (made from evidence that conflicted with the payment sharing its key, once Finance resolved that exception), grossUnstated (made from a settlement line that stated only its net amount). A payment's payer never changes once recorded. Money waiting for Finance (`paymentAwaitsAllocation`) is an unallocated payment's, or the unapplied rest of a partial or overpaid payment. Legacy spellings not_reversed/not_refunded are read as none. A payment whose money all went back to the payer (reversed, or refunded in full outside Valo Pay) is `returned`: its proposals are withdrawn, it cannot be allocated (409), it is in no allocation queue or ageing check, and its money is not customer credit (`paymentUnappliedKobo`, `paymentMoneyReturned`). A refund recorded after part of a payment was applied returns only the rest, such as an overpayment's excess: the applied money stays on its instalments and the payment is `allocated`. That money never went back, so if its allocation is later superseded the payment is `unallocated` again and holds it as customer credit for Finance to allocate; automatic matching, which compares the gross amount, leaves such a payment for Finance with the reason, and an allocation of more than it holds is refused (409). data.refundedKobo records what a refund returned: `record_refund` returns the money the payment had not applied, and the pay-by-bank refund returns the whole receipt after taking its allocations off the instalments. A refund recorded before the field existed is read as the whole payment, so that payment stays `returned` whatever happens to its allocations. Billing, the uplift report and the overview read the applied money that stands (`paymentAppliedKobo`): allocatedKobo less anything a refund took back, and nothing once reversed. A settlement line on a direct debit sets collectionStatus succeeded, since the debit was collected even when its webhook never arrived, and billing reads a settled direct debit stored as received the same way. A payment's status always follows its records: a payment with money applied is never `unallocated`, and each close re-derives any status that contradicts them (`paymentStatusesRepaired`); a payment the rule ladder cannot apply is left for Finance with the reason (`paymentsSkipped`) instead of failing the close.
- allocations: customerId, amountKobo, status confirmed/proposed/superseded; data paymentId, dueItemId, rule, confidence, explanation, reviewed (correct/wrong), automatic, confirmedAt (when it was applied; a precision review or a reinstatement keeps it), confirmedBy (who confirmed a proposal), supersededByReview (a precision review took it out of use), reinstatedAt (a later "correct" verdict applied it again).
- settlement-batches: name, reference=batchReference (the validator copies one to the other), status pending/reconciled/variance (derived by reconciliation, never set directly); data provider, batchReference, grossKobo, feeKobo (stated by the provider), expectedFeeKobo (from the per-provider `providerFeeSchedule` in settings, default 0.5% capped at ₦1,000), feeVarianceKobo (feeKobo less expectedFeeKobo), netKobo, lineObservationIds, linePaymentIds, statementObservationId (the first bank statement credit linked by its batch reference) and statementNetKobo (the sum of every credit that names the batch, so a second credit is compared with the net total instead of replacing the first; a credit with the reference and amount of one already counted is the same bank line again, adds nothing and is marked duplicateStatementCredit), explanation (with two or more credits it says how many the total sums), enteredTotals (the gross, fee and net Finance typed for a batch added by hand, kept when the provider's settlement lines arrive and rebuild the totals). Reconciliation records statementObservationId, statementNetKobo, lineObservationIds, linePaymentIds, expectedFeeKobo, feeVarianceKobo and enteredTotals; the record API cannot set or change them, and Finance corrects a batch through its totals (grossKobo, feeKobo and netKobo). Statement batch credits never become customer payments. Every reconciliation and daily close re-derives the status from the batch's current totals: pending until a statement credit is linked, unless the fees already differ from the schedule by more than ₦100; reconciled when the credit equals netKobo and the fees are within ₦100; variance otherwise, with a settlement_variance exception. A line imported after the credit matched, such as the second part of a provider file split across two imports, or an edit to the totals, moves the batch at the next reconciliation. A collection is counted in one batch only: a settlement line for a payment another batch already counts adds nothing to its own batch, is marked duplicateSettlementLine with countedInBatchId, and raises a settlement_variance exception on its batch that names both batches (a note on the batch's exception when one is already open), so a collection paid out twice shows as that batch's variance once its statement credit arrives. An exception raised for an earlier state stays open for Finance to resolve, and the close review lists it as an open exception until then. Each time the batch moves while that exception is open, the exception's notes gain a dated line saying where the batch now stands (`Update on 2027-07-02 (WAT): the batch is now reconciled.` followed by the batch's explanation, or, for a pending batch, that it waits for its statement credit), so the text it was raised with is not read as current.
- exceptions: customerId, amountKobo, status open/assigned/in_progress/resolved/closed (`exceptionTransitions`; resolved only through resolve_exception); data type (Appendix A `exceptionCatalogue`: activation_expired, unallocated_payment, suspected_duplicate, overpayment, unpaid_after_final_attempt, mandate_limit_exceeded, settlement_variance, provider_status_mismatch, customer_dispute, unknown_outcome, notice_not_evidenced, ownership_conflict, imported_consent_gap, mapping_needed), severity, owner and dueBy (defaulted from the catalogue: owner per type, SLA in business days), resolutionCode (from `resolutionCodesFor(type)`), notes, linkedRecordId, condition (what a daily-close check raised it for; while the same condition holds on the same record, a resolved exception is not raised again, and a changed condition, such as a different fee variance, is new work; a settlement batch's variance is keyed on its statement credit, net total and fees when the credit differs from the net total, and otherwise on its fees and expected fees, before or after a matching credit is linked, so accepting it holds until those change; an acceptance recorded under the statement spelling, which earlier builds used when they linked a matching credit to a batch whose fees differed, also holds), confirmedFailureCode (unknown_outcome resolved as failed). A suspected_duplicate raised for payment evidence that conflicts with the payment its key names is linked to the evidence, not to a payment.
- policies: status draft/submitted/approved/rejected; data version (assigned by the API: 1 for a new policy, and `new_policy_version` numbers the draft one above the highest version of the same policy, drafts and rejected versions included), maxAttempts (<=4), spacingHours (>=24), firstNoticeHours (>=24), retryNoticeHours (>=24), partialAllowed=false, author, reviewer, complianceMapping (`policyGuardrails`), previousVersionId, submittedAt, approvedAt, rejectedAt. The version and review actions record version, previousVersionId, reviewer, submittedAt, approvedAt and rejectedAt; the record API cannot set or change them. A submitted version cannot be edited (400) until a reviewer rejects it, so the reviewer approves the rules that were submitted. Approved versions immutable; a policy-version kill switch is therefore stored in settings.policyKillSwitches.
- templates: status draft/submitted/approved; data purpose, text, author, reviewer, version. Text requires {{amount}}, {{date}}, {{merchant}}, {{contact}}.
- notifications: status simulated/blocked; data purpose, channel, renderedText, acceptedAt, deliveredAt, costKobo.
- cutovers: status draft/ready/handed_back; data inventory, incumbentDisabled, externalAttemptsImported, dualRunComplete, accountableUser, fallbackOwner, confirmation. `ready` needs all three step flags plus accountableUser and confirmation (DEB-11); only then may a due item carry owner valopay. hand_back reverts to fallbackOwner and ends every contract recorded before it (DEB-12): owner valopay then needs a new contract recorded, and made ready, after the last hand-back, and an earlier contract cannot be made ready again (400). SIMULATION only.
- audit: immutable name=action, data actor, previousHash, hash, objectId, summary.
- closes: immutable daily close evidence, named by the WAT date it ran ("Daily close 2027-06-29 · scheduled"), with the business date it closed added when that differs (" · business date 2027-06-28"); data summary, metrics, closedAt, period {from, to} (from the previous close), positionAlert, sourceBusinessDate (the WAT business date whose source files the close checked; see `daily_close`), schedule {trigger scheduled/manual (`closeTriggers`), scheduledFor (the scheduled time this close covered, else null), delayMinutes, late (more than 30 minutes after that time), nextAt} (REC-01), and report (REC-07): openingUnallocated {count, kobo}, observations {received, bySource {received, resolved, unresolved, paymentsResolvedTo, batchesResolvedTo}, paymentsResolvedTo}, allocatedByRule {rule: {count, kobo, automatic}}, allocated (the allocations confirmed during the period, by data.confirmedAt, or createdAt for allocations written before confirmedAt was kept, so a precision review, a reinstatement or a later edit of an earlier match does not count it again), proposed, unallocated {count, kobo, olderThan24Hours} (openingUnallocated and unallocated count the money each payment waiting for Finance holds, `paymentAwaitsAllocation` and `paymentUnappliedKobo`: an unallocated payment and the unapplied rest of a partial or overpaid one, without the part a refund returned), possibleDuplicates, variances {count, feeVarianceKobo, batches [{batchId, reference, feeVarianceKobo, netKobo, statementNetKobo, explanation}]} (the batches in variance after the close re-evaluated every batch), exceptions {opened {count, byType}, closed {count, byType}, openAtClose, overdueAtClose}, retryDecisions, customerPositionsChanged [{customerId, customerName, before, after}], positionRebuild {mismatches, alert} (REC-05), reconciliation.
- retry-decisions: immutable, written by every close for each open obligation under an approved policy (RET-03); never created through the record API. data dueItemId, attemptId, decision (`retryDecisionKinds`), rule (TRD 6.3 row), reason, policyId, policyVersion, nextAt, evaluatedAt, experimentArm (RET-05), inputs {code, rawCode, attemptNumber, ceiling, owner, mode, attemptAt, spacingHours, leadHours, window, calendar {earliestAt, rolledForward, weekendDaysSkipped, holidaysApplied}, noticeEvidence}, noticeRequired {purpose, leadHours, requiredBy, noticeId, acceptedAt, evidenced}, fingerprint, previousDecisionId. An unchanged decision at a later close is not repeated. Two evaluations are the same decision when the attempt, row, outcome, nextAt, policy version, arm, inputs and noticeRequired all match, compared at every depth; evaluatedAt, reason and inputs.calendar are left out, because they follow the evaluation clock and the calendar's effect is already in nextAt. New notice evidence, or any other changed input, is a new record. The comparison recomputes the fingerprint from the latest record's fields, so a decision recorded before this rule (whose fingerprint left out the nested inputs) is recognised and not repeated. They carry customerId, so the customer timeline shows every decision (AUD-01).
- exports: saved jobs with status queued/running/ready/failed, kind, format, requestedBy, attempts and usedInRealCase=false. Ready jobs add checksum (SHA-256 of the file), generatedAt, byteLength, generationMs, and for packs customerReference and events. Failed jobs carry a safe lastError. Private storage identifiers, claim tokens/expiry and requestedRole are removed from list and customer timeline responses.
- invoices: immutable issued invoices (BIL-04), one for every month in order (a month with nothing to bill has a zero invoice), written only by `issue_invoice`; data period (a calendar month in West Africa Time), periodEnd (the last instant of that month in WAT, for example 2027-06-30T22:59:59.999Z), issuedAt, issuedBy, sequence, terms {commercialId, prospect, contractedLicenceKobo, designPartner, effectiveDate} (the signed terms that billed the month, or null), licence {kobo, volumeTier, tierMismatch}, usageLines [{paymentId, paymentReference, allocatedKobo (the applied money that stands), feeKobo (the public price), discountRate (the design-partner share taken off), chargedKobo (what the line charged), allocationIds}], collectionsCounted, designPartnerDiscount {rate, kobo} (on this invoice's licence and usage lines only), adjustments [{reason (`adjustmentReasons`: reversal, refund, confirmed_duplicate, wrong_allocation, re_allocation), paymentId, paymentReference, originalInvoiceId, originalInvoiceReference, kobo (what this invoice carries, negative credit, positive debit, priced at the rate of the invoice that first billed the collection), feeDeltaKobo (the public-price change), discountRate, billedChargedKobo, billedFeeKobo, currentFeeKobo, allocationIds, explanation}] (BIL-07), recoveryFee {enabled, lines, kobo, note} (BIL-03, gated on settings.recoveryFeeEnabled and settings.recoveryFeeDecision="proven", billed only after the 30-day window closes), subtotals, totals {netKobo, vatBps, vatKobo, totalKobo, creditNote}, statement, disputeRoute. amountKobo is the total, floored at zero for a credit note. Invoices issued before discountRate, chargedKobo and feeDeltaKobo were kept are read with their invoice's rate, and their adjustment kobo is the public-price change, discounted with the rest of that invoice.
- commercial: name prospect; data monthlyVolume, averageTicketKobo, implementationKobo, licenceKobo, usageBps=30, usageCapKobo=15000, signed, signedFullPriceTerms, effectiveDate, startCondition, conversationComplete, designPartner. Only list-price entries qualify; synthetic evidence does NOT pass real Test3. Signed terms bill the lender's licence (BIL-02), design-partner terms or not: a month is billed by the latest signed terms in effect by its end (effectiveDate, whose WAT month is the first it bills; terms without one apply from the start; on the same date the later recorded wins), for the whole month with no proration. Terms belong to the lender whose workspace holds them, by its id, whatever name they carry. A design partner's licence and usage are billed at half price in 2027; unsigned terms bill nothing.
- reviews: fortnightly review notes data confirmedJobs, note, reviewer, reviewedAt. Synthetic does NOT pass real Test5.
- evidence: status pending/recorded; data gateId (P1…P5, F1…F4, T1b, T2; what the gate register matches on), reference, notes. Evidence registers are not verification.
- experiments: draft/preregistered/closed; data baselineRate, holdoutShare (0.1–0.5), minPerArm (a floor for both groups), analysisDate, enrolmentClose, seed, policyId; preregistration adds sampleCalculation {holdoutMinimum, engineMinimum}, each group's own minimum. analysisDate and enrolmentClose are WAT dates: enrolment takes a first failure up to the end of the enrolmentClose day in WAT, and the analysis date is reached at midnight WAT.
- costs: name infrastructure/support/notifications; amountKobo, data period.
- calendar: name holiday, data date.
- members: read-only demo role identities.

## Pages
- `/pilot` connects lender setup to the six-step synthetic pilot journey. Counts report saved records, not approval or operational readiness. A sandbox workspace holds at most five lenders, the two samples included; a sixth is refused with 409. Staff workspaces have no such limit.
- `/imports` saves source batches and mapping, checks row identities, allows versioned correction and atomically commits valid rows. A save or commit refused because the batch changed (the service's “record changed after you opened it” refusal; other conflicts keep their own message), or a refresh that shows a newer saved version, offers Load latest version, which replaces the draft with the saved batch after confirmation. If the latest version cannot be loaded, the draft stays and the page says so. For a request with an Idempotency-Key that is decided for the key, not for the attempt: `committed: false` only when nothing sent with the key was or can be saved (its journal entry is cancelled, or nothing was saved under the key before the request failed). A repeat of a saved request, or of one still running, never says nothing was saved: it names the key's journal entry (`operation: "completed"`, `"running"`, or `"pending"` while its outcome is not confirmed) and says so in its words, such as "This lender is busy with another change. This request was saved. Try again in a moment." A repeat sent while another attempt with its key is running is answered at once with 503, `Retry-After: 2` and `operation: "running"` ("This request is still running."), and leaves the entry to that attempt. Queries retry a 503 (the query client's default retries). A mutation treats one with `committed: false` as not saved (`nothingSaved` in `lib/safe-mutations.ts`), so the next submission uses a new key, and holds any other as unconfirmed, to be retried with the same key. A journaled request's entry is closed only by a definitive refusal, or by a failure of the attempt that created it while no other attempt runs it. The contract lists this 503, with `Retry-After`, for every operation that can answer it.
- Refusals and failures (`lib/api-spec/openapi.json`, `ErrorBody`): each operation lists the statuses its route can answer, and every one carries the same body (except readiness's own 503 and the identity provider's re-verification instruction): `error` in plain words and `requestId`, with `details` (one `field` and `message` for each parameter, header or body field the request contract refused, at most 20, and `detailCount`, how many problems there were), `code` (why pilot access was refused), `committed: false` (nothing was saved) and `operation` (the state of the request's journal entry: `completed`, `running`, `pending` or `cancelled`, the last meaning the entry is closed) when they apply. A read that fails is a 500 saying the service could not prepare the answer, without `committed`: a read saves nothing either way. Every POST and PATCH lists 400, 413 and 415, because the body parser reads a body even where the operation takes none: a body is UTF-8 JSON sent as `application/json`, and one in any other format, a form's included, is refused (415). A GET's or HEAD's body is ignored, never read. Before anything is journaled or saved, a body nested more than 32 levels deep, or holding a NUL character or an unpaired UTF-16 surrogate in a string or a field name, is refused (400, naming the field), as is a body that cannot be decompressed and a path whose percent-encoding cannot be decoded. A path after `/api` is matched exactly, in its case and without a trailing slash: another spelling is an unknown resource (404), never journaled. A service a request depends on that cannot be reached (private storage, the identity provider) is a 503 with `Retry-After`. Every write whose Idempotency-Key the journal records lists 410, the answer to a repeat of a completed request whose stored result the lender's retention policy has removed; the export download and retry list it for a file retention deleted. 429 and 503 carry `Retry-After` in seconds; a 429 says 60 after a request limit (300 a minute for a signed-in person, a sandbox the server has served or otherwise the client's network, an IPv4 address or IPv6 /64; 1,200 a minute per network; 120 health checks a minute per network), 3600 after a new-sandbox limit (per network, per IPv6 /48 or per server), and 30 when the lender already has ten exports waiting or running. An operation scoped to a lender answers a missing `merchantId`, or one sent twice, with the same 400 everywhere, naming the field in `details`; the generated query validators no longer turn a missing value into the text `undefined`, which some routes had answered as an unknown lender (404). Date and time inputs (every `expectedUpdatedAt`, a case's `nextActionAt` and a source profile's `firstExpectedAt`) accept `Z` or an offset, such as `2026-09-18T08:00:00+01:00`; the service stores and compares the UTC instant and answers it with `Z`.
- Answers (`artifacts/api-server/src/lib/contract.ts`): every answer, including the ones the pilot, operations, team, readiness, sources, close review, correction, retention, work and connected routes build themselves, is checked against its schema before it is sent. The schemas for those routes live in `lib/valopay-schema` and the contract's components are generated from them. A write's answer is checked inside its transaction, before COMMIT, so an answer that does not match saves nothing: the caller gets a 500 in general words with `committed: false`, and the log records `response.invalid` with the paths that failed, never their values. The answers the retention, personal work and import correction builders check themselves are checked the same way, so a mismatch is never a validation 400 that blames the request; a timestamp stored with an offset, as an earlier build may have written it, is answered as its UTC instant. A repeat of a saved request (the same Idempotency-Key, or a retry from Operations) answers the stored receipt: fields an earlier build stored that the contract no longer lists are left out, and the log records a `response.invalid` warning; a receipt that cannot be answered within the contract is a 500 that says the request was saved (`operation: "completed"`), never `committed: false`, and so is a repeat whose stored receipt cannot be opened (the key service's 503). The console reads these answers through the same schemas (`lib/answers.ts`, `lib/pilot.ts`, `lib/connected.ts`): a field a newer service added is accepted, but a missing or malformed one is not, and an addition counts only within the shape the schema chose, never in one alternative of a union the answer might match by accident. A connected action's confirmation is read in the one shape its action gives (`connectedActionResultFor` in `lib/valopay-schema`, which the API checks it with too): a Cash Desk action's outcome, and for every other action the record it produced, of the lender the request named, so an outcome without a record never confirms a consent, checkout or credit action. A page then says the service's answer was incomplete instead of showing it, and a write is held as an incomplete confirmation, to be checked in Operations before it is submitted again.

## Mutations
`listRecords` takes status, search, and for paging `limit` (1–500; omitted returns the whole filtered set, newest first), `offset` and `updatedSince` (ISO timestamp, inclusive, for incremental sync); the response carries items, total (the filtered count) and nextOffset when more rows remain. createRecord and updateRecord for editable kinds. Business actions go to performAction:
- `set_role` data.role (Admin / Operations / Finance / Compliance reviewer / Read-only), **demo personas ONLY**, each is a separate simulated identity; no real permission granted. Like a team change, it waits only for the requests already running in the workspace, later requests wait behind it, and it answers 503 with `Retry-After` when it cannot start within 5 s: with `committed: false` without an Idempotency-Key, and otherwise as not confirmed, retried with the same key, since the key may have saved an earlier switch. Its answer is kept apart from the journal's, so the same key sent with a journaled write is a separate request.
- `kill_switch` data.enabled boolean, optional data.policyId, and reason; requires Admin. Cancels scheduled attempts under the switched scope.
- `request_instruction` always blocks: live integration/security gates unmet.
- `mandate_suspend` (active only), `mandate_reinstate` (suspended only), `mandate_cancel` (cancels scheduled attempts), `mandate_reissue` (creates a new mandate; needs data.consentEvidence; optional data.amountKobo, the limit the new consent covers, whole kobo above 0, the current limit when absent), `activation_reminder` (pending_activation only; caps 4 transfer_to_activate / 2 hosted_consent, none once consentGiven; refused in quiet hours 21:00–08:00 WAT; logs a notifications record) recordId and reason.
- `submit_policy`, `approve_policy`, `reject_policy`, `new_policy_version` recordId and reason; approval uses different actor and Compliance reviewer role. Same for templates via `submit_template`, `approve_template`. `new_policy_version` numbers the draft one above the highest version of the policy, so two drafts from one version never share a number, and `approve_policy` is refused (409) while another approved version of the same policy (linked by previousVersionId, or sharing its name) carries that number. Templates have no such refusal: `new_template_version` numbers its draft after the template's whole history, and `approve_template` does not check the number.
- `run_reconciliation`, `daily_close` no id. Reconciliation resolves observations to canonical payments, holds suspected duplicates (a payment for an already-paid due item, or the same payer and amount within two minutes), applies the ladder R1 to R5, re-evaluates every settlement batch against its fee schedule and linked statement credit, re-derives instalment statuses that contradict their stored balance (`dueStatusesRepaired`), raises catalogue exceptions with business-day deadlines, evaluates every open obligation under an approved policy and records the decision (RET-03), applies the 6.3 give-up rows (unpaid_final, in_dispute, unknown outcome after 24 hours) and raises notice_not_evidenced when a planned attempt's notice deadline passes without provider acceptance. `daily_close` additionally writes the REC-07 close report on a `closes` record (result.data.closeId, positionAlert, schedule) as a manual close, with optional data.sourceBusinessDate (today or earlier in WAT). The scheduled close (REC-01) is not an action: while its scheduler is enabled and running, the API process checks each lender's requested `closeTime` (default 07:00 WAT) with the system actor `System · scheduled close`. Each scheduled time closes one business date, the WAT day before it (the 07:00 close of 29 June closes 28 June), and checks that date's source files. `settings.nextCloseAt` is the oldest scheduled time still owed: a close that starts at or after it covers that time alone (a scheduled close always; a manual one unless it names another source business date) and moves it one day on. After an outage every missed business date therefore gets its own catch-up close, oldest first, each with its own source evidence and Finance review; the scheduler runs one per lender per pass and the lender stays due until none is owed. A manual close's source business date is the one it names, else the owed date it covers, else its WAT run date. While the automatic close is off nothing is owed and a close leaves `nextCloseAt` alone. The result's message names the business date a close covered and how many missed dates are still owed, and the missed-close alert names those dates, with their number as its count. `updateSettings` accepts `closeTime` (HH:MM WAT) and `scheduledCloseEnabled`; a changed time or switching the preference on recomputes `nextCloseAt` from now, and an unchanged save leaves a pending missed close pending. The preference does not start the scheduler. A failed scheduled attempt is retried with a growing delay and the close stays pending until one succeeds; any close clears the retry. The scheduler switches off the automatic close of an anonymous sandbox nobody has changed for seven days instead of closing it. `getOverview` carries `closeSchedule`, `closeTime` and legacy `nextClose`, which is empty whenever an automatic run is unavailable.
- Payment evidence and the matching ladder, as `run_reconciliation` and every close apply them. Evidence resolves to one canonical payment by its key: the provider connection it came through and its reference, so the same reference through another connection is another payment. Evidence under a payment's key that names another payer (or names a payer while the payment is tied to another customer's instalment), is in another currency or states another gross amount is never merged into that payment and never dropped: it stays unresolved with a Finance-owned suspected_duplicate exception linked to it (see `resolve_exception`). Evidence that names no payer agrees with any payer, and a settlement line that states only its net amount agrees with any gross at least that large; the debit's own gross then completes the payment while nothing of it is applied. The ladder runs on unallocated payments. Money in another currency than NGN is never matched and is held with an unallocated_payment exception. R1 needs the attempt's debit reference or the evidence's instalment link, the lender's own connection (evidence through another connection is held with an unallocated_payment exception) and a gross amount equal to the instalment's; it applies the match automatically and with certainty only when the evidence names the payer, and otherwise proposes it (probable), so that Finance's confirmation identifies the payer. R2 and R3 read a dedicated virtual account. R4 reads instalment references in the narration on word boundaries, across the whole lender, and where references overlap the longest wins (a narration naming LN0042-10 names neither LN0042-1 nor LN0042); it applies only when the narration names exactly one instalment, which is the payer's, open and owed exactly the amount, so a narration naming several instalments, or a reference that two instalments share once case and punctuation are set aside, is never matched automatically. R5 proposes by amount, payer and a five-day window around the due date. A payment the ladder cannot apply is held for Finance with the reason and an unallocated_payment exception, so one record never stops the close. Unallocated payments and the unapplied rest of partial payments age into an unallocated_payment exception after 24 hours (an overpayment's excess has its overpayment exception).
- `confirm_allocation`, `reject_allocation` recordId=payment ID for proposal, reason; Finance/Admin. Rejecting keeps whatever the payment has already applied elsewhere and records the pair in `rejectedDueItemIds`, so the next close does not propose it again. A proposal that no longer fits what the payment has left, for example after Finance allocated it elsewhere by hand, is withdrawn automatically. Confirming the proposal of a payment whose evidence named no payer identifies the payer, as `manual_allocate` does.
- `manual_allocate` recordId=payment ID, data.dueItemId and data.amountKobo, reason. Refused (409) for a returned payment, for more than a payment refunded in part still holds, for a payment in another currency than NGN, and for an instalment of another customer than the payment's payer. Finance's own allocation to an instalment clears an earlier rejection of that pair. A payment whose evidence named no payer, such as the seeded SBX-UNIDENTIFIED-001 or a provider settlement line without a customer, is applied only here or by confirming its proposal, and never automatically: the allocation identifies the payer as the instalment's customer in the same action. The payment takes that customer, data.payerIdentification records who identified the payer, when, the reason, the instalment and the allocation, a proposal of the payment for another customer is withdrawn, and the answer carries data.payerCustomerId and data.auditNote. The audit entry's summary is the reason followed by that note, for example "Payer confirmed by phone. Payer identified as customer DEMO-C1005 for payment SBX-UNIDENTIFIED-001." It is refused (409) when the payment's own evidence names an instalment of another customer.
- `review_allocation` recordId=allocation ID, data.correct boolean, reason; Finance/Admin. `correct=false` supersedes the allocation, reopens the payment and due item (REC-09) and records the pair in `rejectedDueItemIds`, so later closes do not recreate the match. `correct=true` on a match a review had marked wrong applies the same allocation again, or is refused (409) while the payment or instalment no longer allows it; on a match superseded for another reason (a reversal) it records the verdict only. A proposal is refused (409): confirm or reject it instead. RecordDialog always submits checkbox fields as booleans.
- `resolve_exception` recordId and reason, data.resolutionCode from `resolutionCodesFor(exception.data.type)` (Appendix A per type; the generic list only for legacy types); use structured appropriate action first. For unknown_outcome the resolution is the outcome the provider confirmed and becomes the attempt's status: resolved_failed makes it failed with the optional data.confirmedFailureCode (a `failureCodeList` code other than TIMEOUT_UNKNOWN; without one, UNKNOWN, which is never retried), resolved_succeeded makes it succeeded, provider_confirmed_no_debit makes it cancelled; `attempt.data.outcomeConfirmation` keeps what it showed before, and the instalment stops waiting as in flight. Resolutions recorded before this rule are applied by the next close (`attemptOutcomesConfirmed`). A suspected_duplicate resolved as distinct_payments releases its held payment at once (result.data.paymentStatus), and the ladder matches it from the next reconciliation without holding it again for the same reason; confirmed_duplicate_refund keeps it held until `record_refund`. Payment evidence held because it conflicts with the payment its key names becomes a payment of its own at the next reconciliation whatever the resolution, held as a possible duplicate for its refund when resolved as confirmed_duplicate_refund.
- `record_refund` recordId=payment ID data.reference external refund reference, reason. Only records external action, never moves funds. A refund returns what the payment has not applied: with nothing applied the payment becomes `returned`; with money applied, such as an overpayment whose excess went back, that money stays on its instalments and the payment becomes `allocated`. Either way its proposals are withdrawn and nothing it has left can be allocated or counted as credit, until an allocation of the money that stayed is superseded. The amount returned is recorded as data.refundedKobo and given as result.data.refundedKobo and in the message (for example NGN 5,000.00); billing and the uplift report keep the collection on the money that stayed. It is refused (409) for a reversed payment, a payment already refunded (in full or in part) and a payment whose money is all applied, which has nothing unapplied to refund. Reconciliation shows the refund control of a reversed or already refunded payment as unavailable, with the reason beside it, so it never offers a refund the service would refuse.
- `simulate_failure` recordId=due item, data.failureCode from `failureCodeList` (aliases such as ACCOUNT_CLOSED are normalised); TIMEOUT_UNKNOWN creates an attempt with status unknown, which blocks retries until resolved. Not a real debit.
- `backtest_policy` recordId=policy -> result.data.decisions list of {dueItemId,attemptId,decision,rule,reason,nextAt,policyId,policyVersion,experimentArm,inputs,noticeRequired}; decisions follow the TRD 6.3 table in order (settled, kill switch, in-flight, non-retryable, ceiling, restricted once, approval, floor and merchant minimum, mandate, consent, holdout, ownership, mode, plan). Any version, a draft or submitted one included, is tried on the instalments governed by any version of its policy, as if it were approved and applied, so the approval row and the consented-version row (policy_version_not_consented) are left out; the message says when the version is not approved. A plan stands with the failed-debit notice required 24 hours before the slot; a notice linked to the failed attempt counts only when the provider accepted it after that failure, and the attempt waits the full notice period after its acceptance; only a deadline that passes without provider acceptance defers the attempt (rule notice_not_evidenced). Backtest decisions are returned, never recorded; explicitly not a recovery estimate.
- `preregister_experiment` recordId=experiment; freezes parameters, computes sample.
- `hand_back` reason; Admin/Operations. Restores all Valo ownership to the fallbackOwner of the newest cutover that is not itself a hand-back (`handBackFallbackOwner`: lms when the contract names none it may hand back to), cancels every scheduled attempt, switches the lender's emergency stop on (`merchant.killSwitch`, which stays on until `kill_switch` turns it off) and records the checklist on a `handed_back` cutover. It ends every contract recorded before it: an instalment can carry owner valopay again only under a new contract recorded and made ready afterwards. result.data fallbackOwner, reverted (instalments returned) and cancelled (attempts cancelled). Settings lists these consequences before confirmation, with the counts read afresh when its dialog opens (the collections queue filtered to owner valopay, and attempts with status scheduled), announces the result with the service's message and counts, and shows the stop on.
- `verify_audit` result.data.valid, count, headHash.
- `issue_invoice` data.period optional (YYYY-MM, default the previous month), reason; Admin/Finance. Periods are calendar months in West Africa Time: a collection at 00:30 WAT on 1 January belongs to January, and the default is the previous WAT month. Issues the immutable invoice for the period: the contracted licence of the signed terms in effect that month (see commercial), one usage line per billable collection not billed before and observed by the period end (so a collection withheld inside its reversal window is billed on the next invoice), the design-partner discount on the licence and this invoice's usage lines, the BIL-07 adjustment lines for collections billed earlier, each at the rate of the invoice that first billed its collection, the gated recovery fee, VAT on the net. Every month is invoiced, in order, and a month with nothing to bill gets a zero invoice: a month passed over could never be invoiced afterwards, and its licence would be lost. So a period after the next one due is refused, naming the month to issue first: the month after the latest invoice or, before the first invoice, the month the earliest signed terms took effect. Also refuses a second invoice for a period, a period before the latest invoice, a future period and the current month, which can be invoiced from 00:00 WAT on the 1st of the next month (all 400). result.data invoiceId, period, totals.
- `notify_policy_change` recordId=mandate, data.policyId (approved version of the mandate's policy), reason; Admin/Operations; refused in quiet hours. Records a simulated `policy_change` notification, which is not provider-accepted evidence.
- `apply_policy_version` recordId=mandate, data.policyId (approved version of the same policy), optional data.noticeId, data.consentEvidence when settings.policyChangeRequiresConsent is true, reason; Admin/Operations. RET-07: needs a policy_change notice with provider acceptance (synthetic notices never count), moves the mandate and its consent record to the version, appends policyVersionHistory. Until then the engine keeps applying the consented version and refuses another with rule policy_version_not_consented.
- `mark_pack_used` always refuses to count synthetic exports as real cases.

Template review also supports `reject_template` (Compliance reviewer returns a submitted message with a reason) and `new_template_version` (Admin creates a draft linked to an approved predecessor). Approved wording and review metadata remain immutable. Supported placeholders are validated using the shared `templatePlaceholders` and `templateTextProblems` definitions; unknown or malformed placeholders cannot be approved.

Record updates can carry `expectedUpdatedAt`; Settings exposes a content revision and accepts `expectedRevision`. An update's `data` is merged over the stored data as a merge patch: a field left out keeps its value and a field sent as `null` is removed. The record dialog sends `null` for an optional field that an edit emptied, so the edit clears it; before, an emptied field was left out and the dialog reported success while the old value stayed. The console submits the version loaded when editing began. A stale version returns 409 without changing the record. Action reviews can also carry the record version. Stable `Idempotency-Key` values accompany logical writes, including retry after an uncertain response; a replay is checked before the old version is rejected. The contract says which writes need one: a key is required for a connected action, a new lender, a close review's preparation and decision, an import correction's proposal and decision, a source manifest, the personal work receipts and every retention change; it is optional for the writes the operations journal can recover (records, actions other than `set_role`, an import commit, settings, exports and export retries, import batches and their revisions and commits, case updates, source profiles, Paystack fixtures and event replays), which without one are not recorded or recoverable; team and readiness changes take none. A key is 8 to 200 characters; any other is refused by name (400). A refusal that leaves the request's journal entry cancelled says `operation: "cancelled"`, as does any later request with the same key; one whose key's request was saved says `operation: "completed"`. The answer is kept with the request's journal entry, so a key names one request of the person who sent it, in its lender. A repeat of a completed request whose stored result the lender's retention policy has removed is refused (410). A new lender's key is not recorded in Operations: it names the lender, so a repeat returns that lender, and a request refused before the lender was created may be sent again with the same key. A new intentional action receives a new key.

Modified dialogs, import drafts, Settings and the connected pages' forms (Pay-by-bank's checkout and review reason, Credit Desk's assessment and review, Cash Desk's planning inputs and review note, and a permission's grant or revocation) participate in the unsaved-change guard, which asks before a link, a lender change, the browser's Back or Forward, or closing the tab discards a draft. It is installed when the app loads, before the router subscribes to the browser's location, because listeners on the window run in the order they were added. A connected form keeps its inputs after it is sent, so a sent draft, answered or recovered, becomes its new starting point (`useFormDraft` in `lib/unsaved-changes.ts`); a refused one stays a draft. Staying keeps the current input. Choosing to discard permits the requested navigation or close. No customer draft is written to browser persistent storage.

## Imports & exports

`/exports` lists saved evidence jobs for the selected lender, including processing stage, recovery status, permitted retry and private download. Stalled-export alerts lead here. The Sources business-date declaration and Import batches correction workbench preserve original evidence and require named Finance review for accepted source gaps and committed-record amendments.

The CSV console requires an explicit source amount unit for monetary record types. Naira accepts at most two decimal places (including correctly grouped quoted commas); kobo requires whole digits. Conversion uses decimal integer arithmetic and rejects negative, ambiguous or unsafe amounts. The server performs the same conversion for preview and commit. The first ten parsed rows include the converted naira amount, and changing the unit or mapping invalidates the checked preview. Existing API clients that omit `amountUnit` retain integer-kobo semantics. A blank cell in an optional number column is left out, not read as 0; the amount stays required for every record type except customers, and payment evidence must be for more than ₦0. The generic source header `amount` maps to the canonical amount field; custom headers use the existing mapping control. Sample files use the selected unit. Error-free all-or-nothing validation remains required. A payment evidence row is a duplicate only when the same source event (source and eventId) is already saved or, without event IDs, the same source, reference, payer, amounts, currency, connection and batch; a row that only shares a reference is imported and reconciliation merges it or holds it as a conflict, and the same source event with different details is a row error.

Imports expose source columns, a bounded parsed row preview and the skipped count alongside validation/import totals. Mapping remains explicit, and a changed file, mapping or kind requires a fresh preview. Downloaded errors escape spreadsheet formula prefixes. Files remain synthetic-only, up to 500 rows and 1.5 MB, with all-or-nothing commits.
`importRecords`: kind customers/mandates/due-items/attempts/observations, csv text, syntheticOnly=true, commit=false for preview; commit=true to persist. Show errors per row. Header contract matches record properties plus data fields above. Default download a sample CSV for chosen kind. No real data!
`createExport`: kind (record kind / gate-pack / dispute-pack (alias customer-pack, needs customerId) / billing), format csv/json/pdf => saved job id, status and downloadUrl. It queues metadata and returns before file generation; checksum and generatedAt are available only when ready. The client uses a stable Idempotency-Key for an unchanged uncertain submission. `getExportJob` polls `/v1/exports/{id}` with merchantId; `retryExportJob` posts to `/v1/exports/{id}/retry`, retaining the same job and object key. Status, retry and download always re-authorise the lender. Downloading an unfinished job returns 409. A lender holds at most ten exports waiting or running; another is refused (429) with `Retry-After: 30`. An export whose file the retention policy removed can be neither downloaded nor retried (410): a new export is a new request. Old ready exports and older immediate-result clients remain supported.

The shared export control polls selected queued/running jobs every 1.5 seconds, reloads the latest five matching jobs, shows failures with a retry action and leaves a persistent download link plus checksum when ready. Pending jobs survive page changes and process restarts. Late mutation responses from another lender/page are ignored. A status-read failure does not assert that generation failed and offers an explicit refresh. Two worker slots per process, a five-minute claim lease (a worker that stops returns its jobs to the queue at once; the lease covers a crash), ten unfinished jobs per lender and twenty-candidate polling keep work bounded. Every storage call is aborted after sixty seconds. Sources and files have a 32 MB limit. Uploads use a stable private key with a create-only precondition; crash recovery verifies ownership metadata, byte length and SHA-256 before adopting an already-uploaded artifact. No rendering/upload occurs inside a database transaction. Queue/start/release/ready/failure/retry events participate in the audit trail, and only ready packs count in operational.packsGenerated (MEA-01).

CSV downloads are UTF-8 and start with the byte order mark spreadsheet programs need for accented letters (the importer accepts one); PDFs embed Valo Pack Sans (a Latin subset of Liberation Sans carried as base64 source in `artifacts/api-server/src/fonts`), so names print as written, and declare `en-GB`. The dispute pack (AUD-02) is a paginated PDF with a one-page summary, the full timeline oldest first and the policy, template and cutover versions as they applied at each event (AUD-06); CSV is one row per timeline event and JSON is the whole pack. The gate pack carries the RET-06 uplift report with the pre-registered rule and its result, the operational metrics and the billing statement (MEA-02). Generated files are stored privately; imported CSV source is parsed then discarded. All artifacts remain synthetic and cannot satisfy production evidence gates.
