# Valo Pay console contract

The pilot operations release adds `/sources` (versioned mappings, delivery checks and Paystack fixtures), `/work` (personal assignments and supervisor workload), `/close-review` (independent Finance decisions and exact-snapshot exports), and `/lifecycle` (administrator retention policies, holds, deletion previews and receipts). `/team` also shows explicit lender grants and host commissioning status. See [pilot operations controls](pilot-operations-controls.md) for the persistence, authorisation and external-configuration boundaries.

All data is a persistent, isolated **synthetic sandbox**. No payment or SMS is actually sent. No live data upload is permitted. Use British spelling, NGN (kobo / 100) and Africa/Lagos dates. Always say “We never hold money”. Keep a visible “Sandbox · synthetic data” label and current Observation mode. No claims of compliance, live success, or gate passes from seed data.

## Workflow guidance and task queues

`/presentation` is an optional investor demonstration preparation page inside the console. It offers six talking points, a downloadable presenter brief, synthetic CSV files and self-reported preparation checks. The guide persists only in this browser session, scoped to the viewer and lender; invalid saved state is ignored. Starting, advancing, ending or clearing preparation checks never submits operational actions. Presenter notes are collapsed and explicitly labelled as visible on the shared screen. Existing sandbox labels, permissions, source gaps and pending reviews remain visible. See [presentation preparation](investor-presentation.md).

The [evidence-led usability release](usability/README.md) keeps navigation stable while showing the actual demo role, lender operating mode and WAT separately from environment. Queue scroll offsets are held only in memory for the current lender/actor/role, with a bounded map; returning to a visited filtered route restores its position. This is separate from the existing saved-view preferences.

Forms distinguish a structured initial rejection from an unknown result after a lost response. Unknown writes retain the original payload and idempotency key, hold changed inputs and offer an exact retry. Later authentication/policy refusal does not turn that original outcome into a known failure, unless the refusal says `operation: "cancelled"`: the service has closed that request's journal entry, so neither the original nor any retry with its key was or can be saved, and the console releases the held request and shows the refusal. Every notice about an unconfirmed request also offers a way out after a warning that the original may have been saved: Discard original request, which points to Operations, or closing the record and review dialogs. A new submission then gets a new key. A definitive refusal (400, 403, 404, 409, 410, 413, 415, 422) ends its key, so an identical resubmission is a new request; a 401 or 429 keeps it. Recovery state is not persisted through reload or deliberate abandonment. Check-only import failures remain editable; an import check never commits. Consequential dialogs start at their decision evidence, and correction links focus associated fields.

The console sends `proposalId` and `proposalUpdatedAt` in the existing action data for allocation confirmation/rejection. The server validates the supplied pair against the current proposed allocation before changing anything. The pair remains optional for compatibility with older API clients; adopting it as mandatory needs a separately reviewed contract change. At allocation commit, the server also checks current payment credit, current instalment balance and cancelled/closed/disputed state, and refuses an already-applied allocation. An audit correction displays its restored-balance effect and does not imply a refund.

The landing page offers a user-started preview of the actual console and a pilot enquiry email link. Loading the landing page alone still creates no workspace. Selecting Load interactive preview creates or resumes the same sample workspace used by the full console; the caption explains that its changes persist there. The preview omits the personal guide with `embedded=1`.

The console guide has five optional steps: inspect a customer, review a match, follow up an overdue exception, run daily close and export a dispute pack. Progress is stored per lender in the browser and is explicitly self-reported, not operational evidence. It can be dismissed, reopened and restarted.

Overview queues link to the relevant view: `/mandates?view=awaiting-activation`, `/reconciliation?view=review`, `/reconciliation?view=duplicates`, `/collections?view=failed` and `/exceptions?view=overdue`. URL parameters preserve task filters through navigation; exceptions also support due-today, owner and type filters. Urgent records sort first. Collection rows show amount, outstanding amount, due date, owner and next action; CSV import remains available in a secondary disclosure.

Collection next-action links identify the relevant mandate, customer event or instalment for payment review. The destination identifies and focuses that record, and Back to collections restores the view, owner filter and originating row, including its page. Collection next-action return addresses are restricted to the collections route and the same lender. Customer links can also return to Customers, Mandates, Exceptions or Reconciliation; these addresses are validated against the same internal-route and lender boundary. An unavailable record or a link belonging to another lender is explained instead of silently opening unrelated work.

Customers and Audit log request one page from the API using `limit` and `offset`, with 25, 50 or 100 rows and a filtered total. Search waits for a 300 ms pause before requesting results, and lender or search changes reset the page. Exceptions, Mandates and Collections request server-filtered priority pages of 25, 50 or 100 rows. Search matches customer names and record references without case or accent sensitivity. Page, size and filters are lender-bound URL state, so browser Back and customer return links restore the queue. A page number beyond the last page is corrected in place, replacing the address instead of adding a history entry, so Back leaves the list rather than returning to the out-of-range page. Saved views store the search and filters per lender in this browser; they do not store result rows. Reconciliation requests six separate server-paged queues with complete totals and only the related records needed by each page. The allocation picker fetches a searchable page of instalments when opened. Precision review pages the seeded previous-month sample, including superseded allocations already reviewed as wrong. Reports request compact, server-filtered daily-close summaries; opening a close fetches its full evidence. Inclusive WAT date comparisons use the first and latest closes across the entire selected range, independent of the visible page. Current operational and billing measures remain unchanged. Customer timeline sections still page their rendered rows. Printing a paginated list includes only the visible page, with its range and total and an explicit notice when other pages are omitted.

Mandate confirmations show the customer, mandate reference, debit limit, current and resulting state, consequences and available recovery. Resuming a suspended mandate does not restore cancelled attempts. Cancellation cannot be undone; reissue creates a separate mandate with fresh consent evidence, leaves existing instalments linked as before and provides a link to the new record. Fresh-consent fields are not prefilled with the previous evidence. Policy and template reviews show version context, available previous values and synthetic sample messages; a missing or ambiguous predecessor is identified. Approval remains separate from sending a message or applying a new policy to existing mandates.

Money forms accept naira with at most two decimal places and submit exact integer kobo. Manual allocation previews remaining payment credit and instalment balance. Proposed-match decisions show both records and the allocation impact before submission; confirm and reject submit the payment ID required by the action contract. Reconciliation refreshes related records and dashboard reports after a change.

Evidence retains a searchable register across all gates, with owner, evidence date, status and edit controls. Reports distinguish no reviewed matches from a measured zero and identify the reporting period. A failed read is repeated automatically, at most twice, only when no answer arrived or the service failed (a 5xx or 408); a refusal such as 401, 403, 404, 409 or 429 shows at once. Query failures offer retry; actions and exports show useful success or failure feedback. Staff reviews confirm four named tasks individually. Settings label the prepared Paystack adapter as not connected: external verification and direct-debit capability confirmation remain necessary.

Customer history and the case page distinguish a confirmed 404 (Customer not found, Case not found) from a temporary loading failure; temporary failures retain a retry control. Audit verification records the lender and check time, clears its result when a new check starts or the lender changes, and discards late responses from an earlier visit. A successful check describes the entries checked at that time, not future entries or another lender's log.

### Effective daily-close status

Overview and Settings expose `closeSchedule`; Reports carries it in `operational.closeSchedule`. It combines the lender preference with actual process status: `enabled`, `automatic`, `runtimeState`, `serviceIssue`, `time`, `nextAt`, `missed`, `overdueMinutes`, `lateAfterMinutes`, `lastAt`, `lastTrigger`, `lastCheckedAt` and `lastErrorAt`, and the optional `failedAttempts`, `retryAt` and `pausedForInactivityAt`. A requested schedule is automatic only when this process is running the scheduler and has a recent successful service check. `nextAt` is null otherwise, and the legacy Overview `nextClose` is empty. `failedAttempts` counts failed automatic attempts at the pending time and `retryAt` is when the next is due, null unless automatic; `pausedForInactivityAt` says when the scheduler switched off the automatic close of a sandbox nobody changed for seven days. Answers saved by earlier builds, such as a replayed settings change, lack the three optional fields. The interface distinguishes intentionally off, paused for inactivity, unavailable, starting, failed, delayed, retrying, due and missed states and offers manual closing where appropriate. Saving the lender preference does not start the service.

The service check time is a process heartbeat, not proof that this lender's close completed. Completed-close history comes from this lender's records. Heartbeat age uses the API host clock through the internal `observedAt` value; due times and completed-close records use the database clock. A heartbeat is delayed after the greater of two minutes or three scheduler intervals. Overview, Reports and Settings refresh their queries every 60 seconds while active. These observations do not establish an availability guarantee or enable live operations.

## Records
API `ValopayRecord`: id, merchantId, kind, name, status, reference, amountKobo, customerId, createdAt, updatedAt, data (metadata).

Every status list, enum, failure code, exception type and resolution code below is defined once in `lib/valopay-schema` (`@workspace/valopay-schema`) and consumed by the API validator and the console. Never retype a value from this document; import it.

Kinds and data fields:
- customers: name, reference, status active; data bankName, accountMasked, phoneMasked, consentProvenance.
Every kind's data fields, including the ones the platform sets, are declared with their types in `lib/valopay-schema/src/records.ts` (`recordDataSchemas`, one schema per kind; `RecordDataOf<K>` is the inferred type). The API reads and writes record data through those types (`TypedRecord<K>` from `recordsOf`, `findRecord` and `makeRecord`), so the schema is the source and the summary below follows it.

- mandates: customerId, amountKobo=limit, reference provider ref, status per the TRD 4.2 machine (draft/submitted/pending_activation/active/suspended/expired/cancelled/failed; `mandateTransitions`); data workflow (`activationWorkflows`), frequency (`mandateFrequencies`), activationDeadline, consentEvidence, consentGaps, consentGiven, policyId, origin (created/imported/reissued), reminderCount, reissuedFrom. A PATCH may only follow the machine and never into cancelled or suspended; use the actions. RET-07: data.consentPolicyId, consentPolicyVersion and consentPolicySummary are pinned by the validator from data.policyId when the mandate is created (and by mandate_reissue, which accepts an optional data.policyId of an approved version of the same policy); they are server-owned, a direct policyId change is refused, and policyVersionHistory records each move made by apply_policy_version.
- due-items: customerId, reference, amountKobo, status scheduled/in_collection/partially_paid/paid/unpaid_final/in_dispute/cancelled/closed (derived; never set by PATCH: an edit rebuilds outstandingKobo from the confirmed allocations and the status follows it, so an instalment with nothing outstanding is paid and its unsent attempts are cancelled, one with part outstanding is partially_paid, and one with its full balance keeps scheduled or in_collection; in_dispute, cancelled and closed are kept, and unpaid_final is kept while money is owed. Each reconciliation re-derives any status that contradicts the stored balance and reports the count as `dueStatusesRepaired`); data dueDate, mandateId, owner (`executionOwners`; the TRD spelling `valo` is accepted and stored as `valopay`), outstandingKobo, overrideReason (needed between ₦5,000 and the merchant minimum from settings), amendedAt (set when amount or dueDate change), experimentId/experimentArm/firstFailureAt (immutable once assigned).
- attempts: customerId, amountKobo, status scheduled/sent/succeeded/failed/unknown/cancelled/reversed; data dueItemId, number (across every source), source=external, failureCode (normalised to the TRD 4.4 catalogue `failureCodes`; unmapped codes become UNKNOWN with rawFailureCode kept), occurredAt, providerReference (the debit reference the ladder's R1 matches on), noticeId.
- observations: customerId, reference canonical provider reference, amountKobo, status resolved/unresolved; data source (`observationSources`), dueItemId (a strong link the ladder treats as R1 when the amount matches), narration, paymentId, resolutionKey, batchReference, feeKobo, grossAmountKobo, occurredAt, reversed, provider=Sandbox Rail.
- payments: customerId, reference, amountKobo; status unallocated/proposed/allocated/partial/overpaid/possible_duplicate/returned; data channel, observedAt, and the four independent dimensions collectionStatus (received/succeeded/failed/unknown), settlementStatus (unsettled/settled/variance), reversalStatus (none/reversed), refundStatus (none/requested/refunded); dueItemId, allocatedKobo, explanation, rejectedDueItemIds (instalments Finance said the payment does not belong to; automatic matching never pairs them again). Legacy spellings not_reversed/not_refunded are read as none. A payment whose money all went back to the payer (reversed, or refunded in full outside Valo Pay) is `returned`: its proposals are withdrawn, it cannot be allocated (409), it is in no allocation queue or ageing check, and its money is not customer credit (`paymentUnappliedKobo`, `paymentMoneyReturned`). A refund recorded after part of a payment was applied returns only the rest, such as an overpayment's excess: the applied money stays on its instalments and the payment is `allocated`. That money never went back, so if its allocation is later superseded the payment is `unallocated` again and holds it as customer credit for Finance to allocate; automatic matching, which compares the gross amount, leaves such a payment for Finance with the reason, and an allocation of more than it holds is refused (409). data.refundedKobo records what a refund returned: `record_refund` returns the money the payment had not applied, and the pay-by-bank refund returns the whole receipt after taking its allocations off the instalments. A refund recorded before the field existed is read as the whole payment, so that payment stays `returned` whatever happens to its allocations. Billing, the uplift report and the overview read the applied money that stands (`paymentAppliedKobo`): allocatedKobo less anything a refund took back, and nothing once reversed. A settlement line on a direct debit sets collectionStatus succeeded, since the debit was collected even when its webhook never arrived, and billing reads a settled direct debit stored as received the same way. A payment's status always follows its records: a payment with money applied is never `unallocated`, and each close re-derives any status that contradicts them (`paymentStatusesRepaired`); a payment the rule ladder cannot apply is left for Finance with the reason (`paymentsSkipped`) instead of failing the close.
- allocations: customerId, amountKobo, status confirmed/proposed/superseded; data paymentId, dueItemId, rule, confidence, explanation, reviewed (correct/wrong), automatic, confirmedAt (when it was applied; a precision review or a reinstatement keeps it), confirmedBy (who confirmed a proposal), supersededByReview (a precision review took it out of use), reinstatedAt (a later "correct" verdict applied it again).
- settlement-batches: name, reference=batchReference (the validator copies one to the other), status pending/reconciled/variance (derived by reconciliation, never set directly); data provider, batchReference, grossKobo, feeKobo (stated by the provider), expectedFeeKobo (from the per-provider `providerFeeSchedule` in settings, default 0.5% capped at ₦1,000), feeVarianceKobo (feeKobo less expectedFeeKobo), netKobo, lineObservationIds, linePaymentIds, statementObservationId and statementNetKobo (the bank statement credit linked by its batch reference; a later credit replaces it), explanation, enteredTotals (the gross, fee and net Finance typed for a batch added by hand, kept when the provider's settlement lines arrive and rebuild the totals). Reconciliation records statementObservationId, statementNetKobo, lineObservationIds, linePaymentIds, expectedFeeKobo, feeVarianceKobo and enteredTotals; the record API cannot set or change them, and Finance corrects a batch through its totals (grossKobo, feeKobo and netKobo). Statement batch credits never become customer payments. Every reconciliation and daily close re-derives the status from the batch's current totals: pending until a statement credit is linked, unless the fees already differ from the schedule by more than ₦100; reconciled when the credit equals netKobo and the fees are within ₦100; variance otherwise, with a settlement_variance exception. A line imported after the credit matched, such as the second part of a provider file split across two imports, or an edit to the totals, moves the batch at the next reconciliation. An exception raised for an earlier state stays open for Finance to resolve, and the close review lists it as an open exception until then. Each time the batch moves while that exception is open, the exception's notes gain a dated line saying where the batch now stands (`Update on 2027-07-02 (WAT): the batch is now reconciled.` followed by the batch's explanation, or, for a pending batch, that it waits for its statement credit), so the text it was raised with is not read as current.
- exceptions: customerId, amountKobo, status open/assigned/in_progress/resolved/closed (`exceptionTransitions`; resolved only through resolve_exception); data type (Appendix A `exceptionCatalogue`: activation_expired, unallocated_payment, suspected_duplicate, overpayment, unpaid_after_final_attempt, mandate_limit_exceeded, settlement_variance, provider_status_mismatch, customer_dispute, unknown_outcome, notice_not_evidenced, ownership_conflict, imported_consent_gap, mapping_needed), severity, owner and dueBy (defaulted from the catalogue: owner per type, SLA in business days), resolutionCode (from `resolutionCodesFor(type)`), notes, linkedRecordId, condition (what a daily-close check raised it for; while the same condition holds on the same record, a resolved exception is not raised again, and a changed condition, such as a different fee variance, is new work; a settlement batch's variance is keyed on its statement credit, net total and fees when the credit differs from the net total, and otherwise on its fees and expected fees, before or after a matching credit is linked, so accepting it holds until those change; an acceptance recorded under the statement spelling, which earlier builds used when they linked a matching credit to a batch whose fees differed, also holds), confirmedFailureCode (unknown_outcome resolved as failed).
- policies: status draft/submitted/approved/rejected; data version (assigned by the API: 1 for a new policy, and `new_policy_version` numbers the draft one above the highest version of the same policy, drafts and rejected versions included), maxAttempts (<=4), spacingHours (>=24), firstNoticeHours (>=24), retryNoticeHours (>=24), partialAllowed=false, author, reviewer, complianceMapping (`policyGuardrails`), previousVersionId, submittedAt, approvedAt, rejectedAt. The version and review actions record version, previousVersionId, reviewer, submittedAt, approvedAt and rejectedAt; the record API cannot set or change them. Approved versions immutable; a policy-version kill switch is therefore stored in settings.policyKillSwitches.
- templates: status draft/submitted/approved; data purpose, text, author, reviewer, version. Text requires {{amount}}, {{date}}, {{merchant}}, {{contact}}.
- notifications: status simulated/blocked; data purpose, channel, renderedText, acceptedAt, deliveredAt, costKobo.
- cutovers: status draft/ready/handed_back; data inventory, incumbentDisabled, externalAttemptsImported, dualRunComplete, accountableUser, fallbackOwner, confirmation. `ready` needs all three step flags plus accountableUser and confirmation (DEB-11); only then may a due item carry owner valopay. hand_back reverts to fallbackOwner. SIMULATION only.
- audit: immutable name=action, data actor, previousHash, hash, objectId, summary.
- closes: immutable daily close evidence; data summary, metrics, closedAt, period {from, to} (from the previous close), positionAlert, schedule {trigger scheduled/manual (`closeTriggers`), scheduledFor (the pending scheduled instant this close covered, else null), delayMinutes, late (more than 30 minutes after that instant), nextAt} (REC-01), and report (REC-07): openingUnallocated {count, kobo}, observations {received, bySource {received, resolved, unresolved, paymentsResolvedTo, batchesResolvedTo}, paymentsResolvedTo}, allocatedByRule {rule: {count, kobo, automatic}}, allocated (the allocations confirmed during the period, by data.confirmedAt, or createdAt for allocations written before confirmedAt was kept, so a precision review, a reinstatement or a later edit of an earlier match does not count it again), proposed, unallocated {count, kobo, olderThan24Hours} (openingUnallocated and unallocated count the money each unallocated payment holds, `paymentUnappliedKobo`, so the part a refund returned is left out), possibleDuplicates, variances {count, feeVarianceKobo, batches [{batchId, reference, feeVarianceKobo, netKobo, statementNetKobo, explanation}]} (the batches in variance after the close re-evaluated every batch), exceptions {opened {count, byType}, closed {count, byType}, openAtClose, overdueAtClose}, retryDecisions, customerPositionsChanged [{customerId, customerName, before, after}], positionRebuild {mismatches, alert} (REC-05), reconciliation.
- retry-decisions: immutable, written by every close for each open obligation under an approved policy (RET-03); never created through the record API. data dueItemId, attemptId, decision (`retryDecisionKinds`), rule (TRD 6.3 row), reason, policyId, policyVersion, nextAt, evaluatedAt, experimentArm (RET-05), inputs {code, rawCode, attemptNumber, ceiling, owner, mode, attemptAt, spacingHours, leadHours, window, calendar {earliestAt, rolledForward, weekendDaysSkipped, holidaysApplied}, noticeEvidence}, noticeRequired {purpose, leadHours, requiredBy, noticeId, acceptedAt, evidenced}, fingerprint, previousDecisionId. An unchanged decision at a later close is not repeated. Two evaluations are the same decision when the attempt, row, outcome, nextAt, policy version, arm, inputs and noticeRequired all match, compared at every depth; evaluatedAt, reason and inputs.calendar are left out, because they follow the evaluation clock and the calendar's effect is already in nextAt. New notice evidence, or any other changed input, is a new record. The comparison recomputes the fingerprint from the latest record's fields, so a decision recorded before this rule (whose fingerprint left out the nested inputs) is recognised and not repeated. They carry customerId, so the customer timeline shows every decision (AUD-01).
- exports: saved jobs with status queued/running/ready/failed, kind, format, requestedBy, attempts and usedInRealCase=false. Ready jobs add checksum (SHA-256 of the file), generatedAt, byteLength, generationMs, and for packs customerReference and events. Failed jobs carry a safe lastError. Private storage identifiers, claim tokens/expiry and requestedRole are removed from list and customer timeline responses.
- invoices: immutable issued invoices (BIL-04), one per period in period order, written only by `issue_invoice`; data period (a calendar month in West Africa Time), periodEnd (the last instant of that month in WAT, for example 2027-06-30T22:59:59.999Z), issuedAt, issuedBy, sequence, terms, licence {kobo, volumeTier, tierMismatch}, usageLines [{paymentId, paymentReference, allocatedKobo (the applied money that stands), feeKobo (the public price), discountRate (the design-partner share taken off), chargedKobo (what the line charged), allocationIds}], collectionsCounted, designPartnerDiscount {rate, kobo} (on this invoice's licence and usage lines only), adjustments [{reason (`adjustmentReasons`: reversal, refund, confirmed_duplicate, wrong_allocation, re_allocation), paymentId, paymentReference, originalInvoiceId, originalInvoiceReference, kobo (what this invoice carries, negative credit, positive debit, priced at the rate of the invoice that first billed the collection), feeDeltaKobo (the public-price change), discountRate, billedChargedKobo, billedFeeKobo, currentFeeKobo, allocationIds, explanation}] (BIL-07), recoveryFee {enabled, lines, kobo, note} (BIL-03, gated on settings.recoveryFeeEnabled and settings.recoveryFeeDecision="proven", billed only after the 30-day window closes), subtotals, totals {netKobo, vatBps, vatKobo, totalKobo, creditNote}, statement, disputeRoute. amountKobo is the total, floored at zero for a credit note. Invoices issued before discountRate, chargedKobo and feeDeltaKobo were kept are read with their invoice's rate, and their adjustment kobo is the public-price change, discounted with the rest of that invoice.
- commercial: name prospect; data monthlyVolume, averageTicketKobo, implementationKobo, licenceKobo, usageBps=30, usageCapKobo=15000, signed, signedFullPriceTerms, effectiveDate, startCondition, conversationComplete, designPartner. Only list-price entries qualify; synthetic evidence does NOT pass real Test3.
- reviews: fortnightly review notes data confirmedJobs, note, reviewer, reviewedAt. Synthetic does NOT pass real Test5.
- evidence: status pending/recorded; data gateId (P1…P5, F1…F4, T1b, T2; what the gate register matches on), reference, notes. Evidence registers are not verification.
- experiments: draft/preregistered/closed; data baselineRate, holdoutShare (0.1–0.5), minPerArm, analysisDate, enrolmentClose, seed, policyId.
- costs: name infrastructure/support/notifications; amountKobo, data period.
- calendar: name holiday, data date.
- members: read-only demo role identities.

## Pages
- `/pilot` connects lender setup to the six-step synthetic pilot journey. Counts report saved records, not approval or operational readiness. A sandbox workspace holds at most five lenders, the two samples included; a sixth is refused with 409. Staff workspaces have no such limit.
- `/imports` saves source batches and mapping, checks row identities, allows versioned correction and atomically commits valid rows. A save or commit refused because the batch changed, or a refresh that shows a newer saved version, offers Load latest version, which replaces the draft with the saved batch after confirmation. Source rows are restricted to import operators. The batch list's check counts come from a check summary saved with each batch, so the list opens no protected source rows for them. A batch saved before summaries were stored has none (a committed batch never gains one): the list opens its check for the counts and, while the key service is unavailable, lists it without `data.check` instead of failing. A batch's detail and its commit open that batch's rows, and answer 503 while the key service is unavailable.
- `/operations` lists this caller's received requests for the selected lender. Replays use the stored original request under current permissions. Cancellation blocks later execution only when no completion receipt exists. A cancelled request can no longer complete, even if an earlier attempt with its key was still running.
- `/cases/:id` claims, hands over and records the next action on an existing exception, with a version check and immutable event history. Financial resolution remains a separate controlled action. An unknown case ID shows Case not found with links to Exceptions and Overview.
- `/team` shows the access mode. In staff staging, administrators invite, suspend and revoke named memberships; fresh server membership and MFA are required for every transaction. A team, lender-access or invitation change waits only for the requests already running in the workspace, and requests that arrive meanwhile wait behind it. A change that cannot start within the lock limit (5 s) answers 503 with `committed: false`: nothing changed, and it can be tried again.
- `/team-invite` is outside workspace bootstrap so an invited user can accept a token after signing in, selecting the provisioned organisation and verifying MFA. The token stays in the URL fragment until accepted and is not sent to analytics or request logs.

The pilot workflow and staff API supplement is documented in `docs/pilot-workflow-release.md`. Workspace responses include optional `accessMode` and an opaque `viewerScope` for local filter preferences. Browser storage excludes source rows, request bodies and customer search text. Staff mode keys query state by signed-in user and selected organisation; changing either clears the previous workspace.
- `/pay-by-bank` provides bound sample checkouts, separate authorisation, pending/unknown outcomes, canonical reconciliation and independently reviewed refund evidence. Browser return is never a receipt.
- `/credit-desk` provides synthetic evidence checks, explained rule scores and repayment capacity, immutable versions and separate reasoned lender reviews. A rule score is not a probability of default.
- `/cash-desk` provides an independent sample SME entity, multi-account cash positions, scenario forecasts, accounting drafts, VAT evidence and approved-net-pay funding with separate Finance review. Exports never imply a bank payment or ERP write.
- `/connections` is the purpose-specific sample permission register and live-readiness view. Expiry and revocation block new dependent work; in-flight evidence remains reconcilable. The connected modules use the scoped `GET /v1/connected` and idempotent `POST /v1/connected/actions` contract described in `docs/connected-banking.md`.
- `/` is the landing page (`pages/landing.tsx`): what Valo Pay is and is not, the descriptor and "We never hold money" in its first three lines, the four jobs, how it works, the boundaries and the price, with two ways in: Open the sandbox (`/overview`) and Sign in (`/sign-in`). It is routed outside `WorkspaceProvider`, as are the sign-in pages, so visiting it sends no request to the API and creates no sandbox; the workspace request happens only once someone opens the console. The design rationale is `docs/design/console.md`.
- `/overview` shows the operations overview, accessible sandbox without login, with Sign in to own workspace, and the alerts feed (`getOverview` alerts [{key, severity critical/high/medium/info, title, detail, count, since, linkedRecordId}]: audit_chain_broken, instruction_in_observation_mode, position_drift, unallocated_over_threshold (settings.unallocatedAlertThreshold, default 10), exceptions_overdue, attempts_deferred, notification_cost (settings.notificationCostAlertKobo, default 800 per collection, over the current WAT month's direct debits collected by webhook or settlement line), close_overdue (36 hours), kill_switch_active; NFR-OBS-02). Each daily close freezes the alerts into report.alerts.
- `/customers` and `/customers/:id` with position, the complete timeline including every retry decision (reason, next attempt, the notice it requires, policy version, arm), and the dispute pack as PDF, CSV or JSON.
- `/mandates` (suspend, reinstate, cancel, reissue, remind, notify policy change, apply policy version), `/collections` (due items/attempts), `/reconciliation` (payments/observations/proposals, settlement batches and the REC-09 precision audit limited to the month's seeded sample from reports.operational.precisionAudit, with the false-match rate and its interval), `/exceptions` (filters: all open, high severity, resolved).
- `/policies` includes versioned retry policies and notification templates, comparisons where a previous version is identifiable, and labelled synthetic message previews before review decisions.
- `/reports` daily closes with the REC-07 report chips and the position-rebuild alert, operational measurement, the recovery experiment with the 90% interval and rule checks, the billing statement with receipts by channel, the issued invoices, the adjustments the next invoice will carry, and the Issue invoice dialog.
- `/evidence` prerequisite evidence, commercial commitments, three distinct decisions and gate export.
- `/audit` hash-chain log and verification; the result (valid, entry count, head hash, lender and check time) is shown in a persistent page status. A failed request offers recovery without retaining an old success result.

## Mutations
`listRecords` takes status, search, and for paging `limit` (1–500; omitted returns the whole filtered set, newest first), `offset` and `updatedSince` (ISO timestamp, inclusive, for incremental sync); the response carries items, total (the filtered count) and nextOffset when more rows remain. createRecord and updateRecord for editable kinds. Business actions go to performAction:
- `set_role` data.role (Admin / Operations / Finance / Compliance reviewer / Read-only), **demo personas ONLY**, each is a separate simulated identity; no real permission granted. Like a team change, it waits only for the requests already running in the workspace, later requests wait behind it, and it answers 503 with `committed: false` when it cannot start within 5 s.
- `kill_switch` data.enabled boolean, optional data.policyId, and reason; requires Admin. Cancels scheduled attempts under the switched scope.
- `request_instruction` always blocks: live integration/security gates unmet.
- `mandate_suspend` (active only), `mandate_reinstate` (suspended only), `mandate_cancel` (cancels scheduled attempts), `mandate_reissue` (creates a new mandate; needs data.consentEvidence), `activation_reminder` (pending_activation only; caps 4 transfer_to_activate / 2 hosted_consent, none once consentGiven; refused in quiet hours 21:00–08:00 WAT; logs a notifications record) recordId and reason.
- `submit_policy`, `approve_policy`, `reject_policy`, `new_policy_version` recordId and reason; approval uses different actor and Compliance reviewer role. Same for templates via `submit_template`, `approve_template`. `new_policy_version` numbers the draft one above the highest version of the policy, so two drafts from one version never share a number, and `approve_policy` is refused (409) while another approved version of the same policy (linked by previousVersionId, or sharing its name) carries that number. Templates have no such refusal: `new_template_version` numbers its draft after the template's whole history, and `approve_template` does not check the number.
- `run_reconciliation`, `daily_close` no id. Reconciliation resolves observations to canonical payments, holds suspected duplicates (a payment for an already-paid due item, or the same payer and amount within two minutes), applies the ladder R1 to R5, re-evaluates every settlement batch against its fee schedule and linked statement credit, re-derives instalment statuses that contradict their stored balance (`dueStatusesRepaired`), raises catalogue exceptions with business-day deadlines, evaluates every open obligation under an approved policy and records the decision (RET-03), applies the 6.3 give-up rows (unpaid_final, in_dispute, unknown outcome after 24 hours) and raises notice_not_evidenced when a planned attempt's notice deadline passes without provider acceptance. `daily_close` additionally writes the REC-07 close report on a `closes` record (result.data.closeId, positionAlert, schedule) as a manual close. The scheduled close (REC-01) is not an action: while its scheduler is enabled and running, the API process checks each lender's requested `closeTime` (default 07:00 WAT) with the system actor `System · scheduled close`. Every close, manual or scheduled, moves `settings.nextCloseAt` to the next configured time. `updateSettings` accepts `closeTime` (HH:MM WAT) and `scheduledCloseEnabled`; a changed time or switching the preference on recomputes `nextCloseAt` from now, and an unchanged save leaves a pending missed close pending. The preference does not start the scheduler. A failed scheduled attempt is retried with a growing delay and the close stays pending until one succeeds; any close clears the retry. The scheduler switches off the automatic close of an anonymous sandbox nobody has changed for seven days instead of closing it. `getOverview` carries `closeSchedule`, `closeTime` and legacy `nextClose`, which is empty whenever an automatic run is unavailable.
- `confirm_allocation`, `reject_allocation` recordId=payment ID for proposal, reason; Finance/Admin. Rejecting keeps whatever the payment has already applied elsewhere and records the pair in `rejectedDueItemIds`, so the next close does not propose it again. A proposal that no longer fits what the payment has left, for example after Finance allocated it elsewhere by hand, is withdrawn automatically.
- `manual_allocate` recordId=payment ID, data.dueItemId and data.amountKobo, reason. Refused (409) for a returned payment, and for more than a payment refunded in part still holds. Finance's own allocation to an instalment clears an earlier rejection of that pair.
- `review_allocation` recordId=allocation ID, data.correct boolean, reason; Finance/Admin. `correct=false` supersedes the allocation, reopens the payment and due item (REC-09) and records the pair in `rejectedDueItemIds`, so later closes do not recreate the match. `correct=true` on a match a review had marked wrong applies the same allocation again, or is refused (409) while the payment or instalment no longer allows it; on a match superseded for another reason (a reversal) it records the verdict only. A proposal is refused (409): confirm or reject it instead. RecordDialog always submits checkbox fields as booleans.
- `resolve_exception` recordId and reason, data.resolutionCode from `resolutionCodesFor(exception.data.type)` (Appendix A per type; the generic list only for legacy types); use structured appropriate action first. For unknown_outcome the resolution is the outcome the provider confirmed and becomes the attempt's status: resolved_failed makes it failed with the optional data.confirmedFailureCode (a `failureCodeList` code other than TIMEOUT_UNKNOWN; without one, UNKNOWN, which is never retried), resolved_succeeded makes it succeeded, provider_confirmed_no_debit makes it cancelled; `attempt.data.outcomeConfirmation` keeps what it showed before, and the instalment stops waiting as in flight. Resolutions recorded before this rule are applied by the next close (`attemptOutcomesConfirmed`).
- `record_refund` recordId=payment ID data.reference external refund reference, reason. Only records external action, never moves funds. A refund returns what the payment has not applied: with nothing applied the payment becomes `returned`; with money applied, such as an overpayment whose excess went back, that money stays on its instalments and the payment becomes `allocated`. Either way its proposals are withdrawn and nothing it has left can be allocated or counted as credit, until an allocation of the money that stayed is superseded. The amount returned is recorded as data.refundedKobo and given as result.data.refundedKobo and in the message (for example NGN 5,000.00); billing and the uplift report keep the collection on the money that stayed. It is refused (409) for a reversed payment, a payment already refunded (in full or in part) and a payment whose money is all applied, which has nothing unapplied to refund.
- `simulate_failure` recordId=due item, data.failureCode from `failureCodeList` (aliases such as ACCOUNT_CLOSED are normalised); TIMEOUT_UNKNOWN creates an attempt with status unknown, which blocks retries until resolved. Not a real debit.
- `backtest_policy` recordId=policy -> result.data.decisions list of {dueItemId,attemptId,decision,rule,reason,nextAt,policyId,policyVersion,experimentArm,inputs,noticeRequired}; decisions follow the TRD 6.3 table in order (settled, kill switch, in-flight, non-retryable, ceiling, restricted once, approval, floor and merchant minimum, mandate, consent, holdout, ownership, mode, plan). A plan stands with the failed-debit notice required 24 hours before the slot; only a deadline that passes without provider acceptance defers the attempt (rule notice_not_evidenced). Backtest decisions are returned, never recorded; explicitly not a recovery estimate.
- `preregister_experiment` recordId=experiment; freezes parameters, computes sample.
- `hand_back` reason; restores all Valo ownership to the cutover contract's fallbackOwner (default lms), cancels scheduled attempts, records checklist.
- `verify_audit` result.data.valid, count, headHash.
- `issue_invoice` data.period optional (YYYY-MM, default the previous month), reason; Admin/Finance. Periods are calendar months in West Africa Time: a collection at 00:30 WAT on 1 January belongs to January, and the default is the previous WAT month. Issues the immutable invoice for the period: the contracted licence, one usage line per billable collection not billed before and observed by the period end (so a collection withheld inside its reversal window is billed on the next invoice), the design-partner discount on the licence and this invoice's usage lines, the BIL-07 adjustment lines for collections billed earlier, each at the rate of the invoice that first billed its collection, the gated recovery fee, VAT on the net. Refuses a second invoice for a period, an out-of-order period, a future period and the current month, which can be invoiced from 00:00 WAT on the 1st of the next month (400). result.data invoiceId, period, totals.
- `notify_policy_change` recordId=mandate, data.policyId (approved version of the mandate's policy), reason; Admin/Operations; refused in quiet hours. Records a simulated `policy_change` notification, which is not provider-accepted evidence.
- `apply_policy_version` recordId=mandate, data.policyId (approved version of the same policy), optional data.noticeId, data.consentEvidence when settings.policyChangeRequiresConsent is true, reason; Admin/Operations. RET-07: needs a policy_change notice with provider acceptance (synthetic notices never count), moves the mandate and its consent record to the version, appends policyVersionHistory. Until then the engine keeps applying the consented version and refuses another with rule policy_version_not_consented.
- `mark_pack_used` always refuses to count synthetic exports as real cases.

Template review also supports `reject_template` (Compliance reviewer returns a submitted message with a reason) and `new_template_version` (Admin creates a draft linked to an approved predecessor). Approved wording and review metadata remain immutable. Supported placeholders are validated using the shared `templatePlaceholders` and `templateTextProblems` definitions; unknown or malformed placeholders cannot be approved.

Record updates can carry `expectedUpdatedAt`; Settings exposes a content revision and accepts `expectedRevision`. The console submits the version loaded when editing began. A stale version returns 409 without changing the record. Action reviews can also carry the record version. Stable `Idempotency-Key` values accompany logical writes, including retry after an uncertain response; a replay is checked before the old version is rejected. A refusal that leaves the request's journal entry cancelled says `operation: "cancelled"`, as does any later request with the same key. A new intentional action receives a new key.

Modified dialogs, import drafts and Settings participate in the unsaved-change guard. Staying keeps the current input. Choosing to discard permits the requested navigation or close. No customer draft is written to browser persistent storage.

## Imports & exports

`/exports` lists saved evidence jobs for the selected lender, including processing stage, recovery status, permitted retry and private download. Stalled-export alerts lead here. The Sources business-date declaration and Import batches correction workbench preserve original evidence and require named Finance review for accepted source gaps and committed-record amendments.

The CSV console requires an explicit source amount unit for monetary record types. Naira accepts at most two decimal places (including correctly grouped quoted commas); kobo requires whole digits. Conversion uses decimal integer arithmetic and rejects negative, ambiguous or unsafe amounts. The server performs the same conversion for preview and commit. The first ten parsed rows include the converted naira amount, and changing the unit or mapping invalidates the checked preview. Existing API clients that omit `amountUnit` retain integer-kobo semantics. The generic source header `amount` maps to the canonical amount field; custom headers use the existing mapping control. Sample files use the selected unit. Error-free all-or-nothing validation remains required.

Imports expose source columns, a bounded parsed row preview and the skipped count alongside validation/import totals. Mapping remains explicit, and a changed file, mapping or kind requires a fresh preview. Downloaded errors escape spreadsheet formula prefixes. Files remain synthetic-only, up to 500 rows and 1.5 MB, with all-or-nothing commits.
`importRecords`: kind customers/mandates/due-items/attempts/observations, csv text, syntheticOnly=true, commit=false for preview; commit=true to persist. Show errors per row. Header contract matches record properties plus data fields above. Default download a sample CSV for chosen kind. No real data!
`createExport`: kind (record kind / gate-pack / dispute-pack (alias customer-pack, needs customerId) / billing), format csv/json/pdf => saved job id, status and downloadUrl. It queues metadata and returns before file generation; checksum and generatedAt are available only when ready. The client uses a stable Idempotency-Key for an unchanged uncertain submission. `getExportJob` polls `/v1/exports/{id}` with merchantId; `retryExportJob` posts to `/v1/exports/{id}/retry`, retaining the same job and object key. Status, retry and download always re-authorise the lender. Downloading an unfinished job returns 409. Old ready exports and older immediate-result clients remain supported.

The shared export control polls selected queued/running jobs every 1.5 seconds, reloads the latest five matching jobs, shows failures with a retry action and leaves a persistent download link plus checksum when ready. Pending jobs survive page changes and process restarts. Late mutation responses from another lender/page are ignored. A status-read failure does not assert that generation failed and offers an explicit refresh. Two worker slots per process, a five-minute claim lease (a worker that stops returns its jobs to the queue at once; the lease covers a crash), ten unfinished jobs per lender and twenty-candidate polling keep work bounded. Every storage call is aborted after sixty seconds. Sources and files have a 32 MB limit. Uploads use a stable private key with a create-only precondition; crash recovery verifies ownership metadata, byte length and SHA-256 before adopting an already-uploaded artifact. No rendering/upload occurs inside a database transaction. Queue/start/release/ready/failure/retry events participate in the audit trail, and only ready packs count in operational.packsGenerated (MEA-01).

The dispute pack (AUD-02) is a paginated PDF with a one-page summary, the full timeline oldest first and the policy, template and cutover versions as they applied at each event (AUD-06); CSV is one row per timeline event and JSON is the whole pack. The gate pack carries the RET-06 uplift report with the pre-registered rule and its result, the operational metrics and the billing statement (MEA-02). - `GET /v1/queues/{queue}` accepts literal `q` search in addition to the existing view, owner, type, target, limit and offset. Totals and priority counts reflect the complete searched queue.
- `GET /v1/reconciliation/{queue}` accepts proposals, duplicates, payments, observations, audit or batches; it returns items, related records, total, offset and asOf. An optional dueItem restricts linked review to that lender's instalment; an unavailable focus returns an empty result. Audit adds complete sample metadata.
- `GET /v1/close-history` returns compact items, total, allTotal and first/latest summaries across the complete inclusive WAT date range. Invalid or reversed dates return 400.
- `GET /v1/close-history/{id}` fetches one lender-scoped close with its full evidence; another lender's close returns 404.
- `GET /v1/reports?includeCloses=false` omits the historical close array while retaining all operational, billing and experiment measures. Omitting the option preserves the existing response contract.

All paged reads clamp deleted last pages, cap each page at 100 and remain inside the scoped repository. These read models never create writable partial snapshots. Desktop and phone Chromium tests use `artifacts/valo-pay/e2e`; database parity and isolation tests use `artifacts/api-server/tests/console-read-models.integration.test.ts`.

## Provider ingress

The console never calls `POST /v1/providers/paystack/{connectionId}/events`: it is the webhook address an operator registers with a Paystack test account (`docs/paystack.md`). It is off unless the host sets `VALOPAY_PAYSTACK_INGRESS=test`, and it checks each delivery's signature on its raw bytes before it locks or reads a lender, so a forged or tampered delivery gets 401 and nothing else. What it saves appears on `/sources`, in the Paystack test connection panel, through `GET /v1/sources` (`paystack.events`), as test-mode evidence only.

## Search and history paging

The priority queues distinguish an unmatched search from an empty lender queue. Clearing the search keeps the status, owner and type filters. Reconciliation exposes the same explicit search form across its views and applies customer/payment/instalment reference matching before server counts and pages. Its monthly precision sample measures remain unfiltered.

The customer page reads `/api/v1/customers/{id}/history`. Events, mandates, instalments and payments have independent bounded pages, full counts and corrected offsets. The position is calculated from every related record in the same read transaction. Selected-record links may fetch one additional record, scoped to that customer and lender. Exports retain their full-history contract. The older timeline endpoint remains available to existing clients. No partial history response is a writable domain snapshot.
