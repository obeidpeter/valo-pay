# Valo Pay console contract

All data is a persistent, isolated **synthetic sandbox**. No payment or SMS is actually sent. No live data upload is permitted. Use British spelling, NGN (kobo / 100) and Africa/Lagos dates. Always say “We never hold money”. Keep a visible “Sandbox · synthetic data” label and current Observation mode. No claims of compliance, live success, or gate passes from seed data.

## Records
API `ValopayRecord`: id, merchantId, kind, name, status, reference, amountKobo, customerId, createdAt, updatedAt, data (metadata).

Every status list, enum, failure code, exception type and resolution code below is defined once in `lib/valopay-schema` (`@workspace/valopay-schema`) and consumed by the API validator and the console. Never retype a value from this document; import it.

Kinds and data fields:
- customers: name, reference, status active; data bankName, accountMasked, phoneMasked, consentProvenance.
Every kind's data fields, including the ones the platform sets, are declared with their types in `lib/valopay-schema/src/records.ts` (`recordDataSchemas`, one schema per kind; `RecordDataOf<K>` is the inferred type). The API reads and writes record data through those types (`TypedRecord<K>` from `recordsOf`, `findRecord` and `makeRecord`), so the schema is the source and the summary below follows it.

- mandates: customerId, amountKobo=limit, reference provider ref, status per the TRD 4.2 machine (draft/submitted/pending_activation/active/suspended/expired/cancelled/failed; `mandateTransitions`); data workflow (`activationWorkflows`), frequency (`mandateFrequencies`), activationDeadline, consentEvidence, consentGaps, consentGiven, policyId, origin (created/imported/reissued), reminderCount, reissuedFrom. A PATCH may only follow the machine and never into cancelled or suspended; use the actions. RET-07: data.consentPolicyId, consentPolicyVersion and consentPolicySummary are pinned by the validator from data.policyId when the mandate is created (and by mandate_reissue, which accepts an optional data.policyId of an approved version of the same policy); they are server-owned, a direct policyId change is refused, and policyVersionHistory records each move made by apply_policy_version.
- due-items: customerId, reference, amountKobo, status scheduled/in_collection/partially_paid/paid/unpaid_final/in_dispute/cancelled/closed (derived; never set by PATCH); data dueDate, mandateId, owner (`executionOwners`; the TRD spelling `valo` is accepted and stored as `valopay`), outstandingKobo, overrideReason (needed between ₦5,000 and the merchant minimum from settings), amendedAt (set when amount or dueDate change), experimentId/experimentArm/firstFailureAt (immutable once assigned).
- attempts: customerId, amountKobo, status scheduled/sent/succeeded/failed/unknown/cancelled/reversed; data dueItemId, number (across every source), source=external, failureCode (normalised to the TRD 4.4 catalogue `failureCodes`; unmapped codes become UNKNOWN with rawFailureCode kept), occurredAt, providerReference (the debit reference the ladder's R1 matches on), noticeId.
- observations: customerId, reference canonical provider reference, amountKobo, status resolved/unresolved; data source (`observationSources`), dueItemId (a strong link the ladder treats as R1 when the amount matches), narration, paymentId, resolutionKey, batchReference, feeKobo, grossAmountKobo, occurredAt, reversed, provider=Sandbox Rail.
- payments: customerId, reference, amountKobo; status unallocated/proposed/allocated/partial/overpaid/possible_duplicate; data channel, observedAt, and the four independent dimensions collectionStatus (received/succeeded/failed/unknown), settlementStatus (unsettled/settled/variance), reversalStatus (none/reversed), refundStatus (none/requested/refunded); dueItemId, allocatedKobo, explanation. Legacy spellings not_reversed/not_refunded are read as none.
- allocations: customerId, amountKobo, status confirmed/proposed/superseded; data paymentId, dueItemId, rule, confidence, explanation, reviewed (correct/wrong), automatic.
- settlement-batches: name, reference=batchReference (the validator copies one to the other), status pending/reconciled/variance (set by reconciliation); data provider, batchReference, grossKobo, feeKobo (stated by the provider), expectedFeeKobo (from the per-provider `providerFeeSchedule` in settings, default 0.5% capped at ₦1,000), feeVarianceKobo, netKobo, lineObservationIds, linePaymentIds. Statement batch credits never become customer payments.
- exceptions: customerId, amountKobo, status open/assigned/in_progress/resolved/closed (`exceptionTransitions`; resolved only through resolve_exception); data type (Appendix A `exceptionCatalogue`: activation_expired, unallocated_payment, suspected_duplicate, overpayment, unpaid_after_final_attempt, mandate_limit_exceeded, settlement_variance, provider_status_mismatch, customer_dispute, unknown_outcome, notice_not_evidenced, ownership_conflict, imported_consent_gap, mapping_needed), severity, owner and dueBy (defaulted from the catalogue: owner per type, SLA in business days), resolutionCode (from `resolutionCodesFor(type)`), notes, linkedRecordId.
- policies: status draft/submitted/approved/rejected; data version, maxAttempts (<=4), spacingHours (>=24), firstNoticeHours (>=24), retryNoticeHours (>=24), partialAllowed=false, author, reviewer, complianceMapping (`policyGuardrails`). Approved versions immutable; a policy-version kill switch is therefore stored in settings.policyKillSwitches.
- templates: status draft/submitted/approved; data purpose, text, author, reviewer, version. Text requires {{amount}}, {{date}}, {{merchant}}, {{contact}}.
- notifications: status simulated/blocked; data purpose, channel, renderedText, acceptedAt, deliveredAt, costKobo.
- cutovers: status draft/ready/handed_back; data inventory, incumbentDisabled, externalAttemptsImported, dualRunComplete, accountableUser, fallbackOwner, confirmation. `ready` needs all three step flags plus accountableUser and confirmation (DEB-11); only then may a due item carry owner valopay. hand_back reverts to fallbackOwner. SIMULATION only.
- audit: immutable name=action, data actor, previousHash, hash, objectId, summary.
- closes: immutable daily close evidence; data summary, metrics, closedAt, period {from, to} (from the previous close), positionAlert, schedule {trigger scheduled/manual (`closeTriggers`), scheduledFor (the pending scheduled instant this close covered, else null), delayMinutes, late (more than 30 minutes after that instant), nextAt} (REC-01), and report (REC-07): openingUnallocated {count, kobo}, observations {received, bySource {received, resolved, unresolved, paymentsResolvedTo, batchesResolvedTo}, paymentsResolvedTo}, allocatedByRule {rule: {count, kobo, automatic}}, allocated, proposed, unallocated {count, kobo, olderThan24Hours}, possibleDuplicates, variances {count, feeVarianceKobo, batches}, exceptions {opened {count, byType}, closed {count, byType}, openAtClose, overdueAtClose}, retryDecisions, customerPositionsChanged [{customerId, customerName, before, after}], positionRebuild {mismatches, alert} (REC-05), reconciliation.
- retry-decisions: immutable, written by every close for each open obligation under an approved policy (RET-03); never created through the record API. data dueItemId, attemptId, decision (`retryDecisionKinds`), rule (TRD 6.3 row), reason, policyId, policyVersion, nextAt, evaluatedAt, experimentArm (RET-05), inputs {code, rawCode, attemptNumber, ceiling, owner, mode, attemptAt, spacingHours, leadHours, window, calendar {earliestAt, rolledForward, weekendDaysSkipped, holidaysApplied}, noticeEvidence}, noticeRequired {purpose, leadHours, requiredBy, noticeId, acceptedAt, evidenced}, fingerprint, previousDecisionId. An unchanged decision at a later close is not repeated. They carry customerId, so the customer timeline shows every decision (AUD-01).
- exports: generated download metadata; data checksum (SHA-256 of the file), kind, format, usedInRealCase=false, byteLength, generationMs, and for packs customerReference and events.
- invoices: immutable issued invoices (BIL-04), one per period in period order, written only by `issue_invoice`; data period, periodEnd, issuedAt, issuedBy, sequence, terms, licence {kobo, volumeTier, tierMismatch}, usageLines [{paymentId, paymentReference, allocatedKobo, feeKobo, allocationIds}], collectionsCounted, designPartnerDiscount {rate, kobo}, adjustments [{reason (`adjustmentReasons`: reversal, refund, confirmed_duplicate, wrong_allocation, re_allocation), paymentId, paymentReference, originalInvoiceId, originalInvoiceReference, kobo (negative credit, positive debit), billedFeeKobo, currentFeeKobo, allocationIds, explanation}] (BIL-07), recoveryFee {enabled, lines, kobo, note} (BIL-03, gated on settings.recoveryFeeEnabled and settings.recoveryFeeDecision="proven", billed only after the 30-day window closes), subtotals, totals {netKobo, vatBps, vatKobo, totalKobo, creditNote}, statement, disputeRoute. amountKobo is the total, floored at zero for a credit note.
- commercial: name prospect; data monthlyVolume, averageTicketKobo, implementationKobo, licenceKobo, usageBps=30, usageCapKobo=15000, signed, signedFullPriceTerms, effectiveDate, startCondition, conversationComplete, designPartner. Only list-price entries qualify; synthetic evidence does NOT pass real Test3.
- reviews: fortnightly review notes data confirmedJobs, note, reviewer, reviewedAt. Synthetic does NOT pass real Test5.
- evidence: status pending/recorded; data gateId (P1…P5, F1…F4, T1b, T2; what the gate register matches on), reference, notes. Evidence registers are not verification.
- experiments: draft/preregistered/closed; data baselineRate, holdoutShare (0.1–0.5), minPerArm, analysisDate, enrolmentClose, seed, policyId.
- costs: name infrastructure/support/notifications; amountKobo, data period.
- calendar: name holiday, data date.
- members: read-only demo role identities.

## Pages
- `/` is the landing page (`pages/landing.tsx`): what Valo Pay is and is not, the descriptor and "We never hold money" in its first three lines, the four jobs, how it works, the boundaries and the price, with two ways in: Open the sandbox (`/overview`) and Sign in (`/sign-in`). It is routed outside `WorkspaceProvider`, as are the sign-in pages, so visiting it sends no request to the API and creates no sandbox; the workspace request happens only once someone opens the console. The design rationale is `docs/design/landing-and-login.md`.
- `/overview` shows the operations overview, accessible sandbox without login, with Sign in to own workspace, and the alerts feed (`getOverview` alerts [{key, severity critical/high/medium/info, title, detail, count, since, linkedRecordId}]: audit_chain_broken, instruction_in_observation_mode, position_drift, unallocated_over_threshold (settings.unallocatedAlertThreshold, default 10), exceptions_overdue, attempts_deferred, notification_cost (settings.notificationCostAlertKobo, default 800 per collection), close_overdue (36 hours), kill_switch_active; NFR-OBS-02). Each daily close freezes the alerts into report.alerts.
- `/customers` and `/customers/:id` with position, the complete timeline including every retry decision (reason, next attempt, the notice it requires, policy version, arm), and the dispute pack as PDF, CSV or JSON.
- `/mandates` (suspend, reinstate, cancel, reissue, remind, notify policy change, apply policy version), `/collections` (due items/attempts), `/reconciliation` (payments/observations/proposals, settlement batches and the REC-09 precision audit limited to the month's seeded sample from reports.operational.precisionAudit, with the false-match rate and its interval), `/exceptions` (filters: all open, high severity, resolved).
- `/policies` includes versioned retry policies and notification templates.
- `/reports` daily closes with the REC-07 report chips and the position-rebuild alert, operational measurement, the recovery experiment with the 90% interval and rule checks, the billing statement with receipts by channel, the issued invoices, the adjustments the next invoice will carry, and the Issue invoice dialog.
- `/evidence` prerequisite evidence, commercial commitments, three distinct decisions and gate export.
- `/audit` hash-chain log and verification; the verify result (valid, entry count, head hash) is shown on the page and as a toast, never an alert.
- `/settings` roles, access matrix, providers (not connected), calendar, execution settings (window, authorisation mode, contact route, policyChangeRequiresConsent, unallocatedAlertThreshold, notificationCostAlertKobo, closeTime as HH:MM WAT with scheduledCloseEnabled, shown with the next scheduled close from the server-owned settings.nextCloseAt), cutover and hand-back.
- `/sign-in/*?`, `/sign-up/*?` (`pages/sign-in.tsx`) show Clerk's form themed to the console's tokens beside what signing in changes, with a link to the sandbox for anyone without an account; after sign-in Clerk redirects to `/overview`. On a local host with no `VITE_CLERK_PUBLISHABLE_KEY` the console runs without Clerk (`lib/auth.tsx`): sign-in links inside the console are hidden, and these routes say that sign-in is not available on this host, with the reason and a link to the sandbox, instead of a form that could not work. Elsewhere workspace loading waits at most five seconds for Clerk.
- Any other address shows the not-found page (`pages/not-found.tsx`) outside `WorkspaceProvider`: `App.tsx` keeps one list of the console's addresses and mounts the console only for those, so reaching a mistyped address creates no sandbox. The page names the address it looked for, says nothing was changed, and links to `/overview` and `/`. A customer address whose record the current lender does not have (`/customers/:id`, API 404) stays inside the console with the sidebar and shows the same notice with the reference and a link back to `/customers`; its title is `Customer not found · Valo Pay`.
- A page that throws is caught by an error boundary inside the console layout (`components/error-boundary.tsx`), so the sidebar and the lender selector remain. The notice (`role="alert"`, title `Page error · Valo Pay`) says the page stopped working, that an error on a page changes no record and the audit log has the result of any action just confirmed, shows the time and the address for a report, and offers Try again and a plain link to `/overview`; the error's message is shown in development only. Boundaries outside the console and at the root show the same notice in the public frame, and navigating to another address clears a caught error. The not-found states and the error notice share `components/notice.tsx`.
- When the workspace request itself fails, the console shows the notice in the public frame instead of the pages (`components/workspace-unavailable.tsx`, `role="alert"`, title `Workspace not loaded · Valo Pay`): for a 429 the API's own message (a new sandbox refused by the per-address limit, or the request limit), for no answer that the service could not be reached, for a 5xx that the service hit an error with the time for a report and without the body's wording, otherwise the API's message; always that no lender data has been changed, with Try again (which shows its progress), Back to the start and, where sign-in is available, Sign in. While the workspace loads, the layout shows a `Loading your workspace…` status in the page area instead of the pages.

## Mutations
`listRecords` takes status, search, and for paging `limit` (1–500; omitted returns the whole filtered set, newest first), `offset` and `updatedSince` (ISO timestamp, inclusive, for incremental sync); the response carries items, total (the filtered count) and nextOffset when more rows remain. createRecord and updateRecord for editable kinds. Business actions go to performAction:
- `set_role` data.role (Admin / Operations / Finance / Compliance reviewer / Read-only), **demo personas ONLY**, each is a separate simulated identity; no real permission granted.
- `kill_switch` data.enabled boolean, optional data.policyId, and reason; requires Admin. Cancels scheduled attempts under the switched scope.
- `request_instruction` always blocks: live integration/security gates unmet.
- `mandate_suspend` (active only), `mandate_reinstate` (suspended only), `mandate_cancel` (cancels scheduled attempts), `mandate_reissue` (creates a new mandate; needs data.consentEvidence), `activation_reminder` (pending_activation only; caps 4 transfer_to_activate / 2 hosted_consent, none once consentGiven; refused in quiet hours 21:00–08:00 WAT; logs a notifications record) recordId and reason.
- `submit_policy`, `approve_policy`, `reject_policy`, `new_policy_version` recordId and reason; approval uses different actor and Compliance reviewer role. Same for templates via `submit_template`, `approve_template`.
- `run_reconciliation`, `daily_close` no id. Reconciliation resolves observations to canonical payments, holds suspected duplicates (a payment for an already-paid due item, or the same payer and amount within two minutes), applies the ladder R1 to R5, checks settlement fees against the schedule, raises catalogue exceptions with business-day deadlines, evaluates every open obligation under an approved policy and records the decision (RET-03), applies the 6.3 give-up rows (unpaid_final, in_dispute, unknown outcome after 24 hours) and raises notice_not_evidenced when a planned attempt's notice deadline passes without provider acceptance. `daily_close` additionally writes the REC-07 close report on a `closes` record (result.data.closeId, positionAlert, schedule) as a manual close. The scheduled close (REC-01) is not an action: the API process runs it at each lender's `closeTime` (default 07:00 WAT) with the system actor `System · scheduled close`, and every close, manual or scheduled, moves `settings.nextCloseAt` to the next configured time. `updateSettings` accepts `closeTime` (HH:MM WAT) and `scheduledCloseEnabled`; a changed time or switching the automatic close on recomputes `nextCloseAt` from now, and an unchanged save leaves a pending missed close pending. `getOverview` carries `nextClose` (empty when the automatic close is off) and `closeTime`.
- `confirm_allocation`, `reject_allocation` recordId=payment ID for proposal, reason; Finance/Admin.
- `manual_allocate` recordId=payment ID, data.dueItemId and data.amountKobo, reason.
- `review_allocation` recordId=allocation ID, data.correct boolean, reason; Finance/Admin. `correct=false` supersedes the allocation and reopens the payment and due item (REC-09). RecordDialog always submits checkbox fields as booleans.
- `resolve_exception` recordId and reason, data.resolutionCode from `resolutionCodesFor(exception.data.type)` (Appendix A per type; the generic list only for legacy types); use structured appropriate action first.
- `record_refund` recordId=payment ID data.reference external refund reference, reason. Only records external action, never moves funds.
- `simulate_failure` recordId=due item, data.failureCode from `failureCodeList` (aliases such as ACCOUNT_CLOSED are normalised); TIMEOUT_UNKNOWN creates an attempt with status unknown, which blocks retries until resolved. Not a real debit.
- `backtest_policy` recordId=policy -> result.data.decisions list of {dueItemId,attemptId,decision,rule,reason,nextAt,policyId,policyVersion,experimentArm,inputs,noticeRequired}; decisions follow the TRD 6.3 table in order (settled, kill switch, in-flight, non-retryable, ceiling, restricted once, approval, floor and merchant minimum, mandate, consent, holdout, ownership, mode, plan). A plan stands with the failed-debit notice required 24 hours before the slot; only a deadline that passes without provider acceptance defers the attempt (rule notice_not_evidenced). Backtest decisions are returned, never recorded; explicitly not a recovery estimate.
- `preregister_experiment` recordId=experiment; freezes parameters, computes sample.
- `hand_back` reason; restores all Valo ownership to the cutover contract's fallbackOwner (default lms), cancels scheduled attempts, records checklist.
- `verify_audit` result.data.valid, count, headHash.
- `issue_invoice` data.period optional (YYYY-MM, default the previous month), reason; Admin/Finance. Issues the immutable invoice for the period: the contracted licence, one usage line per billable collection not billed before and observed by the period end (so a collection withheld inside its reversal window is billed on the next invoice), the design-partner discount, the BIL-07 adjustment lines for collections billed earlier, the gated recovery fee, VAT on the net. Refuses a second invoice for a period, an out-of-order period and a future period. result.data invoiceId, period, totals.
- `notify_policy_change` recordId=mandate, data.policyId (approved version of the mandate's policy), reason; Admin/Operations; refused in quiet hours. Records a simulated `policy_change` notification, which is not provider-accepted evidence.
- `apply_policy_version` recordId=mandate, data.policyId (approved version of the same policy), optional data.noticeId, data.consentEvidence when settings.policyChangeRequiresConsent is true, reason; Admin/Operations. RET-07: needs a policy_change notice with provider acceptance (synthetic notices never count), moves the mandate and its consent record to the version, appends policyVersionHistory. Until then the engine keeps applying the consented version and refuses another with rule policy_version_not_consented.
- `mark_pack_used` always refuses to count synthetic exports as real cases.

## Imports & exports
`importRecords`: kind customers/mandates/due-items/attempts/observations, csv text, syntheticOnly=true, commit=false for preview; commit=true to persist. Show errors per row. Header contract matches record properties plus data fields above. Default download a sample CSV for chosen kind. No real data!
`createExport`: kind (record kind / gate-pack / dispute-pack (alias customer-pack, needs customerId) / billing), format csv/json/pdf => downloadUrl to same API, checksum (SHA-256), generatedAt. The dispute pack (AUD-02) is a paginated PDF with a one-page summary, the full timeline oldest first and the policy, template and cutover versions as they applied at each event (AUD-06); CSV is one row per timeline event and JSON is the whole pack. The gate pack carries the RET-06 uplift report with the pre-registered rule and its result, the operational metrics and the billing statement (MEA-02). Download or link returned URL; a toast shows the checksum. Exports audit automatically and are counted in operational.packsGenerated (MEA-01). No persistent uploaded files in this build; CSV parsed then discarded; reports rebuilt from immutable snapshot metadata.
`getReports`: metrics; billing (integer totals, item lines, billableChannels [direct_debit], channelBreakdown {channel: {count, kobo, billable}}, withheldInsideReversalWindow, usageFeeKobo, vatBps, invoices [{id, reference, period, collectionsCounted, adjustmentCount, adjustmentsKobo, netKobo, vatKobo, totalKobo, creditNote}], nextInvoicePeriod, pendingAdjustments (the BIL-07 lines the next invoice will carry), pendingAdjustmentsKobo, recoveryFee note; BIL-01 counts only succeeded direct-debit attempts that are settled, unreversed and past the provider reversal window, settings.providerReversalWindowDays[provider] or reversalWindowDays); experiment (results per experiment: engine and holdout {enrolled, mature, recoveryByValue, recoveryByCount, varianceByValue, varianceByCount}, differenceByValue, differenceByCount, confidenceInterval90 {low, high, standardError} from the ratio-estimator variance, confidenceInterval90ByCount, checks {effectAtLeastEightPoints, intervalExcludesZero, sampleMet, analysisDateReached}, result proven/not_proven, reason; result at the top is proven only when every experiment is), operational (closeSchedule {time, enabled, nextAt, missed, overdueMinutes, lateAfterMinutes, lastAt, lastTrigger} for REC-01; liveDays and liveSince from the first daily close, fortnightlyStaffConfirmed, latestReviewAt and reviewCadenceMet from `reviews` records where a named reviewer confirmed all four jobs (MEA-05), test5 {liveDays, liveDaysMet, overdueShareAtMonthEnds [{month, open, overdue, share}] from the last close of each completed month, packsGenerated, realCasesUsed, requiredRealCases}, precisionAudit {month, population, sampleSize, requiredSample, reviewed, wrong, falseMatchRate, interval (95% Wilson), complete, sampledAllocationIds, seed} (REC-09: a seeded sample of at least 200 of the last completed month's automatic certain allocations, or all of them, keyed on data.confirmedAt), falseMatchRate, falseMatchInterval, requiredAuditSample, packsGenerated, disputePacksGenerated, realCasesUsed, timeToClose {month, days, closeId}, unallocatedOlderThan24Hours, all synthetic), closes. billing.unitEconomics (MEA-03): successfulCollections, usageFeeKobo, licenceKobo, recurringKobo, variableCostKobo from `costs` records for the period (name infrastructure/support/notifications, data.period) or the plan's NGN 15 per collection when none are recorded (estimated=true), costPerCollectionKobo, grossMargin, annualisedRecurringRevenueKobo (licence and usage only), checks {costPerCollectionWithinPlan, marginWithinPlan}.
`getGates`: prerequisites list and independent decisions always unproven on demo. limitations enumerates external missing requirements.

Use every provided hook, loading/error states and query invalidation. Main agent builds API concurrently; no hardcoded operational data in client.

Console tests live in `artifacts/valo-pay/tests` (`pnpm --filter @workspace/valopay run test`): the real pages rendered in jsdom against `tests/fake-api.ts`, an in-memory API that serves these routes from seeded lender state with the API's domain code and validates every response against the generated zod contract. Add a test there when a page's behaviour changes.
