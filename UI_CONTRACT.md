# Valo Pay Django template contract

This app deliberately uses Django templates, HTMX and CSS, NOT React, as explicitly required by the user's technical document. Parent owns Python backend. Design owns templates/ and static/ only. No API hooks are needed: forms are server rendered with CSRF. All routes below have trailing slashes. Use normal HTML navigation and forms; optional HTMX progressive enhancement. Do not build charts; numerical summaries are sufficient.

Every page receives: page (today/customers/collections/payments/reviews/reports/settings/credit/cash), title, org (name, retry_preset, receipts), today, actor (name, role), members (id,name,role), messages (Django messages), open_review_count. All money attributes ending _display are formatted naira strings INCLUDING ₦. All customer names and data are sample data. App is a public demo with session-isolated organisation data; choosing a team member ("Acting as") is NOT authentication. Always show "Demo · Sample data only · No real payments". No sign-in pretend functionality.

All wording follows docs/content/content-guide.md. State meanings shown next to TRD labels come from core/content.py (CONSENT, PAYMENT_REQUEST, REVIEW_KIND, ROLE, RETRY_FOR_CUSTOMER); change them there, not in templates. core/tests/test_copy.py checks rendered wording, page titles, labels and link names.

Shared navigation exactly Today / Customers / Collections / Pay-by-bank / Reviews / Reports. Settings via account area. Credit Desk and Cash Desk are separate preview links (/credit/ and /cash/), not live products.

Templates to create:
- base.html: shared shell, {% block content %}, static /static/valo.css, local scripts /static/valo.js; messages (role=status); a visually hidden live region #live that valo.js uses to announce copy results. Page title is "{title} · Valo Pay": name the record or task.
- standalone.html: shell without navigation for start.html and the error pages (403.html, 404.html, 500.html, 403_csrf.html). 500.html renders without a request context, so it must not use context variables.
- today.html: metrics dict due_display, due_kobo, due_count, collected_display, collected_kobo, confirmed_count, month_start, failed_count, review_count, held_count, active_consents, loan_count, customer_count; recent_payments (Payment list); urgent_reviews (Review list); instalments list due today; activity (Audit list).
- customers.html: customers list, q/filter, filtered (true when a search or filter is applied, for the empty state and count wording); GET search q; filters overdue/hold/no-consent (no loan with Active consent); add /customers/new/ and import /import/.
- customer_form.html: form (Django form via form.as_p), customer optional. POST current URL. Fields name,email,phone,external_id,loan_id,product,amount (naira decimal),due_date,instalment_count.
- customer_detail.html: customer (id,name,email,phone,external_id), loans (list; a customer can have several; each has id,reference,product,status,on_hold,consent_status,consent_meaning,consent_max_display,consent_expiry,consent_token,consent_link_expires,hold_reason,unknown_instalments and instalments.all in sequence order), payments, reviews, activity. Edit /customers/<id>/edit/ (?loan=<id> picks the loan). Actions per loan POST /loans/<id>/action/ with action=consent or withdraw or hold or release or close, reason required for withdraw/hold/release/close. Consent shows a copyable link /consent/<token>/ only while consent_status is Requested. Requests /payments/new/?instalment=<id> only where instalment.requestable. History /exports/customer/?customer=<id>. Schedule editing is not available in the demo (TRD FR-C1.4 requires versioned changes); say so, do not pretend.
- import.html: form with textarea name=csv_data, CSV file input may populate textarea via JS; POST action=validate or commit. csv_data string persisted in escaped hidden textarea after validation; errors list strings ("Row {n}, {column}: {problem and fix}"), preview list dicts (customer_id,name,loan_id,amount,due_date), validated bool, row_count. Template /exports/template/. CSV fields customer_id,name,email,phone,loan_id,product,amount,due_date (one row per instalment). Validation all-or-nothing.
- collections.html: instalments list, q, filter (upcoming/in-progress/failed/confirmed/hold); GET filters/search. Each instalment has id, loan (customer,reference,on_hold,consent_status), due_date, amount_display, paid_display, outstanding_display, status, requestable. No run real debit button.
- payments.html: payments list, requests list, filter, q. /payments/new/. Request fields id,reference,customer_name,amount_display,status,status_meaning,expires_at,token. POST /payments/<id>/cancel/. Payment fields id,reference,customer_name,amount_display,status,source,paid_at,instalment; refund link /refunds/<id>/new/.
- request_form.html: form.as_p (instalment dropdown, amount naira, expiry_hours 1..168); POST; confirmation checkbox name=confirmed required. Explain that creating a request sends nothing and moves no money; the person shares the payment link. On saved redirected /payments/<id>/ with request.
- request_detail.html: payment_request (with status_meaning), instalment_total and share_url; cancel form; copy link via JS (button data-copy).
- reviews.html: reviews list (open items unless filter=closed); q/filter mine/overdue/closed/type; type query optional.
- review_detail.html: review (id,kind,kind_meaning,customer_name,amount_display,status,owner,deadline,evidence,note,outcome,prepared_by,resolved_by,affects_money,needs_evidence), refund (for refund requests; status Approved is shown as "Not refunded yet"), owners (members who may own items; never Viewers), can_decide (whether the simulated person may decide); POST action=assign owner=<member id>, or action=resolve outcome=Resolved/Dismissed note=... (label them Approve/Reject refund for refund requests); distinct reviewer enforced. Money outcomes aren't simulated success and Unknown cannot be manually marked Paid. Items needing provider evidence (Unknown result, Unclear match, Possible duplicate, Reversal) cannot be decided in the demo; Preparers may decide items that cannot move money; refund approval only marks Approved in the demo (no provider processing, nothing refunded).
- refund_form.html: form.as_p (amount,reason) and payment; POST current URL; second approval via Reviews.
- reports.html: metrics same today; export links /exports/payments/, /exports/consents/, /exports/reviews/, /exports/audit/ (Admins only), /exports/daily/; CSV downloads real. Give each Download CSV link its export name for screen readers. PDF not implemented yet, do not advertise.
- settings.html: form.as_p for organisation name/retry preset/receipts POST; members list; can_edit (Admins only; others see disabled fields and why); actor selector POST /demo-role/ member=id (section "Act as a team member", button "Switch person"); members with role_description; billing dict licence_display,usage_display,bank_display (Pay-by-bank fees),vat_display,total_display,eligible_count; gate_items list {label,done}; Paystack not connected, live disabled (no key form). Say that inviting team members and two-step verification are not available in this demo.
- preview.html: workspace ("Credit Desk"/"Cash Desk"), features list strings; clearly a preview, not available yet, no dates and no live data claims.
- start.html: standalone page (no staff shell) shown at / when the session has no workspace; messages; form POST /start/ with button "Open the demo workspace". Plain visits must never create a workspace. Not sign-in.
- public.html: standalone phone-first no staff shell. kind consent/payment/confirmation/expired; flow consent/payment (which link this is, also on confirmation and expired pages); lender, first_name, loan_ref, instalments optional, amount_display, max_display, expiry, retry_text (customer wording of the retry preset), instalment and instalment_total (payment), token. Header: "Valo Pay is a service provider to {lender}" (FR-CP1). On consent and payment forms POST current URL -> renders kind confirmation: a truthful demo page saying no bank was contacted and no money moved (never success, never a provider outage). Consent wording, schedule, withdrawal via lender contact; the authorisation and withdrawal sentences are legal text: change them only with owner approval. No third party scripts/fonts/tracking.

Review fields: id,kind,customer_name,amount_display,status,owner.name,deadline,overdue,evidence,note,outcome,prepared_by.name.
Audit: actor_name,action,detail,created_at.
Payment: customer_name,amount_display,status,source,reference,paid_at,id.
Use Django {% load static %}, {% csrf_token %}, {% url %} optional but direct absolute URLs as above simplest (root artifact). Never access Python methods requiring args. No inline JS using unescaped Django data. Accessible 360px layout and text labels for statuses, not colour alone.
